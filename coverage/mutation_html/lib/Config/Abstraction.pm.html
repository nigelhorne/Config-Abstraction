   40: =head1 SYNOPSIS
   41: 
   42: =head2 Pattern 1: Environment overrides file overrides in-code defaults
   43: 
   44: The most common pattern for twelve-factor-style apps.
   45: The C<data> argument supplies defaults, a YAML file supplies site configuration,
   46: and environment variables allow per-deployment overrides without touching any file.
   47: 
   48:   # config/base.yaml
   49:   #   database:
   50:   #     host: db.example.com
   51:   #     port: 5432
   52:   #     user: app
   53: 
   54:   use Config::Abstraction;
   55: 
   56:   my $config = Config::Abstraction->new(
   57:       data        => { database => { host => 'localhost', port => 5432 } },
   58:       config_dirs => ['config'],
   59:       env_prefix  => 'APP_',
   60:   );
   61: 
   62:   # In production, set APP_DATABASE__HOST=db.prod.example.com in the environment.
   63:   # That silently overrides the file value, which in turn overrides the default.
   64:   my $host = $config->get('database.host');
   65:   my $port = $config->get('database.port');
   66: 
   67: =head2 Pattern 2: Command-line arguments override everything
   68: 
   69: Useful for CLI tools where operator flags must win over every other source.
   70: 
   71:   # Run as: myscript.pl --APP_LOGLEVEL=debug --APP_DATABASE__HOST=localhost
   72: 
   73:   use Config::Abstraction;
   74: 
   75:   my $config = Config::Abstraction->new(
   76:       config_dirs => ['config'],
   77:       env_prefix  => 'APP_',
   78:   );
   79: 
   80:   # @ARGV is consumed and stripped during new(); the resulting config already
   81:   # has cli-layer values at the highest precedence.
   82:   my $loglevel = $config->get('loglevel');       # 'debug'  (from --APP_LOGLEVEL)
   83:   my $db_host  = $config->get('database.host');  # 'localhost' (from --APP_DATABASE__HOST)
   84: 
   85: =head2 Pattern 3: Multi-file layering (base + local override)
   86: 
   87: Separates shared defaults from machine-specific tweaks.
   88: Every developer has a C<base.yaml>; only the production server has C<local.yaml>.
   89: 
   90:   # config/base.yaml   -- checked into version control
   91:   #   database:
   92:   #     host: localhost
   93:   #     user: dev
   94:   #
   95:   # config/local.yaml  -- NOT checked in; production only
   96:   #   database:
   97:   #     host: db.prod.example.com
   98:   #     user: produser
   99:   #     password: s3cr3t
  100: 
  101:   use Config::Abstraction;
  102: 
  103:   my $config = Config::Abstraction->new(
  104:       config_dirs => ['config'],   # loads base.yaml then local.yaml
  105:       env_prefix  => 'APP_',
  106:   );
  107: 
  108:   # On a dev machine (no local.yaml): host='localhost', user='dev'
  109:   # On the prod server:               host='db.prod.example.com', user='produser'
  110:   my $db = $config->get('database.host');
  111:   my $user = $config->get('database.user');

  113: =head1 DESCRIPTION
  114: 
  115: C<Config::Abstraction> is a flexible configuration management layer that sits above C<Config::*> modules.
  116: It provides a simple way to layer multiple configuration sources with predictable merge order.
  117: It lets you define sources such as:
  118: 
  119: =over 4
  120: 
  121: =item * Perl hashes (in-memory defaults or dynamic values)
  122: 
  123: =item * Environment variables (with optional prefixes)
  124: 
  125: =item * Configuration files (YAML, JSON, INI, or plain key=value)
  126: 
  127: =item * Command-line arguments
  128: 
  129: =back
  130: 
  131: Sources are applied in the order they are provided. Later sources override
  132: earlier ones unless a key is explicitly set to C<undef> in the later source.
  133: 
  134: In addition to using drivers to load configuration data from multiple file
  135: formats (YAML, JSON, XML, and INI),
  136: it also allows levels of configuration, each of which overrides the lower levels.
  137: So, it also integrates environment variable
  138: overrides and command line arguments for runtime configuration adjustments.
  139: This module is designed to help developers manage layered configurations that can be loaded from files and overridden at run-time for debugging,
  140: offering a modern, robust and dynamic approach
  141: to configuration management.
  142: 
  143: =head2 Merge Precedence
  144: 
  145: Sources are applied in the order shown below.  Each row wins over every row
  146: above it.  When the same key appears in multiple sources, the highest-priority
  147: source always determines the final value - including when that value is C<undef>.
  148: 
  149:   Priority   Source                         Set with
  150:   --------   ------                         --------
  151:      1 (lo)  data constructor argument      data => { key => 'default' }
  152:      2        base.*  config files          config/base.yaml, base.json, ...
  153:      3        base.{env}.* config files     config/base.prod.yaml, ...
  154:      4        local.* config files          config/local.yaml, local.json, ...
  155:      5        local.{env}.* config files    config/local.prod.yaml, ...
  156:      6        default / script-name files   config/default.yaml, myapp.yaml, ...
  157:      7        config_file / config_files    config_file => '/etc/myapp.yaml'
  158:      8        Environment variables         APP_DATABASE__HOST=db.prod.example.com
  159:      9 (hi)  CLI arguments (@ARGV)          --APP_DATABASE__HOST=db.prod.example.com
  160: 
  161: The active environment is set by the C<environment> constructor option, or
  162: auto-detected from C<{env_prefix}ENV> (e.g. C<APP_ENV>), C<PLACK_ENV>, or
  163: C<NODE_ENV>.  When no environment is configured, rows 3 and 5 are skipped.
  164: 
  165: Within the file tier (rows 2-7), later files override earlier files using
  166: C<Hash::Merge> LEFT_PRECEDENT: every key in the later file wins over the same
  167: key in an earlier file, even when the later value is C<undef> (YAML C<~>).
  168: Nested hashes are merged recursively, so a C<local.yaml> that only sets
  169: C<database.host> will not erase C<database.port> from C<base.yaml>.
  170: 
  171:   Example - what wins for the key C<database.host> when APP_ENV=prod:
  172: 
  173:   data              =>  'localhost'              (overridden by base.yaml)
  174:   base.yaml         =>  'db.example.com'         (overridden by base.prod.yaml)
  175:   base.prod.yaml    =>  'db.prod.example.com'    (overridden by local.yaml)
  176:   local.yaml        =>  'db.local.example.com'   (overridden by local.prod.yaml)
  177:   local.prod.yaml   =>  'db.prod-local.example.com'  (overridden by $APP_DATABASE__HOST)
  178:   $APP_DATABASE__HOST  =>  'db.override.example.com'    <-- this wins
  179: 
  180: =head2 KEY FEATURES
  181: 
  182: =over 4
  183: 
  184: =item * Multi-Format Support
  185: 
  186: Supports configuration files in YAML, JSON, XML, and INI formats.
  187: Automatically merges configuration data from these different formats,
  188: allowing hierarchical configuration management.
  189: 
  190: =item * Environment Variable Overrides
  191: 
  192: Allows environment variables to override values in the configuration files.
  193: By setting environment variables with a specific prefix (default: C<APP_>),
  194: values in the configuration files can be dynamically adjusted without modifying
  195: the file contents.
  196: 
  197: =item * Flattened Configuration Option
  198: 
  199: Optionally supports flattening the configuration structure. This converts deeply
  200: nested configuration keys into a flat key-value format (e.g., C<database.user>
  201: instead of C<database-E<gt>{user}>). This makes accessing values easier for
  202: applications that prefer flat structures or need compatibility with flat
  203: key-value stores.
  204: 
  205: =item * Layered Configuration
  206: 
  207: Supports merging multiple layers of configuration files. For example, you can
  208: have a C<base.yaml> configuration file that provides default values, and a
  209: C<local.yaml> (or C<local.json>, C<local.xml>, etc.) file that overrides
  210: specific values. This allows for environment-specific configurations while
  211: keeping defaults intact.
  212: 
  213: =item * Merge Strategy
  214: 
  215: The module merges the configuration data intelligently, allowing values in more
  216: specific files (like C<local.yaml>, C<local.json>, C<local.xml>, C<local.ini>)
  217: to override values in base files. This enables a flexible and layered configuration
  218: system where you can set defaults and override them for specific environments.
  219: 
  220: =item * Error Handling
  221: 
  222: Includes error handling for loading configuration files.
  223: If any file fails to
  224: load (e.g., due to syntax issues), the module will throw descriptive error
  225: messages to help with debugging.
  226: 
  227: =item * Centralized Configuration Management
  228: 
  229: Supports remote configuration management files,
  230: so that configuration on remote machines can be centrally managed.
  231: 
  232: =back

  250: =item * INI (C<*.ini>)
  251: 
  252: Loaded with C<Config::IniFiles>.
  253: 
  254: =item * TOML (C<*.toml>)
  255: 
  256: Loaded with C<TOML::Tiny>, which implements TOML 1.0.  TOML is a good choice
  257: for human-editable configuration because its syntax is unambiguous: all values
  258: are typed, strings must be quoted, and nesting uses C<[section]> headers or
  259: dotted keys rather than indentation.
  260: 
  261:   # Example: config/base.toml
  262:   [database]
  263:   host   = "db.example.com"
  264:   port   = 5432
  265:   user   = "app"
  266: 
  267:   [cache]
  268:   ttl    = 300
  269:   debug  = false
  270: 
  271: C<base.toml> and C<local.toml> are discovered automatically in C<config_dirs>;
  272: C<local.toml> has higher precedence than C<base.toml>, following the same
  273: layering rules as all other formats.  TOML is also tried as a fallback parser
  274: in the all-parsers chain used for extensionless C<config_file> entries.
  275: 
  276: If C<TOML::Tiny> is not installed, TOML files are silently skipped with a
  277: C<carp> warning.
  278: 
  279: =back

  281: =head2 ENVIRONMENT VARIABLE HANDLING
  282: 
  283: Configuration values can be overridden via environment variables. Environment variables use double underscores (__) to denote nested configuration keys and single underscores remain as part of the key name under the prefix namespace.
  284: 
  285: For example:
  286: 
  287:   APP_DATABASE__USER becomes database.user (nested structure)
  288: 
  289:     $ export APP_DATABASE__USER="env_user"
  290: 
  291: will override any value set for `database.user` in the configuration files.
  292: 
  293:   APP_LOGLEVEL becomes APP.loglevel (flat under prefix namespace)
  294: 
  295:   APP_API__RATE_LIMIT becomes api.rate_limit (mixed usage)
  296: 
  297: This allows you to override both top-level and nested configuration values using environment variables.
  298: 
  299: Configuration values can be overridden via the command line (C<@ARGV>).
  300: For instance, if you have a key in the configuration such as C<database.user>,
  301: you can override it by adding C<"--APP_DATABASE__USER=other_user_name"> to the command line arguments.
  302: This will override any value set for C<database.user> in the configuration files.

  304: =head2 EXAMPLE CONFIGURATION FLOW
  305: 
  306: =over 4
  307: 
  308: =item 1. Data Argument
  309: 
  310: The data passed into the constructor via the C<data> argument is the starting point.
  311: Essentially,
  312: this contains the default values.
  313: 
  314: =item 2. Loading Files
  315: 
  316: The module then looks for configuration files in the specified directories.
  317: It loads the following files in order of preference:
  318: C<base.yaml>, C<local.yaml>, C<base.json>, C<local.json>, C<base.xml>,
  319: C<local.xml>, C<base.ini>, and C<local.ini>.
  320: 
  321: If C<config_file> or C<config_files> is set, those files are loaded last.
  322: 
  323: If no C<config_dirs> is given, try hard to find the files in various places.
  324: 
  325: The value of C<config_dirs> can be overridden at runtime by the environment variable CONFIG_DIR
  326: (note that is just one directory, hence it's CONFIG_DIR not CONFIG_DIRS).
  327: 
  328: =item 3. Merging and Resolving
  329: 
  330: The module merges the contents of these files, with more specific configurations
  331: (e.g., C<local.*>) overriding general ones (e.g., C<base.*>).
  332: 
  333: =item 4. Environment Overrides
  334: 
  335: After loading and merging the configuration files,
  336: the environment variables are
  337: checked and used to override any conflicting settings.
  338: 
  339: =item 5. Command Line
  340: 
  341: Next, the command line arguments are checked and used to override any conflicting settings.
  342: 
  343: =item 6. Accessing Values
  344: 
  345: Values in the configuration can be accessed using a dotted notation
  346: (e.g., C<'database.user'>), regardless of the file format used.
  347: 
  348: =back

  351: 
  352: =head2 new
  353: 
  354: Constructor for creating a new configuration object.
  355: 
  356: Options:
  357: 
  358: =over 4
  359: 
  360: =item * C<config_dirs>
  361: 
  362: An arrayref of directories to look for configuration files
  363: (default: C<$CONFIG_DIR>, C<$HOME/.conf>, C<$HOME/config>, C<$HOME/conf>, C<$DOCUMENT_ROOT/conf>, C<$DOCUMENT_ROOT/../conf>, C<conf>).
  364: 
  365: For centralised configuration management,
  366: entries beginning with C</../> are treated as remote specifications using the
  367: Newcastle Connection convention -- see L</Remote configuration directories (Newcastle Connection)>.
  368: 
  369: =item * C<config_file>
  370: 
  371: Points to a configuration file of any format.
  372: 
  373: =item * C<config_files>
  374: 
  375: An arrayref of files to look for in the configuration directories.
  376: Put the more important files later,
  377: since later files override earlier ones.
  378: 
  379: Considers the files C<default> and C<$script_name> before looking at C<config_file> and C<config_files>.
  380: 
  381: =item * C<data>
  382: 
  383: A hash ref of default data to prime the configuration with.
  384: These are applied before loading
  385: other sources and can be overridden by later sources or by explicitly passing
  386: options directly to C<new>.
  387: 
  388:   $config = Config::Abstraction->new(
  389:       data => {
  390:           log_level => 'info',
  391:           retries => 3,
  392:       }
  393:   );
  394: 
  395: =item * C<defaults>
  396: 
  397: A hash reference that provides default values for the object's own attributes (such as C<config_dirs>, C<logger>, C<flatten>, etc.).
  398: If this option is supplied,
  399: the object is initialized using the keys in this hash as the base;
  400: any other options passed directly to C<new()> (aside from C<env_prefix>) are ignored.
  401: This allows you to pre-define a standard configuration profile for the object itself.
  402: Note that C<defaults> is distinct from the C<data> option - C<data> supplies the initial configuration values that will be merged with files, environment, and command line,
  403: while C<defaults> sets the object's internal parameters.
  404: The C<env_prefix> value,
  405: if provided as a top-level argument,
  406: still takes precedence over any C<env_prefix> that might exist inside the C<defaults> hash.
  407: 
  408: =item * C<encryption_key>
  409: 
  410: A 256-bit (32-byte) AES key used to transparently decrypt C<ENC[...]> values found in any
  411: configuration source after the full merge.  The key may be supplied as:
  412: 
  413: =over 4
  414: 
  415: =item 32 raw bytes
  416: 
  417: =item 64 lowercase or uppercase hex characters
  418: 
  419: =item 44 Base64 or Base64url characters (standard or URL-safe alphabet, with or without trailing C<=>)
  420: 
  421: =back
  422: 
  423: If no key is configured (and neither C<encryption_key_file> nor the corresponding
  424: environment variables are set), C<ENC[...]> tokens are left as literal strings.
  425: Decryption requires L<CryptX> (C<Crypt::AuthEnc::GCM>); if that module is absent a
  426: C<croak> is raised when an encrypted value is encountered.
  427: 
  428: See L</ENCRYPTED VALUES> for the full workflow.
  429: 
  430: =item * C<encryption_key_file>
  431: 
  432: Path to a file whose first line contains the encryption key in any of the formats accepted
  433: by C<encryption_key>.  Takes precedence over the C<ENCRYPTION_KEY_FILE> and
  434: C<{env_prefix}ENCRYPTION_KEY_FILE> environment variables, but is overridden by a key
  435: supplied directly via C<encryption_key>.
  436: 
  437: =item * C<env_prefix>
  438: 
  439: A prefix for environment variable keys and comment line options, e.g. C<MYAPP_DATABASE__USER>,
  440: (default: C<'APP_'>).
  441: 
  442: =item * C<environment>
  443: 
  444: The name of the active deployment environment (e.g. C<'dev'>, C<'staging'>, C<'prod'>).
  445: When set, config files named C<base.{env}.*> are loaded immediately after their C<base.*>
  446: equivalents, and C<local.{env}.*> files are loaded immediately after C<local.*> files,
  447: giving two additional override tiers at no cost to the base configuration.
  448: 
  449:   my $cfg = Config::Abstraction->new(
  450:       config_dirs => ['config'],
  451:       environment => 'prod',          # loads base.prod.yaml, local.prod.yaml, ...
  452:   );
  453: 
  454: If C<environment> is not given, the value is auto-detected in this order:
  455: 
  456: =over 4
  457: 
  458: =item 1. C<{env_prefix}ENV> environment variable (e.g. C<APP_ENV>)
  459: 
  460: =item 2. C<PLACK_ENV>
  461: 
  462: =item 3. C<NODE_ENV>
  463: 
  464: =back
  465: 
  466: When none of these is set, the environment-specific tiers are silently skipped.
  467: The environment name must contain only ASCII letters, digits, hyphens, and underscores
  468: (matched against C</^[A-Za-z0-9_\-]+$/>); any other value causes a C<croak>.
  469: 
  470: =item * C<file>
  471: 
  472: Synonym for C<config_file>
  473: 
  474: =item * C<flatten>
  475: 
  476: If true, returns a flat hash structure like C<{database.user}> (default: C<0>) instead of C<{database}{user}>.
  477: `
  478: =item * C<level>
  479: 
  480: Level for logging.
  481: 
  482: =item * C<logger>
  483: 
  484: Used for warnings and traces.
  485: It can be an object that understands warn() and trace() messages,
  486: such as a L<Log::Log4perl> or L<Log::Any> object,

  488: a reference to an array,
  489: or a filename.

  492: 
  493: A synonym of C<config_dirs>.
  494: 
  495: =item * C<sep_char>
  496: 
  497: The separator in keys.
  498: The default is a C<'.'>,
  499: as in dotted notation,
  500: such as C<'database.user'>.

  502: =item * C<schema>
  503: 
  504: A L<Params::Validate::Strict> compatible schema to validate the configuration file against.
  505: 
  506: =item * C<validators>
  507: 
  508: A hashref mapping dotted config keys to validation rules.  Each rule is applied to the
  509: corresponding value in the merged configuration immediately after all sources have been
  510: merged (or on first access when C<lazy> is set).  A validation failure croaks.
  511: 
  512: Each rule may be one of:
  513: 
  514: =over 4
  515: 
  516: =item A type name string
  517: 
  518:   validators => {
  519:       'database.port' => 'integer',
  520:       'app.name'      => 'string',
  521:       'price'         => 'number',
  522:       'enabled'       => 'boolean',
  523:       'tags'          => 'array',
  524:       'settings'      => 'hash',
  525:   }
  526: 
  527: Supported types: C<integer> (matches C</^-?\d+$/> -- no decimal point),
  528: C<number> or C<float> (C<Scalar::Util::looks_like_number>), C<boolean>
  529: (C<0>, C<1>, C<true>, C<false>, C<yes>, C<no> -- case-insensitive),
  530: C<string> (any defined non-reference scalar), C<array> (arrayref),
  531: C<hash> (hashref).
  532: 
  533: =item A compiled regular expression
  534: 
  535:   validators => {
  536:       'log.level' => qr/^(?:debug|info|warn|error|fatal)$/i,
  537:       'app.name'  => qr/^\w[\w\-]{1,63}$/,
  538:   }
  539: 
  540: The value must be defined and must match the regex.
  541: 
  542: =item A coderef
  543: 
  544:   validators => {
  545:       'database.port' => sub { my $v = shift; defined($v) && $v >= 1 && $v <= 65535 },
  546:   }
  547: 
  548: Called with the value as its only argument.  Must return a true value; otherwise the
  549: constructor croaks.
  550: 
  551: =item A hashref combining multiple constraints
  552: 
  553:   validators => {
  554:       'database.port' => {
  555:           type     => 'integer',
  556:           min      => 1,
  557:           max      => 65535,
  558:           required => 1,
  559:       },
  560:       'api.key' => {
  561:           pattern  => qr/^[A-Za-z0-9]{32}$/,
  562:           required => 1,
  563:       },
  564:   }
  565: 
  566: Keys: C<type> (type-name string as above), C<pattern> (compiled regex), C<min> (numeric
  567: lower bound, inclusive), C<max> (numeric upper bound, inclusive), C<required> (if true,
  568: the key must exist and its value must be defined).

  604: they will access it.
  605: 
  606: B<Differences from the default (eager) behaviour, and the debugging problems they cause:>
  607: 
  608: =over 4
  609: 
  610: =item 1. C<new()> always succeeds, even when no configuration exists.
  611: 
  612: In eager mode, C<new()> returns C<undef> immediately when no files are found and no
  613: C<data> was supplied, so a missing config is caught at the point of construction.
  614: In lazy mode, C<new()> always returns a blessed object.  If the configuration
  615: directories do not exist, the files are missing, or the prefix is wrong, you will
  616: not find out until the first accessor call - which may be deep inside your business
  617: logic, far from where the object was created.
  618: 
  619:   # Problem: the typo in config_dirs goes unnoticed until runtime
  620:   my $cfg = Config::Abstraction->new(
  621:       config_dirs => ['/etc/myapp/conifg'],   # typo - directory does not exist
  622:       lazy => 1,
  623:   );
  624:   # ... many lines later ...
  625:   my $host = $cfg->get('database.host');      # silently returns undef here
  626: 
  627: =item 2. Schema validation errors appear at the wrong place in the call stack.
  628: 
  629: When a C<schema> is supplied, eager mode validates the merged configuration inside
  630: C<new()> and throws immediately if the config does not match.  In lazy mode,
  631: validation is deferred to the first accessor call.  A schema violation therefore
  632: surfaces as an exception thrown by C<get()> or C<all()>, not by C<new()>, and the
  633: stack trace points to the accessor call rather than the construction site.  If the
  634: object is created in one module and accessed in another, the error message can be
  635: very misleading.
  636: 
  637: =item 3. Environment variables and C<@ARGV> are captured at access time, not construction time.
  638: 
  639: The module reads C<%ENV> and C<@ARGV> during C<_load_config()>.  In eager mode that
  640: happens in C<new()>, so the configuration reflects the environment at the moment the
  641: object is built.  In lazy mode, any change to C<%ENV> or C<@ARGV> between C<new()>
  642: and the first accessor call is silently picked up.  This makes test isolation harder:
  643: setting an environment variable I<after> constructing a lazy object will affect the
  644: values it returns, which is not the case with an eager object.
  645: 
  646: =item 4. File system state may change between construction and first use.
  647: 
  648: Because lazy mode defers all I/O, the files that are read are those that exist at the
  649: moment of first access, not at the moment C<new()> is called.  If a config file is
  650: written, deleted, or replaced between those two points (for example, by another
  651: process or test fixture), the object will silently use the new state.  An eager object
  652: is immune to this race.
  653: 
  654: =item 5. Errors from format parsers appear at accessor call sites.
  655: 
  656: Malformed YAML, JSON, XML, or INI files emit a C<carp> warning and are skipped during
  657: loading.  In eager mode those warnings appear near the program's startup.  In lazy mode
  658: they appear during the first accessor call, which can make it look as though a routine
  659: in your business logic is generating configuration warnings.
  660: 
  661: =back
  662: 
  663: B<When to use lazy loading:> It is most useful when a C<Config::Abstraction> object is
  664: created speculatively at module-load time and may never be accessed (for example, in a
  665: web framework where the config object is built for every request but some request paths
  666: never read it).  Avoid it when startup correctness is important, when you rely on
  667: C<new()> returning C<undef> to detect missing configuration, or when you use schema
  668: validation and need errors to point at the construction site.

 2298: =head2 Remote configuration directories (Newcastle Connection)
 2299: 
 2300: Any entry in C<config_dirs> whose path begins with C</../> is treated as a
 2301: remote specification rather than a local directory:
 2302: 
 2303:   /../hostname/path/to/dir
 2304: 
 2305: The hostname and directory are extracted, and the same standard files searched
 2306: locally (C<base.yaml>, C<local.yaml>, C<base.json>, etc.) are fetched from
 2307: the remote machine via L<File::Slurp::Remote> over SSH.
 2308: 
 2309: When the hostname resolves to the local machine -- C<localhost>, C<127.0.0.1>,
 2310: C<::1>, or the value returned by C<Sys::Hostname::hostname()> (checked as
 2311: both fully-qualified and short form, case-insensitively) -- the C</../host/>
 2312: wrapper is silently unwrapped and the enclosed path is processed through the
 2313: normal local file pipeline instead.  No SSH connection is made.  This means a
 2314: configuration written for a shared remote host degrades gracefully when run on
 2315: that host itself:
 2316: 
 2317:   # On any other machine: fetches /etc/myapp over SSH
 2318:   # On cfg-server itself: reads /etc/myapp from disk directly
 2319:   config_dirs => ['/../cfg-server/etc/myapp']
 2320: 
 2321: Remote directories participate in the normal merge pipeline and can be freely
 2322: mixed with local ones:
 2323: 
 2324:   my $cfg = Config::Abstraction->new(
 2325:       config_dirs => [
 2326:           '/etc/myapp',                        # local
 2327:           '/../deploy@cfg-server/etc/myapp',   # remote via SSH (local on cfg-server)
 2328:       ],
 2329:   );
 2330: 
 2331: SSH authentication is handled by the system SSH client.
 2332: No extra constructor options are required; use your SSH agent or
 2333: C<~/.ssh/config> for host-specific settings.
 2334: 
 2335: L<File::Slurp::Remote> must be installed for remote directories to work.
 2336: If it is absent the directory is silently skipped and a warning is emitted.
 2337: 
 2338: =head3 Why C</../> (the Newcastle Connection convention)
 2339: 
 2340: Several syntaxes were considered for marking a C<config_dirs> entry as remote.
 2341: Each alternative was rejected for a concrete reason:
 2342: 
 2343: =over 4
 2344: 
 2345: =item C<hostname/path> -- ambiguous
 2346: 
 2347: Indistinguishable from a relative local directory named C<hostname>.
 2348: The module cannot tell at parse time whether C<myserver/etc> is a two-level
 2349: local path or a remote specification.
 2350: 
 2351: =item C<hostname:/path> -- collides with Windows drive letters
 2352: 
 2353: The C<X:\> drive-letter convention on Windows uses exactly the same
 2354: C<letter:> prefix.  A single-letter hostname would be misidentified as a
 2355: drive, and path-normalisation code on Windows would mangle it.
 2356: 
 2357: =item C<file://hostname/path> -- wrong semantics
 2358: 
 2359: RFC 8089 defines C<file://> as a reference to a B<local> file.
 2360: C<file:///etc/passwd> (three slashes, empty host) is the canonical local form;
 2361: C<file://hostname/path> is reserved for the host component but is explicitly
 2362: discouraged for general use and is not understood by most tooling as meaning
 2363: SSH.
 2364: 
 2365: =item C<ssh://hostname/path> -- requires URI parsing
 2366: 
 2367: Introduces a dependency on URI parsing (or a bespoke prefix check) and
 2368: implies a specific transport.  C<File::Slurp::Remote> already abstracts
 2369: the transport; encoding C<ssh://> in the path would be misleading if a future
 2370: version of that module supports other transports such as C<rsync://>.
 2371: 
 2372: =item C</../hostname/path> -- the Newcastle Connection
 2373: 
 2374: The Newcastle Connection (Brownbridge, Dion, Elsworth, 1982) is a distributed
 2375: Unix convention in which the token C</../> at the start of a pathname means
 2376: "leave the local namespace and enter the named remote host".
 2377: It works because C</../> B<cannot exist> as a real filesystem path:
 2378: C<..> from the root directory resolves back to the root on every POSIX system,
 2379: so C</../> always denotes the root itself, never a child of the root.
 2380: No pathname-normalisation step, C<chdir>, or filesystem traversal will ever
 2381: produce a path that legitimately begins with C</../>, which means the prefix
 2382: is a permanent, collision-free sentinel that requires only a regex to detect.
 2383: 
 2384: =back
 2385: 
 2386: The Newcastle Connection prefix is therefore the only choice that is:
 2387: 
 2388: =over 4
 2389: 
 2390: =item * unambiguous on all platforms (POSIX and Windows)
 2391: 
 2392: =item * impossible to produce accidentally from a real local path
 2393: 
 2394: =item * detectable with a single C<m{^\Q/../\E}> regex, no URI parser needed
 2395: 
 2396: =item * transport-neutral (the hostname is passed to whatever remote driver is installed)
 2397: 
 2398: =back

 2789:   my $merged = $cfg->merge_defaults(defaults => \%my_defaults);
 2790: 
 2791: With the first form, C<Params::Get> treats the single hashref as the entire
 2792: parameter bag and returns the full config without merging anything.
 2793: 
 2794: =head2 3. Shallow merge in merge_defaults() silently drops nested keys from defaults
 2795: 
 2796: Without C<merge =E<gt> 1>, C<merge_defaults()> uses a plain Perl hash merge
 2797: (C<{ %defaults, %config }>) at the top level.  If the config contains a nested hash
 2798: for a key, it entirely replaces the corresponding nested hash in your defaults - any
 2799: keys that exist only in the defaults' nested hash are silently discarded.
 2800: 
 2801:   my $cfg = Config::Abstraction->new(
 2802:       data        => { db => { host => 'localhost', port => 5432 } },
 2803:       config_dirs => [],
 2804:   );
 2805: 
 2806:   my $merged = $cfg->merge_defaults(defaults => { db => { user => 'guest' } });
 2807:   # $merged->{db}{user} is UNDEF -- the whole 'db' hash was replaced by the config's version
 2808: 
 2809:   # To combine nested keys from both sides, pass merge => 1:
 2810:   my $merged = $cfg->merge_defaults(defaults => { db => { user => 'guest' } }, merge => 1);
 2811:   # $merged->{db}{user} is 'guest', $merged->{db}{host} is 'localhost'
 2812: 
 2813: =head2 4. undef from a higher-priority source permanently wins
 2814: 
 2815: C<Hash::Merge> LEFT_PRECEDENT means that an explicit C<undef> (YAML C<~>) in a
 2816: higher-priority source overrides a real value in a lower-priority source, including
 2817: when the lower-priority value is defined.
 2818: 
 2819:   # base.yaml:  timeout: 30
 2820:   # local.yaml: timeout: ~
 2821: 
 2822:   my $t = $cfg->get('timeout');   # undef -- local.yaml's null wins over base.yaml
 2823: 
 2824: This is intentional: it lets a local config deliberately unset a value.  If you
 2825: want to detect whether a key was explicitly nulled versus simply absent, use
 2826: C<explain_sources()> and inspect the C<sources> list.
 2827: 
 2828: =head2 5. Double underscore vs. single underscore in environment variable names
 2829: 
 2830: Single underscores are part of the key name; double underscores create a nesting level.
 2831: 
 2832:   APP_LOG_LEVEL=debug       => key 'log_level'   (single underscore, flat key)
 2833:   APP_DATABASE__HOST=db     => key 'database.host' (double underscore, nested)
 2834:   APP_API__RATE_LIMIT=100   => key 'api.rate_limit' (double underscore + single)
 2835: 
 2836: A common mistake is using single underscores expecting nested keys:
 2837: 
 2838:   APP_DATABASE_HOST=db   # produces key 'database_host', NOT 'database.host'
 2839: 
 2840: =head2 6. Using AUTOLOAD requires sep_char set to '_'
 2841: 
 2842: AUTOLOAD translates method names to config keys using C<sep_char>.  The default
 2843: C<sep_char> is C<'.'>, but method names cannot contain dots.  Set C<sep_char =E<gt> '_'>
 2844: to use AUTOLOAD, and be aware that this makes single underscores into hierarchy separators.
 2845: 
 2846:   my $cfg = Config::Abstraction->new(
 2847:       data    => { database => { host => 'localhost' } },
 2848:       sep_char => '_',
 2849:       config_dirs => [],
 2850:   );
 2851:   my $host = $cfg->database_host();   # works
 2852:   my $bad  = $cfg->no_such_key();    # dies: No such config key 'no_such_key'
 2853: 
 2854: =head2 7. Absolute config_file paths require an empty or omitted config_dirs
 2855: 
 2856: On Unix, C<File::Spec-E<gt>catfile('/etc', '/absolute/path.yaml')> concatenates the
 2857: two strings instead of letting the absolute path take over, producing a wrong path.
 2858: When C<config_file> is an absolute path, either omit C<config_dirs> entirely
 2859: (the constructor sets it to C<['']> automatically) or pass C<config_dirs =E<gt> ['']>
 2860: explicitly.
 2861: 
 2862:   # WRONG on Unix -- produces '/etc/etc/myapp/app.yaml'
 2863:   Config::Abstraction->new(
 2864:       config_file => '/etc/myapp/app.yaml',
 2865:       config_dirs => ['/etc'],
 2866:   );
 2867: 
 2868:   # RIGHT
 2869:   Config::Abstraction->new( config_file => '/etc/myapp/app.yaml' );
 2870: 
 2871: =head2 8. Tests must isolate from the developer's real config files
 2872: 
 2873: A call to C<new()> without C<config_dirs> will scan C</etc>, C<~/.conf>,
 2874: C<~/.config>, and other default locations and load any C<base.yaml> or
 2875: C<local.yaml> it finds there.  In a test suite this injects real host
 2876: configuration into your test object, causing non-deterministic failures.
 2877: 
 2878: Always pass C<config_dirs =E<gt> []> in tests that use only in-memory C<data>:
 2879: 
 2880:   my $cfg = Config::Abstraction->new(
 2881:       data        => { key => 'value' },
 2882:       config_dirs => [],              # do not scan the filesystem
 2883:   );
 2884: 
 2885: =head2 9. lazy => 1 defers errors until the first accessor call
 2886: 
 2887: With C<lazy =E<gt> 1>, C<new()> always returns a blessed object - it cannot return
 2888: C<undef> for a missing config, and any schema validation errors surface at the first
 2889: C<get()> or C<all()> call rather than at construction time.  See the C<lazy>
 2890: option documentation in L</new> for the full list of debugging implications.

 2975: =head1 LIMITATIONS
 2976: 
 2977: =over 4
 2978: 
 2979: =item * B<No separator escaping>
 2980: 
 2981: The separator character (C<sep_char>, default C<.>) cannot be embedded in a key name.
 2982: A key that literally contains a dot cannot be accessed via C<get()> when C<sep_char> is
 2983: the default.  Workaround: set C<sep_char> to a character not present in any key.
 2984: 
 2985: =item * B<Data::Reuse fixation disabled>
 2986: 
 2987: The C<Data::Reuse::fixate()> call inside C<get()> is currently a no-op because the
 2988: behaviour of C<Crypt::Storable::dclone> differs between Linux and macOS in a way
 2989: that cannot be resolved portably (RT#100461).  Hash values returned by C<get()> are
 2990: mutable references, not read-only copies.
 2991: 
 2992: =item * B<Windows environment variable case sensitivity>
 2993: 
 2994: On Windows, environment variable names are case-insensitive at the OS level but
 2995: case-sensitive in C<%ENV> as seen by Perl.  Overriding config keys via environment
 2996: variables may silently fail if the case does not match exactly.
 2997: 
 2998: =item * B<AUTOLOAD requires sep_char set to '_'>
 2999: 
 3000: AUTOLOAD method dispatch converts underscores to key separators.  If C<sep_char> is
 3001: the default C<'.'>, AUTOLOAD cannot reach nested keys because Perl method names cannot
 3002: contain dots.
 3003: 
 3004: =item * B<Remote directory TOML support requires File::Slurp::Remote>
 3005: 
 3006: TOML files in Newcastle Connection remote directories are only fetched when the
 3007: C<File::Slurp::Remote> module is installed.  Without it, remote directories are
 3008: skipped entirely regardless of file format.
 3009: 
 3010: =back
