   46: 
   47: =head2 Pattern 1: Environment overrides file overrides in-code defaults
   48: 
   49: The most common pattern for twelve-factor-style apps.
   50: The C<data> argument supplies defaults, a YAML file supplies site configuration,
   51: and environment variables allow per-deployment overrides without touching any file.
   52: 
   53:   # config/base.yaml
   54:   #   database:
   55:   #     host: db.example.com
   56:   #     port: 5432
   57:   #     user: app
   58: 
   59:   use Config::Abstraction;
   60: 
   61:   my $config = Config::Abstraction->new(
   62:       data        => { database => { host => 'localhost', port => 5432 } },
   63:       config_dirs => ['config'],
   64:       env_prefix  => 'APP_',
   65:   );
   66: 
   67:   # In production, set APP_DATABASE__HOST=db.prod.example.com in the environment.
   68:   # That silently overrides the file value, which in turn overrides the default.
   69:   my $host = $config->get('database.host');
   70:   my $port = $config->get('database.port');
   71: 
   72: =head2 Pattern 2: Command-line arguments override everything
   73: 
   74: Useful for CLI tools where operator flags must win over every other source.
   75: 
   76:   # Run as: myscript.pl --APP_LOGLEVEL=debug --APP_DATABASE__HOST=localhost
   77: 
   78:   use Config::Abstraction;
   79: 
   80:   my $config = Config::Abstraction->new(
   81:       config_dirs => ['config'],
   82:       env_prefix  => 'APP_',
   83:   );
   84: 
   85:   # @ARGV is consumed and stripped during new(); the resulting config already
   86:   # has cli-layer values at the highest precedence.
   87:   my $loglevel = $config->get('loglevel');       # 'debug'  (from --APP_LOGLEVEL)
   88:   my $db_host  = $config->get('database.host');  # 'localhost' (from --APP_DATABASE__HOST)
   89: 
   90: =head2 Pattern 3: Multi-file layering (base + local override)
   91: 
   92: Separates shared defaults from machine-specific tweaks.
   93: Every developer has a C<base.yaml>; only the production server has C<local.yaml>.
   94: 
   95:   # config/base.yaml   -- checked into version control
   96:   #   database:
   97:   #     host: localhost
   98:   #     user: dev
   99:   #
  100:   # config/local.yaml  -- NOT checked in; production only
  101:   #   database:
  102:   #     host: db.prod.example.com
  103:   #     user: produser
  104:   #     password: s3cr3t
  105: 
  106:   use Config::Abstraction;

  111:   );

  113:   # On a dev machine (no local.yaml): host='localhost', user='dev'
  114:   # On the prod server:               host='db.prod.example.com', user='produser'
  115:   my $db = $config->get('database.host');
  116:   my $user = $config->get('database.user');

  118: =head1 DESCRIPTION
  119: 
  120: C<Config::Abstraction> is a flexible configuration management layer that sits above C<Config::*> modules.
  121: It provides a simple way to layer multiple configuration sources with predictable merge order.
  122: It lets you define sources such as:
  123: 
  124: =over 4
  125: 
  126: =item * Perl hashes (in-memory defaults or dynamic values)
  127: 
  128: =item * Environment variables (with optional prefixes)
  129: 
  130: =item * Configuration files (YAML, JSON, INI, or plain key=value)
  131: 
  132: =item * Command-line arguments
  133: 
  134: =back
  135: 
  136: Sources are applied in the order they are provided. Later sources override
  137: earlier ones unless a key is explicitly set to C<undef> in the later source.
  138: 
  139: In addition to using drivers to load configuration data from multiple file
  140: formats (YAML, JSON, XML, and INI),
  141: it also allows levels of configuration, each of which overrides the lower levels.
  142: So, it also integrates environment variable
  143: overrides and command line arguments for runtime configuration adjustments.
  144: This module is designed to help developers manage layered configurations that can be loaded from files and overridden at run-time for debugging,
  145: offering a modern, robust and dynamic approach
  146: to configuration management.
  147: 
  148: =head2 Merge Precedence
  149: 
  150: Sources are applied in the order shown below.  Each row wins over every row
  151: above it.  When the same key appears in multiple sources, the highest-priority
  152: source always determines the final value - including when that value is C<undef>.
  153: 
  154:   Priority   Source                         Set with
  155:   --------   ------                         --------
  156:      1 (lo)  data constructor argument      data => { key => 'default' }
  157:      2        base.*  config files          config/base.yaml, base.json, ...
  158:      3        base.{env}.* config files     config/base.prod.yaml, ...
  159:      4        local.* config files          config/local.yaml, local.json, ...
  160:      5        local.{env}.* config files    config/local.prod.yaml, ...
  161:      6        default / script-name files   config/default.yaml, myapp.yaml, ...
  162:      7        config_file / config_files    config_file => '/etc/myapp.yaml'
  163:      8        Environment variables         APP_DATABASE__HOST=db.prod.example.com
  164:      9 (hi)  CLI arguments (@ARGV)          --APP_DATABASE__HOST=db.prod.example.com
  165: 
  166: The active environment is set by the C<environment> constructor option, or
  167: auto-detected from C<{env_prefix}ENV> (e.g. C<APP_ENV>), C<PLACK_ENV>, or
  168: C<NODE_ENV>.  When no environment is configured, rows 3 and 5 are skipped.
  169: 
  170: Within the file tier (rows 2-7), later files override earlier files using
  171: C<Hash::Merge> LEFT_PRECEDENT: every key in the later file wins over the same
  172: key in an earlier file, even when the later value is C<undef> (YAML C<~>).
  173: Nested hashes are merged recursively, so a C<local.yaml> that only sets
  174: C<database.host> will not erase C<database.port> from C<base.yaml>.
  175: 
  176:   Example - what wins for the key C<database.host> when APP_ENV=prod:
  177: 
  178:   data              =>  'localhost'              (overridden by base.yaml)
  179:   base.yaml         =>  'db.example.com'         (overridden by base.prod.yaml)
  180:   base.prod.yaml    =>  'db.prod.example.com'    (overridden by local.yaml)
  181:   local.yaml        =>  'db.local.example.com'   (overridden by local.prod.yaml)
  182:   local.prod.yaml   =>  'db.prod-local.example.com'  (overridden by $APP_DATABASE__HOST)
  183:   $APP_DATABASE__HOST  =>  'db.override.example.com'    <-- this wins
  184: 
  185: =head2 KEY FEATURES
  186: 
  187: =over 4
  188: 
  189: =item * Multi-Format Support
  190: 
  191: Supports configuration files in YAML, JSON, XML, and INI formats.
  192: Automatically merges configuration data from these different formats,
  193: allowing hierarchical configuration management.
  194: 
  195: =item * Environment Variable Overrides
  196: 
  197: Allows environment variables to override values in the configuration files.
  198: By setting environment variables with a specific prefix (default: C<APP_>),
  199: values in the configuration files can be dynamically adjusted without modifying
  200: the file contents.
  201: 
  202: =item * Flattened Configuration Option
  203: 
  204: Optionally supports flattening the configuration structure. This converts deeply
  205: nested configuration keys into a flat key-value format (e.g., C<database.user>
  206: instead of C<database-E<gt>{user}>). This makes accessing values easier for
  207: applications that prefer flat structures or need compatibility with flat
  208: key-value stores.
  209: 
  210: =item * Layered Configuration
  211: 
  212: Supports merging multiple layers of configuration files. For example, you can
  213: have a C<base.yaml> configuration file that provides default values, and a
  214: C<local.yaml> (or C<local.json>, C<local.xml>, etc.) file that overrides
  215: specific values. This allows for environment-specific configurations while
  216: keeping defaults intact.
  217: 
  218: =item * Merge Strategy
  219: 
  220: The module merges the configuration data intelligently, allowing values in more
  221: specific files (like C<local.yaml>, C<local.json>, C<local.xml>, C<local.ini>)
  222: to override values in base files. This enables a flexible and layered configuration
  223: system where you can set defaults and override them for specific environments.
  224: 
  225: =item * Error Handling
  226: 
  227: Includes error handling for loading configuration files.
  228: If any file fails to
  229: load (e.g., due to syntax issues), the module will throw descriptive error
  230: messages to help with debugging.
  231: 
  232: =item * Centralized Configuration Management
  233: 
  234: Supports remote configuration management files,
  235: so that configuration on remote machines can be centrally managed.
  236: 
  237: =back

  240: 
  241: =over 4
  242: 
  243: =item * YAML (C<*.yaml>, C<*.yml>)
  244: 
  245: Loaded with C<YAML::XS>.
  246: 
  247: =item * JSON (C<*.json>)
  248: 
  249: Loaded with C<JSON::MaybeXS>.
  250: 
  251: =item * XML (C<*.xml>)
  252: 
  253: Loaded with C<XML::Simple> (preferred) or C<XML::PP> (fallback).
  254: 
  255: =item * INI (C<*.ini>)
  256: 
  257: Loaded with C<Config::IniFiles>.
  258: 
  259: =item * TOML (C<*.toml>)
  260: 
  261: Loaded with C<TOML::Tiny>, which implements TOML 1.0.  TOML is a good choice
  262: for human-editable configuration because its syntax is unambiguous: all values
  263: are typed, strings must be quoted, and nesting uses C<[section]> headers or
  264: dotted keys rather than indentation.
  265: 
  266:   # Example: config/base.toml
  267:   [database]
  268:   host   = "db.example.com"
  269:   port   = 5432
  270:   user   = "app"
  271: 
  272:   [cache]
  273:   ttl    = 300
  274:   debug  = false
  275: 
  276: C<base.toml> and C<local.toml> are discovered automatically in C<config_dirs>;
  277: C<local.toml> has higher precedence than C<base.toml>, following the same
  278: layering rules as all other formats.  TOML is also tried as a fallback parser
  279: in the all-parsers chain used for extensionless C<config_file> entries.
  280: 
  281: If C<TOML::Tiny> is not installed, TOML files are silently skipped with a
  282: C<carp> warning.
  283: 
  284: =back

  286: =head2 ENVIRONMENT VARIABLE HANDLING
  287: 
  288: Configuration values can be overridden via environment variables. Environment variables use double underscores (__) to denote nested configuration keys and single underscores remain as part of the key name under the prefix namespace.
  289: 
  290: For example:
  291: 
  292:   APP_DATABASE__USER becomes database.user (nested structure)
  293: 
  294:     $ export APP_DATABASE__USER="env_user"
  295: 
  296: will override any value set for `database.user` in the configuration files.
  297: 
  298:   APP_LOGLEVEL becomes APP.loglevel (flat under prefix namespace)
  299: 
  300:   APP_API__RATE_LIMIT becomes api.rate_limit (mixed usage)
  301: 
  302: This allows you to override both top-level and nested configuration values using environment variables.
  303: 
  304: Configuration values can be overridden via the command line (C<@ARGV>).
  305: For instance, if you have a key in the configuration such as C<database.user>,
  306: you can override it by adding C<"--APP_DATABASE__USER=other_user_name"> to the command line arguments.
  307: This will override any value set for C<database.user> in the configuration files.

  309: =head2 EXAMPLE CONFIGURATION FLOW
  310: 
  311: =over 4
  312: 
  313: =item 1. Data Argument
  314: 
  315: The data passed into the constructor via the C<data> argument is the starting point.
  316: Essentially,
  317: this contains the default values.
  318: 
  319: =item 2. Loading Files
  320: 
  321: The module then looks for configuration files in the specified directories.
  322: It loads the following files in order of preference:
  323: C<base.yaml>, C<local.yaml>, C<base.json>, C<local.json>, C<base.xml>,
  324: C<local.xml>, C<base.ini>, and C<local.ini>.
  325: 
  326: If C<config_file> or C<config_files> is set, those files are loaded last.
  327: 
  328: If no C<config_dirs> is given,
  329: C<Config::Abstraction> tries hard to find the files in various places.
  330: 
  331: The value of C<config_dirs> can be overridden at runtime by the environment variable CONFIG_DIR
  332: (note that is just one directory, hence it's CONFIG_DIR not CONFIG_DIRS).
  333: 
  334: =item 3. Merging and Resolving
  335: 
  336: The module merges the contents of these files, with more specific configurations
  337: (e.g., C<local.*>) overriding general ones (e.g., C<base.*>).
  338: 
  339: =item 4. Environment Overrides
  340: 
  341: After loading and merging the configuration files,
  342: the environment variables are
  343: checked and used to override any conflicting settings.
  344: 
  345: =item 5. Command Line
  346: 
  347: Next, the command line arguments are checked and used to override any conflicting settings.
  348: 
  349: =item 6. Accessing Values
  350: 
  351: Values in the configuration can be accessed using a dotted notation
  352: (e.g., C<'database.user'>), regardless of the file format used.
  353: 
  354: =back

  356: =head1 METHODS
  357: 
  358: =head2 new
  359: 
  360: Constructor for creating a new configuration object.
  361: 
  362: Options:
  363: 
  364: =over 4
  365: 
  366: =item * C<config_dirs>
  367: 
  368: An arrayref of directories to look for configuration files
  369: (default: C<$CONFIG_DIR>, C<$HOME/.conf>, C<$HOME/config>, C<$HOME/conf>, C<$DOCUMENT_ROOT/conf>, C<$DOCUMENT_ROOT/../conf>, C<conf>).
  370: 
  371: For centralised configuration management,
  372: entries beginning with C</../> are treated as remote specifications using the
  373: Newcastle Connection convention -- see L</Remote configuration directories (Newcastle Connection)>.
  374: 
  375: =item * C<config_file>
  376: 
  377: Points to a configuration file of any format.
  378: 
  379: =item * C<config_files>
  380: 
  381: An arrayref of files to look for in the configuration directories.
  382: Put the more important files later,
  383: since later files override earlier ones.
  384: 
  385: Considers the files C<default> and C<$script_name> before looking at C<config_file> and C<config_files>.
  386: 
  387: The running script itself is never read as configuration, even when one of the
  388: configuration directories is the directory it is in, and neither is any file
  389: that starts with C<#!>, since such a file is a program rather than
  390: configuration, and the Perl parser would run it.
  391: 
  392: =item * C<data>
  393: 
  394: A hash ref of default data to prime the configuration with.
  395: These are applied before loading
  396: other sources and can be overridden by later sources or by explicitly passing
  397: options directly to C<new>.
  398: 
  399:   $config = Config::Abstraction->new(
  400:       data => {
  401:           log_level => 'info',
  402:           retries => 3,
  403:       }
  404:   );
  405: 
  406: =item * C<defaults>
  407: 
  408: A hash reference that provides default values for the object's own attributes (such as C<config_dirs>, C<logger>, C<flatten>, etc.).
  409: If this option is supplied,
  410: the object is initialized using the keys in this hash as the base;
  411: any other options passed directly to C<new()> (aside from C<env_prefix>) are ignored.
  412: This allows you to pre-define a standard configuration profile for the object itself.
  413: Note that C<defaults> is distinct from the C<data> option - C<data> supplies the initial configuration values that will be merged with files, environment, and command line,
  414: while C<defaults> sets the object's internal parameters.
  415: The C<env_prefix> value,
  416: if provided as a top-level argument,
  417: still takes precedence over any C<env_prefix> that might exist inside the C<defaults> hash.
  418: 
  419: =item * C<encryption_key>
  420: 
  421: A 256-bit (32-byte) AES key used to transparently decrypt C<ENC[...]> values found in any
  422: configuration source after the full merge.  The key may be supplied as:
  423: 
  424: =over 4
  425: 
  426: =item 32 raw bytes
  427: 
  428: =item 64 lowercase or uppercase hex characters
  429: 
  430: =item 44 Base64 or Base64url characters (standard or URL-safe alphabet, with or without trailing C<=>)
  431: 
  432: =back
  433: 
  434: If no key is configured (and neither C<encryption_key_file> nor the corresponding
  435: environment variables are set), C<ENC[...]> tokens are left as literal strings.
  436: Decryption requires L<CryptX> (C<Crypt::AuthEnc::GCM>); if that module is absent a
  437: C<croak> is raised when an encrypted value is encountered.
  438: 
  439: See L</ENCRYPTED VALUES> for the full workflow.
  440: 
  441: =item * C<encryption_key_file>
  442: 
  443: Path to a file whose first line contains the encryption key in any of the formats accepted
  444: by C<encryption_key>.  Takes precedence over the C<ENCRYPTION_KEY_FILE> and
  445: C<{env_prefix}ENCRYPTION_KEY_FILE> environment variables, but is overridden by a key
  446: supplied directly via C<encryption_key>.
  447: 
  448: =item * C<env_prefix>
  449: 
  450: A prefix for environment variable keys and comment line options, e.g. C<MYAPP_DATABASE__USER>,
  451: (default: C<'APP_'>).
  452: 
  453: =item * C<environment>
  454: 
  455: The name of the active deployment environment (e.g. C<'dev'>, C<'staging'>, C<'prod'>).
  456: When set, config files named C<base.{env}.*> are loaded immediately after their C<base.*>
  457: equivalents, and C<local.{env}.*> files are loaded immediately after C<local.*> files,
  458: giving two additional override tiers at no cost to the base configuration.
  459: 
  460:   my $cfg = Config::Abstraction->new(
  461:       config_dirs => ['config'],
  462:       environment => 'prod',          # loads base.prod.yaml, local.prod.yaml, ...
  463:   );
  464: 
  465: If C<environment> is not given, the value is auto-detected in this order:
  466: 
  467: =over 4
  468: 
  469: =item 1. C<{env_prefix}ENV> environment variable (e.g. C<APP_ENV>)
  470: 
  471: =item 2. C<PLACK_ENV>
  472: 
  473: =item 3. C<NODE_ENV>
  474: 
  475: =back
  476: 
  477: When none of these is set, the environment-specific tiers are silently skipped.
  478: The environment name must contain only ASCII letters, digits, hyphens, and underscores
  479: (matched against C</^[A-Za-z0-9_\-]+$/>); any other value causes a C<croak>.
  480: 
  481: =item * C<file>
  482: 
  483: Synonym for C<config_file>
  484: 
  485: =item * C<flatten>
  486: 
  487: If true, returns a flat hash structure like C<{database.user}> (default: C<0>) instead of C<{database}{user}>.
  488: `

  490: 
  491: Level for logging.
  492: 
  493: =item * C<logger>
  494: 
  495: Used for warnings and traces.
  496: It can be an object that understands warn() and trace() messages,
  497: such as a L<Log::Log4perl> or L<Log::Any> object,
  498: a reference to code,
  499: a reference to an array,
  500: or a filename.

  503: 
  504: A synonym of C<config_dirs>.

  506: =item * C<sep_char>
  507: 
  508: The separator in keys.
  509: The default is a C<'.'>,
  510: as in dotted notation,
  511: such as C<'database.user'>.

  513: =item * C<schema>
  514: 
  515: A L<Params::Validate::Strict> compatible schema to validate the configuration file against.
  516: 
  517: =item * C<validators>
  518: 
  519: A hashref mapping dotted config keys to validation rules.  Each rule is applied to the
  520: corresponding value in the merged configuration immediately after all sources have been
  521: merged (or on first access when C<lazy> is set).  A validation failure croaks.
  522: 
  523: Each rule may be one of:
  524: 
  525: =over 4
  526: 
  527: =item A type name string
  528: 
  529:   validators => {
  530:       'database.port' => 'integer',
  531:       'app.name'      => 'string',
  532:       'price'         => 'number',
  533:       'enabled'       => 'boolean',
  534:       'tags'          => 'array',
  535:       'settings'      => 'hash',
  536:   }
  537: 
  538: Supported types: C<integer> (matches C</^-?\d+$/> -- no decimal point),
  539: C<number> or C<float> (C<Scalar::Util::looks_like_number>), C<boolean>
  540: (C<0>, C<1>, C<true>, C<false>, C<yes>, C<no> -- case-insensitive),
  541: C<string> (any defined non-reference scalar), C<array> (arrayref),
  542: C<hash> (hashref).
  543: 
  544: =item A compiled regular expression
  545: 
  546:   validators => {
  547:       'log.level' => qr/^(?:debug|info|warn|error|fatal)$/i,
  548:       'app.name'  => qr/^\w[\w\-]{1,63}$/,
  549:   }
  550: 
  551: The value must be defined and must match the regex.
  552: 
  553: =item A coderef
  554: 
  555:   validators => {
  556:       'database.port' => sub { my $v = shift; defined($v) && $v >= 1 && $v <= 65535 },
  557:   }
  558: 
  559: Called with the value as its only argument.  Must return a true value; otherwise the
  560: constructor croaks.
  561: 
  562: =item A hashref combining multiple constraints

  617: B<Differences from the default (eager) behaviour, and the debugging problems they cause:>
  618: 
  619: =over 4
  620: 
  621: =item 1. C<new()> always succeeds, even when no configuration exists.
  622: 
  623: In eager mode, C<new()> returns C<undef> immediately when no files are found and no
  624: C<data> was supplied, so a missing config is caught at the point of construction.
  625: In lazy mode, C<new()> always returns a blessed object.  If the configuration
  626: directories do not exist, the files are missing, or the prefix is wrong, you will
  627: not find out until the first accessor call - which may be deep inside your business
  628: logic, far from where the object was created.
  629: 
  630:   # Problem: the typo in config_dirs goes unnoticed until runtime
  631:   my $cfg = Config::Abstraction->new(
  632:       config_dirs => ['/etc/myapp/conifg'],   # typo - directory does not exist
  633:       lazy => 1,
  634:   );
  635:   # ... many lines later ...
  636:   my $host = $cfg->get('database.host');      # silently returns undef here
  637: 
  638: =item 2. Schema validation errors appear at the wrong place in the call stack.
  639: 
  640: When a C<schema> is supplied, eager mode validates the merged configuration inside
  641: C<new()> and throws immediately if the config does not match.  In lazy mode,
  642: validation is deferred to the first accessor call.  A schema violation therefore
  643: surfaces as an exception thrown by C<get()> or C<all()>, not by C<new()>, and the
  644: stack trace points to the accessor call rather than the construction site.  If the
  645: object is created in one module and accessed in another, the error message can be
  646: very misleading.
  647: 
  648: =item 3. Environment variables and C<@ARGV> are captured at access time, not construction time.
  649: 
  650: The module reads C<%ENV> and C<@ARGV> during C<_load_config()>.  In eager mode that
  651: happens in C<new()>, so the configuration reflects the environment at the moment the
  652: object is built.  In lazy mode, any change to C<%ENV> or C<@ARGV> between C<new()>
  653: and the first accessor call is silently picked up.  This makes test isolation harder:
  654: setting an environment variable I<after> constructing a lazy object will affect the
  655: values it returns, which is not the case with an eager object.
  656: 
  657: =item 4. File system state may change between construction and first use.
  658: 
  659: Because lazy mode defers all I/O, the files that are read are those that exist at the
  660: moment of first access, not at the moment C<new()> is called.  If a config file is
  661: written, deleted, or replaced between those two points (for example, by another
  662: process or test fixture), the object will silently use the new state.  An eager object
  663: is immune to this race.
  664: 
  665: =item 5. Errors from format parsers appear at accessor call sites.
  666: 
  667: Malformed YAML, JSON, XML, or INI files emit a C<carp> warning and are skipped during
  668: loading.  In eager mode those warnings appear near the program's startup.  In lazy mode
  669: they appear during the first accessor call, which can make it look as though a routine
  670: in your business logic is generating configuration warnings.
  671: 
  672: =back
  673: 
  674: B<When to use lazy loading:> It is most useful when a C<Config::Abstraction> object is
  675: created speculatively at module-load time and may never be accessed (for example, in a
  676: web framework where the config object is built for every request but some request paths
  677: never read it).  Avoid it when startup correctness is important, when you rely on
  678: C<new()> returning C<undef> to detect missing configuration, or when you use schema
  679: validation and need errors to point at the construction site.

 2336: =head2 Remote configuration directories (Newcastle Connection)
 2337: 
 2338: Any entry in C<config_dirs> whose path begins with C</../> is treated as a
 2339: remote specification rather than a local directory:
 2340: 
 2341:   /../hostname/path/to/dir
 2342: 
 2343: The hostname and directory are extracted, and the same standard files searched
 2344: locally (C<base.yaml>, C<local.yaml>, C<base.json>, etc.) are fetched from
 2345: the remote machine via L<File::Slurp::Remote> over SSH.
 2346: 
 2347: When the hostname resolves to the local machine -- C<localhost>, C<127.0.0.1>,
 2348: C<::1>, or the value returned by C<Sys::Hostname::hostname()> (checked as
 2349: both fully-qualified and short form, case-insensitively) -- the C</../host/>
 2350: wrapper is silently unwrapped and the enclosed path is processed through the
 2351: normal local file pipeline instead.  No SSH connection is made.  This means a
 2352: configuration written for a shared remote host degrades gracefully when run on
 2353: that host itself:
 2354: 
 2355:   # On any other machine: fetches /etc/myapp over SSH
 2356:   # On cfg-server itself: reads /etc/myapp from disk directly
 2357:   config_dirs => ['/../cfg-server/etc/myapp']
 2358: 
 2359: Remote directories participate in the normal merge pipeline and can be freely
 2360: mixed with local ones:
 2361: 
 2362:   my $cfg = Config::Abstraction->new(
 2363:       config_dirs => [
 2364:           '/etc/myapp',                        # local
 2365:           '/../deploy@cfg-server/etc/myapp',   # remote via SSH (local on cfg-server)
 2366:       ],
 2367:   );
 2368: 
 2369: SSH authentication is handled by the system SSH client.
 2370: No extra constructor options are required; use your SSH agent or
 2371: C<~/.ssh/config> for host-specific settings.
 2372: 
 2373: L<File::Slurp::Remote> must be installed for remote directories to work.
 2374: If it is absent the directory is silently skipped and a warning is emitted.
 2375: 
 2376: =head3 Why C</../> (the Newcastle Connection convention)
 2377: 
 2378: Several syntaxes were considered for marking a C<config_dirs> entry as remote.
 2379: Each alternative was rejected for a concrete reason:
 2380: 
 2381: =over 4
 2382: 
 2383: =item C<hostname/path> -- ambiguous
 2384: 
 2385: Indistinguishable from a relative local directory named C<hostname>.
 2386: The module cannot tell at parse time whether C<myserver/etc> is a two-level
 2387: local path or a remote specification.
 2388: 
 2389: =item C<hostname:/path> -- collides with Windows drive letters
 2390: 
 2391: The C<X:\> drive-letter convention on Windows uses exactly the same
 2392: C<letter:> prefix.  A single-letter hostname would be misidentified as a
 2393: drive, and path-normalisation code on Windows would mangle it.
 2394: 
 2395: =item C<file://hostname/path> -- wrong semantics
 2396: 
 2397: RFC 8089 defines C<file://> as a reference to a B<local> file.
 2398: C<file:///etc/passwd> (three slashes, empty host) is the canonical local form;
 2399: C<file://hostname/path> is reserved for the host component but is explicitly
 2400: discouraged for general use and is not understood by most tooling as meaning
 2401: SSH.
 2402: 
 2403: =item C<ssh://hostname/path> -- requires URI parsing
 2404: 
 2405: Introduces a dependency on URI parsing (or a bespoke prefix check) and
 2406: implies a specific transport.  C<File::Slurp::Remote> already abstracts
 2407: the transport; encoding C<ssh://> in the path would be misleading if a future
 2408: version of that module supports other transports such as C<rsync://>.
 2409: 
 2410: =item C</../hostname/path> -- the Newcastle Connection
 2411: 
 2412: The Newcastle Connection (Brownbridge, Dion, Elsworth, 1982) is a distributed
 2413: Unix convention in which the token C</../> at the start of a pathname means
 2414: "leave the local namespace and enter the named remote host".
 2415: It works because C</../> B<cannot exist> as a real filesystem path:
 2416: C<..> from the root directory resolves back to the root on every POSIX system,
 2417: so C</../> always denotes the root itself, never a child of the root.
 2418: No pathname-normalisation step, C<chdir>, or filesystem traversal will ever
 2419: produce a path that legitimately begins with C</../>, which means the prefix
 2420: is a permanent, collision-free sentinel that requires only a regex to detect.
 2421: 
 2422: =back
 2423: 
 2424: The Newcastle Connection prefix is therefore the only choice that is:
 2425: 
 2426: =over 4
 2427: 
 2428: =item * unambiguous on all platforms (POSIX and Windows)
 2429: 
 2430: =item * impossible to produce accidentally from a real local path
 2431: 
 2432: =item * detectable with a single C<m{^\Q/../\E}> regex, no URI parser needed
 2433: 
 2434: =item * transport-neutral (the hostname is passed to whatever remote driver is installed)
 2435: 
 2436: =back

 2777: B<Never commit the key to version control.>
 2778: 
 2779: =head2 Token format
 2780: 
 2781:   ENC[AES256GCM,<base64url(nonce || ciphertext || tag)>]
 2782: 
 2783: =over 4
 2784: 
 2785: =item * C<AES256GCM> -- AES-256 in GCM mode (authenticated encryption)
 2786: 
 2787: =item * Nonce -- 12 random bytes (fresh per encryption, never reused)
 2788: 
 2789: =item * GCM authentication tag -- 16 bytes; any modification causes decryption to croak
 2790: 
 2791: =item * Base64url encoding -- URL-safe alphabet, no padding ambiguity
 2792: 
 2793: =back
 2794: 
 2795: =head2 Behaviour when no key is configured
 2796: 
 2797: If no key is found, C<ENC[...]> tokens are left as literal strings.  This means
 2798: the feature is purely opt-in: existing deployments without a key configured are
 2799: unaffected.
 2800:

 2802: 
 2803: L<CryptX> (C<Crypt::AuthEnc::GCM>, C<Crypt::PRNG>) must be installed:
 2804: 
 2805:   cpanm CryptX

 2807: =head1 COMMON PITFALLS
 2808: 
 2809: =head2 1. new() returns undef when no configuration is found
 2810: 
 2811: C<new()> returns C<undef>, not a blessed object, when no configuration data is
 2812: found and no C<data> argument was supplied.  Every caller must check the return value.
 2813: 
 2814:   my $cfg = Config::Abstraction->new(config_dirs => ['/etc/myapp']);
 2815:   die "No configuration found" unless defined $cfg;
 2816:   my $host = $cfg->get('database.host');   # safe
 2817: 
 2818: Forgetting the check leads to a cryptic "Can't call method on undef" error later,
 2819: with a stack trace that points to C<get()> rather than to the missing config file.
 2820: 
 2821: =head2 2. merge_defaults() requires a named argument, not a bare hashref
 2822: 
 2823:   # WRONG -- Params::Get fast-path returns the whole config unchanged
 2824:   my $merged = $cfg->merge_defaults(\%my_defaults);
 2825: 
 2826:   # RIGHT
 2827:   my $merged = $cfg->merge_defaults(defaults => \%my_defaults);
 2828: 
 2829: With the first form, C<Params::Get> treats the single hashref as the entire
 2830: parameter bag and returns the full config without merging anything.
 2831: 
 2832: =head2 3. Shallow merge in merge_defaults() silently drops nested keys from defaults
 2833: 
 2834: Without C<merge =E<gt> 1>, C<merge_defaults()> uses a plain Perl hash merge
 2835: (C<{ %defaults, %config }>) at the top level.  If the config contains a nested hash
 2836: for a key, it entirely replaces the corresponding nested hash in your defaults - any
 2837: keys that exist only in the defaults' nested hash are silently discarded.
 2838: 
 2839:   my $cfg = Config::Abstraction->new(
 2840:       data        => { db => { host => 'localhost', port => 5432 } },
 2841:       config_dirs => [],
 2842:   );
 2843: 
 2844:   my $merged = $cfg->merge_defaults(defaults => { db => { user => 'guest' } });
 2845:   # $merged->{db}{user} is UNDEF -- the whole 'db' hash was replaced by the config's version
 2846: 
 2847:   # To combine nested keys from both sides, pass merge => 1:
 2848:   my $merged = $cfg->merge_defaults(defaults => { db => { user => 'guest' } }, merge => 1);
 2849:   # $merged->{db}{user} is 'guest', $merged->{db}{host} is 'localhost'
 2850: 
 2851: =head2 4. undef from a higher-priority source permanently wins
 2852: 
 2853: C<Hash::Merge> LEFT_PRECEDENT means that an explicit C<undef> (YAML C<~>) in a
 2854: higher-priority source overrides a real value in a lower-priority source, including
 2855: when the lower-priority value is defined.
 2856: 
 2857:   # base.yaml:  timeout: 30
 2858:   # local.yaml: timeout: ~
 2859: 
 2860:   my $t = $cfg->get('timeout');   # undef -- local.yaml's null wins over base.yaml
 2861: 
 2862: This is intentional: it lets a local config deliberately unset a value.  If you
 2863: want to detect whether a key was explicitly nulled versus simply absent, use
 2864: C<explain_sources()> and inspect the C<sources> list.
 2865: 
 2866: =head2 5. Double underscore vs. single underscore in environment variable names
 2867: 
 2868: Single underscores are part of the key name; double underscores create a nesting level.
 2869: 
 2870:   APP_LOG_LEVEL=debug       => key 'log_level'   (single underscore, flat key)
 2871:   APP_DATABASE__HOST=db     => key 'database.host' (double underscore, nested)
 2872:   APP_API__RATE_LIMIT=100   => key 'api.rate_limit' (double underscore + single)
 2873: 
 2874: A common mistake is using single underscores expecting nested keys:
 2875: 
 2876:   APP_DATABASE_HOST=db   # produces key 'database_host', NOT 'database.host'
 2877: 
 2878: =head2 6. Using AUTOLOAD requires sep_char set to '_'
 2879: 
 2880: AUTOLOAD translates method names to config keys using C<sep_char>.  The default
 2881: C<sep_char> is C<'.'>, but method names cannot contain dots.  Set C<sep_char =E<gt> '_'>
 2882: to use AUTOLOAD, and be aware that this makes single underscores into hierarchy separators.
 2883: 
 2884:   my $cfg = Config::Abstraction->new(
 2885:       data    => { database => { host => 'localhost' } },
 2886:       sep_char => '_',
 2887:       config_dirs => [],
 2888:   );
 2889:   my $host = $cfg->database_host();   # works
 2890:   my $bad  = $cfg->no_such_key();    # dies: No such config key 'no_such_key'
 2891: 
 2892: =head2 7. Absolute config_file paths require an empty or omitted config_dirs
 2893: 
 2894: On Unix, C<File::Spec-E<gt>catfile('/etc', '/absolute/path.yaml')> concatenates the
 2895: two strings instead of letting the absolute path take over, producing a wrong path.
 2896: When C<config_file> is an absolute path, either omit C<config_dirs> entirely
 2897: (the constructor sets it to C<['']> automatically) or pass C<config_dirs =E<gt> ['']>
 2898: explicitly.
 2899: 
 2900:   # WRONG on Unix -- produces '/etc/etc/myapp/app.yaml'
 2901:   Config::Abstraction->new(
 2902:       config_file => '/etc/myapp/app.yaml',
 2903:       config_dirs => ['/etc'],
 2904:   );
 2905: 
 2906:   # RIGHT
 2907:   Config::Abstraction->new( config_file => '/etc/myapp/app.yaml' );
 2908: 
 2909: =head2 8. Tests must isolate from the developer's real config files
 2910: 
 2911: A call to C<new()> without C<config_dirs> will scan C</etc>, C<~/.conf>,
 2912: C<~/.config>, and other default locations and load any C<base.yaml> or
 2913: C<local.yaml> it finds there.  In a test suite this injects real host
 2914: configuration into your test object, causing non-deterministic failures.
 2915: 
 2916: Always pass C<config_dirs =E<gt> []> in tests that use only in-memory C<data>:
 2917: 
 2918:   my $cfg = Config::Abstraction->new(
 2919:       data        => { key => 'value' },
 2920:       config_dirs => [],              # do not scan the filesystem
 2921:   );
 2922: 
 2923: =head2 9. lazy => 1 defers errors until the first accessor call
 2924: 
 2925: With C<lazy =E<gt> 1>, C<new()> always returns a blessed object - it cannot return
 2926: C<undef> for a missing config, and any schema validation errors surface at the first
 2927: C<get()> or C<all()> call rather than at construction time.  See the C<lazy>
 2928: option documentation in L</new> for the full list of debugging implications.

 3013: =head1 LIMITATIONS
 3014: 
 3015: =over 4
 3016: 
 3017: =item * B<No separator escaping>
 3018: 
 3019: The separator character (C<sep_char>, default C<.>) cannot be embedded in a key name.
 3020: A key that literally contains a dot cannot be accessed via C<get()> when C<sep_char> is
 3021: the default.  Workaround: set C<sep_char> to a character not present in any key.
 3022: 
 3023: =item * B<Data::Reuse fixation disabled>
 3024: 
 3025: The C<Data::Reuse::fixate()> call inside C<get()> is currently a no-op because the
 3026: behaviour of C<Crypt::Storable::dclone> differs between Linux and macOS in a way
 3027: that cannot be resolved portably (RT#100461).  Hash values returned by C<get()> are
 3028: mutable references, not read-only copies.
 3029: 
 3030: =item * B<Windows environment variable case sensitivity>
 3031: 
 3032: On Windows, environment variable names are case-insensitive at the OS level but
 3033: case-sensitive in C<%ENV> as seen by Perl.  Overriding config keys via environment
 3034: variables may silently fail if the case does not match exactly.
 3035: 
 3036: =item * B<AUTOLOAD requires sep_char set to '_'>
 3037: 
 3038: AUTOLOAD method dispatch converts underscores to key separators.  If C<sep_char> is
 3039: the default C<'.'>, AUTOLOAD cannot reach nested keys because Perl method names cannot
 3040: contain dots.
 3041: 
 3042: =item * B<Remote directory TOML support requires File::Slurp::Remote>
 3043: 
 3044: TOML files in Newcastle Connection remote directories are only fetched when the
 3045: C<File::Slurp::Remote> module is installed.  Without it, remote directories are
 3046: skipped entirely regardless of file format.
 3047: 
 3048: =back
