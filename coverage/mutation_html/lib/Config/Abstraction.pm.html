   46: =head1 SYNOPSIS
   47: 
   48: =head2 Pattern 1: Environment overrides file overrides in-code defaults
   49: 
   50: The most common pattern for twelve-factor-style apps.
   51: The C<data> argument supplies defaults, a YAML file supplies site configuration,
   52: and environment variables allow per-deployment overrides without touching any file.
   53: 
   54:   # config/base.yaml
   55:   #   database:
   56:   #     host: db.example.com
   57:   #     port: 5432
   58:   #     user: app
   59: 
   60:   use Config::Abstraction;
   61: 
   62:   my $config = Config::Abstraction->new(
   63:       data        => { database => { host => 'localhost', port => 5432 } },
   64:       config_dirs => ['config'],
   65:       env_prefix  => 'APP_',
   66:   );
   67: 
   68:   # In production, set APP_DATABASE__HOST=db.prod.example.com in the environment.
   69:   # That silently overrides the file value, which in turn overrides the default.
   70:   my $host = $config->get('database.host');
   71:   my $port = $config->get('database.port');
   72: 
   73: =head2 Pattern 2: Command-line arguments override everything
   74: 
   75: Useful for CLI tools where operator flags must win over every other source.
   76: 
   77:   # Run as: myscript.pl --APP_LOGLEVEL=debug --APP_DATABASE__HOST=localhost
   78: 
   79:   use Config::Abstraction;
   80: 
   81:   my $config = Config::Abstraction->new(
   82:       config_dirs => ['config'],
   83:       env_prefix  => 'APP_',
   84:   );
   85: 
   86:   # @ARGV is consumed and stripped during new(); the resulting config already
   87:   # has cli-layer values at the highest precedence.
   88:   my $loglevel = $config->get('loglevel');       # 'debug'  (from --APP_LOGLEVEL)
   89:   my $db_host  = $config->get('database.host');  # 'localhost' (from --APP_DATABASE__HOST)
   90: 
   91: =head2 Pattern 3: Multi-file layering (base + local override)
   92: 
   93: Separates shared defaults from machine-specific tweaks.
   94: Every developer has a C<base.yaml>; only the production server has C<local.yaml>.
   95: 
   96:   # config/base.yaml   -- checked into version control
   97:   #   database:
   98:   #     host: localhost
   99:   #     user: dev
  100:   #
  101:   # config/local.yaml  -- NOT checked in; production only
  102:   #   database:
  103:   #     host: db.prod.example.com
  104:   #     user: produser
  105:   #     password: s3cr3t
  106: 
  107:   use Config::Abstraction;
  108: 
  109:   my $config = Config::Abstraction->new(
  110:       config_dirs => ['config'],   # loads base.yaml then local.yaml
  111:       env_prefix  => 'APP_',
  112:   );
  113: 
  114:   # On a dev machine (no local.yaml): host='localhost', user='dev'
  115:   # On the prod server:               host='db.prod.example.com', user='produser'
  116:   my $db = $config->get('database.host');
  117:   my $user = $config->get('database.user');

  119: =head1 DESCRIPTION
  120: 
  121: C<Config::Abstraction> is a flexible configuration management layer that sits above C<Config::*> modules.
  122: It provides a simple way to layer multiple configuration sources with predictable merge order.
  123: It lets you define sources such as:
  124: 
  125: =over 4
  126: 
  127: =item * Perl hashes (in-memory defaults or dynamic values)
  128: 
  129: =item * Environment variables (with optional prefixes)
  130: 
  131: =item * Configuration files (YAML, JSON, INI, or plain key=value)
  132: 
  133: =item * Command-line arguments
  134: 
  135: =back
  136: 
  137: Sources are applied in the order they are provided. Later sources override
  138: earlier ones unless a key is explicitly set to C<undef> in the later source.
  139: 
  140: In addition to using drivers to load configuration data from multiple file
  141: formats (YAML, JSON, XML, and INI),
  142: it also allows levels of configuration, each of which overrides the lower levels.
  143: So, it also integrates environment variable
  144: overrides and command line arguments for runtime configuration adjustments.
  145: This module is designed to help developers manage layered configurations that can be loaded from files and overridden at run-time for debugging,
  146: offering a modern, robust and dynamic approach
  147: to configuration management.
  148: 
  149: =head2 Merge Precedence
  150: 
  151: Sources are applied in the order shown below.  Each row wins over every row
  152: above it.  When the same key appears in multiple sources, the highest-priority
  153: source always determines the final value - including when that value is C<undef>.
  154: 
  155:   Priority   Source                         Set with
  156:   --------   ------                         --------
  157:      1 (lo)  data constructor argument      data => { key => 'default' }
  158:      2        base.*  config files          config/base.yaml, base.json, ...
  159:      3        base.{env}.* config files     config/base.prod.yaml, ...
  160:      4        local.* config files          config/local.yaml, local.json, ...
  161:      5        local.{env}.* config files    config/local.prod.yaml, ...
  162:      6        default / script-name files   config/default.yaml, myapp.yaml, ...
  163:      7        config_file / config_files    config_file => '/etc/myapp.yaml'
  164:      8        Environment variables         APP_DATABASE__HOST=db.prod.example.com
  165:      9 (hi)  CLI arguments (@ARGV)          --APP_DATABASE__HOST=db.prod.example.com
  166: 
  167: The active environment is set by the C<environment> constructor option, or
  168: auto-detected from C<{env_prefix}ENV> (e.g. C<APP_ENV>), C<PLACK_ENV>, or
  169: C<NODE_ENV>.  When no environment is configured, rows 3 and 5 are skipped.
  170: 
  171: Within the file tier (rows 2-7), later files override earlier files using
  172: C<Hash::Merge> LEFT_PRECEDENT: every key in the later file wins over the same
  173: key in an earlier file, even when the later value is C<undef> (YAML C<~>).
  174: Nested hashes are merged recursively, so a C<local.yaml> that only sets
  175: C<database.host> will not erase C<database.port> from C<base.yaml>.
  176: 
  177:   Example - what wins for the key C<database.host> when APP_ENV=prod:
  178: 
  179:   data              =>  'localhost'              (overridden by base.yaml)
  180:   base.yaml         =>  'db.example.com'         (overridden by base.prod.yaml)
  181:   base.prod.yaml    =>  'db.prod.example.com'    (overridden by local.yaml)
  182:   local.yaml        =>  'db.local.example.com'   (overridden by local.prod.yaml)
  183:   local.prod.yaml   =>  'db.prod-local.example.com'  (overridden by $APP_DATABASE__HOST)
  184:   $APP_DATABASE__HOST  =>  'db.override.example.com'    <-- this wins
  185: 
  186: =head2 KEY FEATURES
  187: 
  188: =over 4
  189: 
  190: =item * Multi-Format Support
  191: 
  192: Supports configuration files in YAML, JSON, XML, and INI formats.
  193: Automatically merges configuration data from these different formats,
  194: allowing hierarchical configuration management.
  195: 
  196: =item * Environment Variable Overrides
  197: 
  198: Allows environment variables to override values in the configuration files.
  199: By setting environment variables with a specific prefix (default: C<APP_>),
  200: values in the configuration files can be dynamically adjusted without modifying
  201: the file contents.
  202: 
  203: =item * Flattened Configuration Option
  204: 
  205: Optionally supports flattening the configuration structure. This converts deeply
  206: nested configuration keys into a flat key-value format (e.g., C<database.user>
  207: instead of C<database-E<gt>{user}>). This makes accessing values easier for
  208: applications that prefer flat structures or need compatibility with flat
  209: key-value stores.
  210: 
  211: =item * Layered Configuration
  212: 
  213: Supports merging multiple layers of configuration files. For example, you can
  214: have a C<base.yaml> configuration file that provides default values, and a
  215: C<local.yaml> (or C<local.json>, C<local.xml>, etc.) file that overrides
  216: specific values. This allows for environment-specific configurations while
  217: keeping defaults intact.
  218: 
  219: =item * Merge Strategy
  220: 
  221: The module merges the configuration data intelligently, allowing values in more
  222: specific files (like C<local.yaml>, C<local.json>, C<local.xml>, C<local.ini>)
  223: to override values in base files. This enables a flexible and layered configuration
  224: system where you can set defaults and override them for specific environments.
  225: 
  226: =item * Error Handling
  227: 
  228: Includes error handling for loading configuration files.
  229: If any file fails to
  230: load (e.g., due to syntax issues), the module will throw descriptive error
  231: messages to help with debugging.
  232: 
  233: =item * Centralized Configuration Management
  234: 
  235: Supports remote configuration management files,
  236: so that configuration on remote machines can be centrally managed.
  237: 
  238: =back

  240: =head2 SUPPORTED FILE FORMATS
  241: 
  242: =over 4
  243: 
  244: =item * YAML (C<*.yaml>, C<*.yml>)
  245: 
  246: Loaded with L<YAML::XS>.
  247: 
  248: =item * JSON (C<*.json>)
  249: 
  250: Loaded with L<JSON::MaybeXS>.
  251: 
  252: =item * XML (C<*.xml>)
  253: 
  254: Loaded with L<XML::Simple> (preferred) or L<XML::PP> (fallback).
  255: 
  256: =item * INI (C<*.ini>)
  257: 
  258: Loaded with L<Config::IniFiles>.
  259: 
  260: =item * TOML (C<*.toml>)
  261: 
  262: Loaded with L<TOML::Tiny>, which implements TOML 1.0.  TOML is a good choice
  263: for human-editable configuration because its syntax is unambiguous: all values
  264: are typed, strings must be quoted, and nesting uses C<[section]> headers or
  265: dotted keys rather than indentation.
  266: 
  267:   # Example: config/base.toml
  268:   [database]
  269:   host   = "db.example.com"
  270:   port   = 5432
  271:   user   = "app"
  272: 
  273:   [cache]
  274:   ttl    = 300
  275:   debug  = false
  276: 
  277: C<base.toml> and C<local.toml> are discovered automatically in C<config_dirs>;
  278: C<local.toml> has higher precedence than C<base.toml>, following the same
  279: layering rules as all other formats.  TOML is also tried as a fallback parser
  280: in the all-parsers chain used for extensionless C<config_file> entries.
  281: 
  282: If C<TOML::Tiny> is not installed, TOML files are silently skipped with a
  283: C<carp> warning.
  284: 
  285: =item * Apache-style (C<*.conf>)
  286: 
  287: Loaded with L<Config::General>, which is optional.  C<base.conf>,
  288: C<local.conf> and their environment-specific forms are discovered like the
  289: other formats, and Config::General is the last parser tried for an
  290: extensionless C<config_file>.  If it is not installed, C<.conf> files are
  291: skipped.
  292: 
  293:   name      = myapp
  294:   log       debug
  295:   log       trace            # repeated keys become an array
  296:   <database>
  297:       host  = db.example.com
  298:       port  = 5432
  299:   </database>
  300:   <host www.example.com>     # a named block nests one level further
  301:       root  /var/www
  302:   </host>
  303: 
  304: Config::General's own C<E<lt>E<lt>include ...E<gt>E<gt>> directive is B<not>
  305: honoured, and a file that uses it is skipped with a warning, because it reads
  306: any file the process can read.  Use the C<include> key described under
  307: L</INCLUDING FILES> instead.  Config::General's variable interpolation is
  308: switched off in favour of L</VARIABLE INTERPOLATION>.
  309: 
  310: Apache-style content has C<E<lt>blockE<gt>...E<lt>/blockE<gt>> tags that look
  311: like XML.  When an extensionless C<config_file> that does not begin with an
  312: C<E<lt>?xmlE<gt>> declaration fails to parse as XML, it is given one attempt
  313: as Apache-style configuration before the XML error is reported.
  314: 
  315: =back
  316: 
  317: =head2 INCLUDING FILES
  318: 
  319: With C<allow_includes =E<gt> 1>, a configuration file may name other files
  320: in a top-level C<include> key (a path, a glob, or an arrayref of them):
  321: 
  322:   # base.yaml
  323:   include:
  324:     - defaults/common.yaml
  325:     - conf.d/*.json
  326:   name: myapp
  327: 
  328: Any format may include any other.  The included files are merged I<under> the
  329: file that includes them, so the including file wins over its includes and,
  330: of several includes, the later one wins over the earlier.  Globs are expanded
  331: in sorted order.  A relative path is taken relative to the including file, not
  332: to the current directory.  Included files appear in C<config_path> and, with
  333: their own entries, in C<explain_sources()>.
  334: 
  335: Because an include is a way to make the module read a file, it is confined:
  336: an included file must be within the directory of the file that began the
  337: chain (any depth below it), or within a directory listed in C<include_dirs>.
  338: Symbolic links are resolved before the check.  A file outside those
  339: directories, a circular include, or a chain deeper than C<include_max_depth>
  340: croaks.  An include that does not exist is skipped with a warning.
  341: 
  342: The key name can be changed with C<include_key>.  A glob that matches no
  343: file is silently ignored, whereas an explicit path that does not exist warns.
  344: A file that starts with C<#!> is a program and is never read as an include, and
  345: the running script is never included.  An included file with an unrecognised
  346: extension is detected by its content (JSON, YAML, TOML, then Apache-style).
  347: 
  348: Includes are not followed in files fetched from remote directories
  349: (Newcastle Connection).
  350: 
  351: =head2 VARIABLE INTERPOLATION
  352: 
  353: With C<interpolate =E<gt> 1>, string values may refer to other values:
  354: 
  355:   database:
  356:     host: db.example.com
  357:     port: 5432
  358:   dsn:  "dbi:Pg:host=${database.host};port=${database.port}"
  359:   home: "${env:HOME}/app"
  360:   lang: "${env:LANG:-C}"
  361:   cost: "$$5"                    # a literal $5
  362: 
  363: =over 4
  364: 
  365: =item * C<${a.b}> -- the value of the configuration key C<a.b> (always C<.>-separated, whatever C<sep_char> is)
  366: 
  367: =item * C<${env:NAME}> -- the environment variable C<NAME>
  368: 
  369: =item * C<${...:-default}> -- C<default> when the key or variable is missing
  370: 
  371: =item * C<$$> -- a literal C<$>
  372: 
  373: =back
  374: 
  375: Expansion happens after every source (files, includes, environment, command
  376: line) has been merged, so a reference sees the final value of its key, and
  377: references may chain.  A bare C<$name> is not special.  Values that are
  378: C<ENC[...]> tokens are left alone, so a secret can be referred to only after
  379: decryption by not referring to it.  An undefined key or variable, a circular
  380: reference, or a reference to a hash or array croaks, unless
  381: C<interpolate_strict> is false.  The caller's C<data> hashref is never
  382: modified.
  383: 
  384: Turn this on only for configuration you trust: a value taken from an
  385: environment variable or command-line argument that contains
  386: C<${env:NAME}> will be expanded too.
  387: 
  388: =head2 ENVIRONMENT VARIABLE HANDLING
  389: 
  390: Configuration values can be overridden via environment variables. Environment variables use double underscores (__) to denote nested configuration keys and single underscores remain as part of the key name under the prefix namespace.
  391: 
  392: For example:
  393: 
  394:   APP_DATABASE__USER becomes database.user (nested structure)
  395: 
  396:     $ export APP_DATABASE__USER="env_user"
  397: 
  398: will override any value set for `database.user` in the configuration files.
  399: 
  400:   APP_LOGLEVEL becomes APP.loglevel (flat under prefix namespace)
  401: 
  402:   APP_API__RATE_LIMIT becomes api.rate_limit (mixed usage)
  403: 
  404: This allows you to override both top-level and nested configuration values using environment variables.
  405: 
  406: Configuration values can be overridden via the command line (C<@ARGV>).
  407: For instance, if you have a key in the configuration such as C<database.user>,
  408: you can override it by adding C<"--APP_DATABASE__USER=other_user_name"> to the command line arguments.
  409: This will override any value set for C<database.user> in the configuration files.
  410: 
  411: =head2 EXAMPLE CONFIGURATION FLOW
  412: 
  413: =over 4
  414: 
  415: =item 1. Data Argument
  416: 
  417: The data passed into the constructor via the C<data> argument is the starting point.
  418: Essentially,
  419: this contains the default values.
  420: 
  421: =item 2. Loading Files
  422: 
  423: The module then looks for configuration files in the specified directories.
  424: It loads the following files in order of preference:
  425: C<base.yaml>, C<local.yaml>, C<base.json>, C<local.json>, C<base.xml>,
  426: C<local.xml>, C<base.ini>, and C<local.ini>.
  427: 
  428: If C<config_file> or C<config_files> is set, those files are loaded last.
  429: 
  430: If no C<config_dirs> is given,
  431: C<Config::Abstraction> tries hard to find the files in various places.
  432: 
  433: The value of C<config_dirs> can be overridden at runtime by the environment variable CONFIG_DIR
  434: (note that is just one directory, hence it's CONFIG_DIR not CONFIG_DIRS).
  435: 
  436: =item 3. Merging and Resolving
  437: 
  438: The module merges the contents of these files, with more specific configurations
  439: (e.g., C<local.*>) overriding general ones (e.g., C<base.*>).
  440: 
  441: =item 4. Environment Overrides
  442: 
  443: After loading and merging the configuration files,
  444: the environment variables are
  445: checked and used to override any conflicting settings.
  446: 
  447: =item 5. Command Line
  448: 
  449: Next, the command line arguments are checked and used to override any conflicting settings.
  450: 
  451: =item 6. Accessing Values
  452: 
  453: Values in the configuration can be accessed using a dotted notation
  454: (e.g., C<'database.user'>), regardless of the file format used.
  455: 
  456: =back

  458: =head1 METHODS
  459: 
  460: =head2 new
  461: 
  462: Constructor for creating a new configuration object.
  463: 
  464: Options:
  465: 
  466: =over 4
  467: 
  468: =item * C<config_dirs>
  469: 
  470: An arrayref of directories to look for configuration files
  471: (default: C<$CONFIG_DIR>, C<$HOME/.conf>, C<$HOME/config>, C<$HOME/conf>, C<$DOCUMENT_ROOT/conf>, C<$DOCUMENT_ROOT/../conf>, C<conf>).
  472: 
  473: For centralised configuration management,
  474: entries beginning with C</../> are treated as remote specifications using the
  475: Newcastle Connection convention -- see L</Remote configuration directories (Newcastle Connection)>.
  476: 
  477: =item * C<config_file>
  478: 
  479: Points to a configuration file of any format.
  480: 
  481: =item * C<config_files>
  482: 
  483: An arrayref of files to look for in the configuration directories.
  484: Put the more important files later,
  485: since later files override earlier ones.
  486: 
  487: Considers the files C<default> and C<$script_name> before looking at C<config_file> and C<config_files>.
  488: 
  489: The running script itself is never read as configuration, even when one of the
  490: configuration directories is the directory it is in, and neither is any file
  491: that starts with C<#!>, since such a file is a program rather than
  492: configuration, and the Perl parser would run it.
  493: 
  494: =item * C<data>
  495: 
  496: A hash ref of default data to prime the configuration with.
  497: These are applied before loading
  498: other sources and can be overridden by later sources or by explicitly passing
  499: options directly to C<new>.
  500: 
  501:   $config = Config::Abstraction->new(
  502:       data => {
  503:           log_level => 'info',
  504:           retries => 3,
  505:       }
  506:   );
  507: 
  508: =item * C<defaults>
  509: 
  510: A hash reference that provides default values for the object's own attributes (such as C<config_dirs>, C<logger>, C<flatten>, etc.).
  511: If this option is supplied,
  512: the object is initialized using the keys in this hash as the base;
  513: any other options passed directly to C<new()> (aside from C<env_prefix>) are ignored.
  514: This allows you to pre-define a standard configuration profile for the object itself.
  515: Note that C<defaults> is distinct from the C<data> option - C<data> supplies the initial configuration values that will be merged with files, environment, and command line,
  516: while C<defaults> sets the object's internal parameters.
  517: The C<env_prefix> value,
  518: if provided as a top-level argument,
  519: still takes precedence over any C<env_prefix> that might exist inside the C<defaults> hash.
  520: 
  521: =item * C<encryption_key>
  522: 
  523: A 256-bit (32-byte) AES key used to transparently decrypt C<ENC[...]> values found in any
  524: configuration source after the full merge.  The key may be supplied as:
  525: 
  526: =over 4
  527: 
  528: =item 32 raw bytes
  529: 
  530: =item 64 lowercase or uppercase hex characters
  531: 
  532: =item 44 Base64 or Base64url characters (standard or URL-safe alphabet, with or without trailing C<=>)
  533: 
  534: =back
  535: 
  536: If no key is configured (and neither C<encryption_key_file> nor the corresponding
  537: environment variables are set), C<ENC[...]> tokens are left as literal strings.
  538: Decryption requires L<CryptX> (C<Crypt::AuthEnc::GCM>); if that module is absent a
  539: C<croak> is raised when an encrypted value is encountered.
  540: 
  541: See L</ENCRYPTED VALUES> for the full workflow.
  542: 
  543: =item * C<encryption_key_file>

 2898: =head2 Remote configuration directories (Newcastle Connection)
 2899: 
 2900: Any entry in C<config_dirs> whose path begins with C</../> is treated as a
 2901: remote specification rather than a local directory:
 2902: 
 2903:   /../hostname/path/to/dir
 2904: 
 2905: The hostname and directory are extracted, and the same standard files searched
 2906: locally (C<base.yaml>, C<local.yaml>, C<base.json>, etc.) are fetched from
 2907: the remote machine via L<File::Slurp::Remote> over SSH.
 2908: 
 2909: When the hostname resolves to the local machine -- C<localhost>, C<127.0.0.1>,
 2910: C<::1>, or the value returned by C<Sys::Hostname::hostname()> (checked as
 2911: both fully-qualified and short form, case-insensitively) -- the C</../host/>
 2912: wrapper is silently unwrapped and the enclosed path is processed through the
 2913: normal local file pipeline instead.  No SSH connection is made.  This means a
 2914: configuration written for a shared remote host degrades gracefully when run on
 2915: that host itself:
 2916: 
 2917:   # On any other machine: fetches /etc/myapp over SSH
 2918:   # On cfg-server itself: reads /etc/myapp from disk directly
 2919:   config_dirs => ['/../cfg-server/etc/myapp']
 2920: 
 2921: Remote directories participate in the normal merge pipeline and can be freely
 2922: mixed with local ones:
 2923: 
 2924:   my $cfg = Config::Abstraction->new(
 2925:       config_dirs => [
 2926:           '/etc/myapp',                        # local
 2927:           '/../deploy@cfg-server/etc/myapp',   # remote via SSH (local on cfg-server)
 2928:       ],
 2929:   );
 2930: 
 2931: SSH authentication is handled by the system SSH client.
 2932: No extra constructor options are required; use your SSH agent or
 2933: C<~/.ssh/config> for host-specific settings.
 2934: 
 2935: L<File::Slurp::Remote> must be installed for remote directories to work.
 2936: If it is absent the directory is silently skipped and a warning is emitted.
 2937: 
 2938: =head3 Why C</../> (the Newcastle Connection convention)
 2939: 
 2940: Several syntaxes were considered for marking a C<config_dirs> entry as remote.
 2941: Each alternative was rejected for a concrete reason:
 2942: 
 2943: =over 4
 2944: 
 2945: =item C<hostname/path> -- ambiguous
 2946: 
 2947: Indistinguishable from a relative local directory named C<hostname>.
 2948: The module cannot tell at parse time whether C<myserver/etc> is a two-level
 2949: local path or a remote specification.
 2950: 
 2951: =item C<hostname:/path> -- collides with Windows drive letters
 2952: 
 2953: The C<X:\> drive-letter convention on Windows uses exactly the same
 2954: C<letter:> prefix.  A single-letter hostname would be misidentified as a
 2955: drive, and path-normalisation code on Windows would mangle it.
 2956: 
 2957: =item C<file://hostname/path> -- wrong semantics
 2958: 
 2959: RFC 8089 defines C<file://> as a reference to a B<local> file.
 2960: C<file:///etc/passwd> (three slashes, empty host) is the canonical local form;
 2961: C<file://hostname/path> is reserved for the host component but is explicitly
 2962: discouraged for general use and is not understood by most tooling as meaning
 2963: SSH.
 2964: 
 2965: =item C<ssh://hostname/path> -- requires URI parsing
 2966: 
 2967: Introduces a dependency on URI parsing (or a bespoke prefix check) and
 2968: implies a specific transport.  C<File::Slurp::Remote> already abstracts
 2969: the transport; encoding C<ssh://> in the path would be misleading if a future
 2970: version of that module supports other transports such as C<rsync://>.
 2971: 
 2972: =item C</../hostname/path> -- the Newcastle Connection
 2973: 
 2974: The Newcastle Connection (Brownbridge, Dion, Elsworth, 1982) is a distributed
 2975: Unix convention in which the token C</../> at the start of a pathname means
 2976: "leave the local namespace and enter the named remote host".
 2977: It works because C</../> B<cannot exist> as a real filesystem path:
 2978: C<..> from the root directory resolves back to the root on every POSIX system,
 2979: so C</../> always denotes the root itself, never a child of the root.
 2980: No pathname-normalisation step, C<chdir>, or filesystem traversal will ever
 2981: produce a path that legitimately begins with C</../>, which means the prefix
 2982: is a permanent, collision-free sentinel that requires only a regex to detect.
 2983: 
 2984: =back
 2985: 
 2986: The Newcastle Connection prefix is therefore the only choice that is:
 2987: 
 2988: =over 4
 2989: 
 2990: =item * unambiguous on all platforms (POSIX and Windows)
 2991: 
 2992: =item * impossible to produce accidentally from a real local path
 2993: 
 2994: =item * detectable with a single C<m{^\Q/../\E}> regex, no URI parser needed
 2995: 
 2996: =item * transport-neutral (the hostname is passed to whatever remote driver is installed)
 2997: 
 2998: =back

 3275: =head1 ENCRYPTED VALUES
 3276: 
 3277: Config::Abstraction supports transparent AES-256-GCM encryption of individual
 3278: configuration values.  This lets you store secrets (passwords, API keys, tokens)
 3279: in config files without exposing them as plaintext, even when those files are
 3280: committed to version control.
 3281: 
 3282: =head2 Quick start
 3283: 
 3284: B<Step 1 -- generate a key:>
 3285: 
 3286:   # 32 random bytes, encoded as 64 hex chars
 3287:   perl -e 'use Crypt::PRNG qw(random_bytes); use MIME::Base64 qw(encode_base64url);
 3288:            print encode_base64url(random_bytes(32)), "\n"'
 3289: 
 3290: Store the result in an environment variable or a key file (outside version control):
 3291: 
 3292:   export ENCRYPTION_KEY=<the 44-char base64url output>
 3293: 
 3294: B<Step 2 -- encrypt a secret value:>
 3295: 
 3296:   perl -MConfig::Abstraction -e '
 3297:     my $cfg = Config::Abstraction->new(data => {});
 3298:     print $cfg->encrypt_value("my_secret_password"), "\n";
 3299:   '
 3300: 
 3301: This prints something like:
 3302: 
 3303:   ENC[AES256GCM,QkJCQkJCQkJCQkJCO6Gfb0o5...]
 3304: 
 3305: B<Step 3 -- paste the token into your config file:>
 3306: 
 3307:   # config/base.yaml
 3308:   database:
 3309:     host: db.example.com
 3310:     user: myapp
 3311:     password: 'ENC[AES256GCM,QkJCQkJCQkJCQkJCO6Gfb0o5...]'
 3312: 
 3313: B<Step 4 -- load and use normally:>
 3314: 
 3315:   my $cfg = Config::Abstraction->new(config_dirs => ['config']);
 3316:   # $cfg->get('database.password') returns 'my_secret_password' -- already decrypted
 3317: 
 3318: =head2 Key configuration
 3319: 
 3320: The encryption key is resolved in this order (first match wins):
 3321: 
 3322: =over 4
 3323: 
 3324: =item 1. C<encryption_key> constructor option (raw bytes, hex, or base64)
 3325: 
 3326: =item 2. C<{env_prefix}ENCRYPTION_KEY> environment variable (default: C<APP_ENCRYPTION_KEY>)
 3327: 
 3328: =item 3. C<ENCRYPTION_KEY> environment variable
 3329: 
 3330: =item 4. File at C<encryption_key_file> constructor option
 3331: 
 3332: =item 5. File at C<{env_prefix}ENCRYPTION_KEY_FILE> environment variable
 3333: 
 3334: =item 6. File at C<ENCRYPTION_KEY_FILE> environment variable
 3335: 
 3336: =back
 3337: 
 3338: The key file should contain the key on its first line in any supported format.
 3339: B<Never commit the key to version control.>
 3340: 
 3341: =head2 Token format
 3342: 
 3343:   ENC[AES256GCM,<base64url(nonce || ciphertext || tag)>]
 3344: 
 3345: =over 4
 3346: 
 3347: =item * C<AES256GCM> -- AES-256 in GCM mode (authenticated encryption)
 3348: 
 3349: =item * Nonce -- 12 random bytes (fresh per encryption, never reused)
 3350: 
 3351: =item * GCM authentication tag -- 16 bytes; any modification causes decryption to croak
 3352: 
 3353: =item * Base64url encoding -- URL-safe alphabet, no padding ambiguity
 3354: 
 3355: =back
 3356: 
 3357: =head2 Behaviour when no key is configured
 3358: 
 3359: If no key is found, C<ENC[...]> tokens are left as literal strings.  This means
 3360: the feature is purely opt-in: existing deployments without a key configured are
 3361: unaffected.
 3362: 
 3363: =head2 Requirements
 3364: 
 3365: L<CryptX> (C<Crypt::AuthEnc::GCM>, C<Crypt::PRNG>) must be installed:
 3366: 
 3367:   cpanm CryptX

 3369: =head1 COMMON PITFALLS
 3370: 
 3371: =head2 1. new() returns undef when no configuration is found
 3372: 
 3373: C<new()> returns C<undef>, not a blessed object, when no configuration data is
 3374: found and no C<data> argument was supplied.  Every caller must check the return value.
 3375: 
 3376:   my $cfg = Config::Abstraction->new(config_dirs => ['/etc/myapp']);
 3377:   die "No configuration found" unless defined $cfg;
 3378:   my $host = $cfg->get('database.host');   # safe
 3379: 
 3380: Forgetting the check leads to a cryptic "Can't call method on undef" error later,
 3381: with a stack trace that points to C<get()> rather than to the missing config file.
 3382: 
 3383: =head2 2. merge_defaults() requires a named argument, not a bare hashref
 3384: 
 3385:   # WRONG -- Params::Get fast-path returns the whole config unchanged
 3386:   my $merged = $cfg->merge_defaults(\%my_defaults);
 3387: 
 3388:   # RIGHT
 3389:   my $merged = $cfg->merge_defaults(defaults => \%my_defaults);
 3390: 
 3391: With the first form, C<Params::Get> treats the single hashref as the entire
 3392: parameter bag and returns the full config without merging anything.
 3393: 
 3394: =head2 3. Shallow merge in merge_defaults() silently drops nested keys from defaults
 3395: 
 3396: Without C<merge =E<gt> 1>, C<merge_defaults()> uses a plain Perl hash merge
 3397: (C<{ %defaults, %config }>) at the top level.  If the config contains a nested hash
 3398: for a key, it entirely replaces the corresponding nested hash in your defaults - any
 3399: keys that exist only in the defaults' nested hash are silently discarded.
 3400: 
 3401:   my $cfg = Config::Abstraction->new(
 3402:       data        => { db => { host => 'localhost', port => 5432 } },
 3403:       config_dirs => [],
 3404:   );
 3405: 
 3406:   my $merged = $cfg->merge_defaults(defaults => { db => { user => 'guest' } });
 3407:   # $merged->{db}{user} is UNDEF -- the whole 'db' hash was replaced by the config's version
 3408: 
 3409:   # To combine nested keys from both sides, pass merge => 1:
 3410:   my $merged = $cfg->merge_defaults(defaults => { db => { user => 'guest' } }, merge => 1);
 3411:   # $merged->{db}{user} is 'guest', $merged->{db}{host} is 'localhost'
 3412: 
 3413: =head2 4. undef from a higher-priority source permanently wins
 3414: 
 3415: C<Hash::Merge> LEFT_PRECEDENT means that an explicit C<undef> (YAML C<~>) in a
 3416: higher-priority source overrides a real value in a lower-priority source, including
 3417: when the lower-priority value is defined.
 3418: 
 3419:   # base.yaml:  timeout: 30
 3420:   # local.yaml: timeout: ~
 3421: 
 3422:   my $t = $cfg->get('timeout');   # undef -- local.yaml's null wins over base.yaml
 3423: 
 3424: This is intentional: it lets a local config deliberately unset a value.  If you
 3425: want to detect whether a key was explicitly nulled versus simply absent, use
 3426: C<explain_sources()> and inspect the C<sources> list.
 3427: 
 3428: =head2 5. Double underscore vs. single underscore in environment variable names
 3429: 
 3430: Single underscores are part of the key name; double underscores create a nesting level.
 3431: 
 3432:   APP_LOG_LEVEL=debug       => key 'log_level'   (single underscore, flat key)
 3433:   APP_DATABASE__HOST=db     => key 'database.host' (double underscore, nested)
 3434:   APP_API__RATE_LIMIT=100   => key 'api.rate_limit' (double underscore + single)
 3435: 
 3436: A common mistake is using single underscores expecting nested keys:
 3437: 
 3438:   APP_DATABASE_HOST=db   # produces key 'database_host', NOT 'database.host'
 3439: 
 3440: =head2 6. Using AUTOLOAD requires sep_char set to '_'
 3441: 
 3442: AUTOLOAD translates method names to config keys using C<sep_char>.  The default
 3443: C<sep_char> is C<'.'>, but method names cannot contain dots.  Set C<sep_char =E<gt> '_'>
 3444: to use AUTOLOAD, and be aware that this makes single underscores into hierarchy separators.
 3445: 
 3446:   my $cfg = Config::Abstraction->new(
 3447:       data    => { database => { host => 'localhost' } },
 3448:       sep_char => '_',
 3449:       config_dirs => [],
 3450:   );
 3451:   my $host = $cfg->database_host();   # works
 3452:   my $bad  = $cfg->no_such_key();    # dies: No such config key 'no_such_key'
 3453: 
 3454: =head2 7. Absolute config_file paths require an empty or omitted config_dirs
 3455: 
 3456: On Unix, C<File::Spec-E<gt>catfile('/etc', '/absolute/path.yaml')> concatenates the
 3457: two strings instead of letting the absolute path take over, producing a wrong path.
 3458: When C<config_file> is an absolute path, either omit C<config_dirs> entirely
 3459: (the constructor sets it to C<['']> automatically) or pass C<config_dirs =E<gt> ['']>
 3460: explicitly.
 3461: 
 3462:   # WRONG on Unix -- produces '/etc/etc/myapp/app.yaml'
 3463:   Config::Abstraction->new(
 3464:       config_file => '/etc/myapp/app.yaml',
 3465:       config_dirs => ['/etc'],
 3466:   );
 3467: 
 3468:   # RIGHT
 3469:   Config::Abstraction->new( config_file => '/etc/myapp/app.yaml' );
 3470: 
 3471: =head2 8. Tests must isolate from the developer's real config files
 3472: 
 3473: A call to C<new()> without C<config_dirs> will scan C</etc>, C<~/.conf>,
 3474: C<~/.config>, and other default locations and load any C<base.yaml> or
 3475: C<local.yaml> it finds there.  In a test suite this injects real host
 3476: configuration into your test object, causing non-deterministic failures.
 3477: 
 3478: Always pass C<config_dirs =E<gt> []> in tests that use only in-memory C<data>:
 3479: 
 3480:   my $cfg = Config::Abstraction->new(
 3481:       data        => { key => 'value' },
 3482:       config_dirs => [],              # do not scan the filesystem
 3483:   );
 3484: 
 3485: =head2 9. lazy => 1 defers errors until the first accessor call
 3486: 
 3487: With C<lazy =E<gt> 1>, C<new()> always returns a blessed object - it cannot return
 3488: C<undef> for a missing config, and any schema validation errors surface at the first
 3489: C<get()> or C<all()> call rather than at construction time.  See the C<lazy>
 3490: option documentation in L</new> for the full list of debugging implications.

 3580: =head1 LIMITATIONS
 3581: 
 3582: =over 4
 3583: 
 3584: =item * B<No separator escaping>
 3585: 
 3586: The separator character (C<sep_char>, default C<.>) cannot be embedded in a key name.
 3587: A key that literally contains a dot cannot be accessed via C<get()> when C<sep_char> is
 3588: the default.  Workaround: set C<sep_char> to a character not present in any key.
 3589: 
 3590: =item * B<Data::Reuse fixation disabled>
 3591: 
 3592: The C<Data::Reuse::fixate()> call inside C<get()> is currently a no-op because the
 3593: behaviour of C<Crypt::Storable::dclone> differs between Linux and macOS in a way
 3594: that cannot be resolved portably (RT#100461).  Hash values returned by C<get()> are
 3595: mutable references, not read-only copies.
 3596: 
 3597: =item * B<Windows environment variable case sensitivity>
 3598: 
 3599: On Windows, environment variable names are case-insensitive at the OS level but
 3600: case-sensitive in C<%ENV> as seen by Perl.  Overriding config keys via environment
 3601: variables may silently fail if the case does not match exactly.
 3602: 
 3603: =item * B<AUTOLOAD requires sep_char set to '_'>
 3604: 
 3605: AUTOLOAD method dispatch converts underscores to key separators.  If C<sep_char> is
 3606: the default C<'.'>, AUTOLOAD cannot reach nested keys because Perl method names cannot
 3607: contain dots.
 3608: 
 3609: =item * B<Includes are checked, then read>
 3610: 
 3611: The directory check on an included file resolves its path and reads it a moment
 3612: later.  Someone who can write to the configuration directory could swap the file
 3613: for a symbolic link in between.  Anyone with that access can already change the
 3614: configuration, so this is not a privilege boundary, but do not rely on
 3615: C<include_dirs> to confine a directory that untrusted users can write to.
 3616: 
 3617: =item * B<Interpolation reaches values from every source>
 3618: 
 3619: With C<interpolate>, a configuration value is expanded whichever source it came
 3620: from, so an C<APP_> environment variable or command-line argument that
 3621: contains C<${env:NAME}> will pull in that other variable.  The text of a
 3622: variable read through C<${env:NAME}> is inserted as it is, without being
 3623: expanded again.
 3624: 
 3625: =item * B<Remote directory TOML support requires File::Slurp::Remote>
 3626: 
 3627: TOML files in Newcastle Connection remote directories are only fetched when the
 3628: C<File::Slurp::Remote> module is installed.  Without it, remote directories are
 3629: skipped entirely regardless of file format.
 3630: 
 3631: =back
