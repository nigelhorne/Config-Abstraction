   36: 
   37: =head2 Pattern 1: Environment overrides file overrides in-code defaults
   38: 
   39: The most common pattern for twelve-factor-style apps.
   40: The C<data> argument supplies defaults, a YAML file supplies site configuration,
   41: and environment variables allow per-deployment overrides without touching any file.
   42: 
   43:   # config/base.yaml
   44:   #   database:
   45:   #     host: db.example.com
   46:   #     port: 5432
   47:   #     user: app
   48: 
   49:   use Config::Abstraction;
   50: 
   51:   my $config = Config::Abstraction->new(
   52:       data        => { database => { host => 'localhost', port => 5432 } },
   53:       config_dirs => ['config'],
   54:       env_prefix  => 'APP_',
   55:   );
   56: 
   57:   # In production, set APP_DATABASE__HOST=db.prod.example.com in the environment.
   58:   # That silently overrides the file value, which in turn overrides the default.
   59:   my $host = $config->get('database.host');
   60:   my $port = $config->get('database.port');
   61: 
   62: =head2 Pattern 2: Command-line arguments override everything
   63: 
   64: Useful for CLI tools where operator flags must win over every other source.
   65: 
   66:   # Run as: myscript.pl --APP_LOGLEVEL=debug --APP_DATABASE__HOST=localhost
   67: 
   68:   use Config::Abstraction;
   69: 
   70:   my $config = Config::Abstraction->new(
   71:       config_dirs => ['config'],
   72:       env_prefix  => 'APP_',
   73:   );
   74: 
   75:   # @ARGV is consumed and stripped during new(); the resulting config already
   76:   # has cli-layer values at the highest precedence.
   77:   my $loglevel = $config->get('loglevel');       # 'debug'  (from --APP_LOGLEVEL)
   78:   my $db_host  = $config->get('database.host');  # 'localhost' (from --APP_DATABASE__HOST)
   79: 
   80: =head2 Pattern 3: Multi-file layering (base + local override)
   81: 
   82: Separates shared defaults from machine-specific tweaks.
   83: Every developer has a C<base.yaml>; only the production server has C<local.yaml>.
   84: 
   85:   # config/base.yaml   -- checked into version control
   86:   #   database:
   87:   #     host: localhost
   88:   #     user: dev
   89:   #
   90:   # config/local.yaml  -- NOT checked in; production only

  104:   # On the prod server:               host='db.prod.example.com', user='produser'
  105:   my $db = $config->get('database.host');
  106:   my $user = $config->get('database.user');

  108: =head1 DESCRIPTION
  109: 
  110: C<Config::Abstraction> is a flexible configuration management layer that sits above C<Config::*> modules.
  111: It provides a simple way to layer multiple configuration sources with predictable merge order.
  112: It lets you define sources such as:
  113: 
  114: =over 4
  115: 
  116: =item * Perl hashes (in-memory defaults or dynamic values)
  117: 
  118: =item * Environment variables (with optional prefixes)
  119: 
  120: =item * Configuration files (YAML, JSON, INI, or plain key=value)
  121: 
  122: =item * Command-line arguments
  123: 
  124: =back
  125: 
  126: Sources are applied in the order they are provided. Later sources override
  127: earlier ones unless a key is explicitly set to C<undef> in the later source.
  128: 
  129: In addition to using drivers to load configuration data from multiple file
  130: formats (YAML, JSON, XML, and INI),
  131: it also allows levels of configuration, each of which overrides the lower levels.
  132: So, it also integrates environment variable
  133: overrides and command line arguments for runtime configuration adjustments.
  134: This module is designed to help developers manage layered configurations that can be loaded from files and overridden at run-time for debugging,
  135: offering a modern, robust and dynamic approach
  136: to configuration management.
  137: 
  138: =head2 Merge Precedence
  139: 
  140: Sources are applied in the order shown below.  Each row wins over every row
  141: above it.  When the same key appears in multiple sources, the highest-priority
  142: source always determines the final value â€” including when that value is C<undef>.
  143: 
  144:   Priority   Source                         Set with
  145:   --------   ------                         --------
  146:      1 (lo)  data constructor argument      data => { key => 'default' }
  147:      2        base.*  config files          config/base.yaml, base.json, â€¦
  148:      3        local.* config files          config/local.yaml, local.json, â€¦
  149:      4        default / script-name files   config/default.yaml, myapp.yaml, â€¦
  150:      5        config_file / config_files    config_file => '/etc/myapp.yaml'
  151:      6        Environment variables         APP_DATABASE__HOST=db.prod.example.com
  152:      7 (hi)  CLI arguments (@ARGV)          --APP_DATABASE__HOST=db.prod.example.com
  153: 
  154: Within the file tier (rows 2â€“5), later files override earlier files using
  155: C<Hash::Merge> LEFT_PRECEDENT: every key in the later file wins over the same
  156: key in an earlier file, even when the later value is C<undef> (YAML C<~>).
  157: Nested hashes are merged recursively, so a C<local.yaml> that only sets
  158: C<database.host> will not erase C<database.port> from C<base.yaml>.
  159: 
  160:   Example â€” what wins for the key C<database.host>:
  161: 
  162:   data         =>  'localhost'       (overridden by base.yaml)
  163:   base.yaml    =>  'db.example.com'  (overridden by local.yaml)
  164:   local.yaml   =>  'db.prod.example.com'   (overridden by $APP_DATABASE__HOST)
  165:   $APP_DATABASE__HOST => 'db.staging.example.com'   <-- this wins

  167: =head2 KEY FEATURES
  168: 
  169: =over 4
  170: 
  171: =item * Multi-Format Support
  172: 
  173: Supports configuration files in YAML, JSON, XML, and INI formats.
  174: Automatically merges configuration data from these different formats,
  175: allowing hierarchical configuration management.
  176: 
  177: =item * Environment Variable Overrides
  178: 
  179: Allows environment variables to override values in the configuration files.
  180: By setting environment variables with a specific prefix (default: C<APP_>),
  181: values in the configuration files can be dynamically adjusted without modifying
  182: the file contents.
  183: 
  184: =item * Flattened Configuration Option
  185: 
  186: Optionally supports flattening the configuration structure. This converts deeply
  187: nested configuration keys into a flat key-value format (e.g., C<database.user>
  188: instead of C<database-E<gt>{user}>). This makes accessing values easier for
  189: applications that prefer flat structures or need compatibility with flat
  190: key-value stores.
  191: 
  192: =item * Layered Configuration
  193: 
  194: Supports merging multiple layers of configuration files. For example, you can
  195: have a C<base.yaml> configuration file that provides default values, and a
  196: C<local.yaml> (or C<local.json>, C<local.xml>, etc.) file that overrides
  197: specific values. This allows for environment-specific configurations while
  198: keeping defaults intact.
  199: 
  200: =item * Merge Strategy
  201: 
  202: The module merges the configuration data intelligently, allowing values in more
  203: specific files (like C<local.yaml>, C<local.json>, C<local.xml>, C<local.ini>)
  204: to override values in base files. This enables a flexible and layered configuration
  205: system where you can set defaults and override them for specific environments.
  206: 
  207: =item * Error Handling
  208: 
  209: Includes error handling for loading configuration files.
  210: If any file fails to
  211: load (e.g., due to syntax issues), the module will throw descriptive error
  212: messages to help with debugging.
  213: 
  214: =item * Centralized Configuration Management
  215: 
  216: Supports remote configuration management files,
  217: so that configuration on remote machines can be centrally managed.
  218: 
  219: =back

  243: =head2 ENVIRONMENT VARIABLE HANDLING
  244: 
  245: Configuration values can be overridden via environment variables. Environment variables use double underscores (__) to denote nested configuration keys and single underscores remain as part of the key name under the prefix namespace.
  246: 
  247: For example:
  248: 
  249:   APP_DATABASE__USER becomes database.user (nested structure)
  250: 
  251:     $ export APP_DATABASE__USER="env_user"
  252: 
  253: will override any value set for `database.user` in the configuration files.
  254: 
  255:   APP_LOGLEVEL becomes APP.loglevel (flat under prefix namespace)
  256: 
  257:   APP_API__RATE_LIMIT becomes api.rate_limit (mixed usage)
  258: 
  259: This allows you to override both top-level and nested configuration values using environment variables.
  260: 
  261: Configuration values can be overridden via the command line (C<@ARGV>).
  262: For instance, if you have a key in the configuration such as C<database.user>,
  263: you can override it by adding C<"--APP_DATABASE__USER=other_user_name"> to the command line arguments.
  264: This will override any value set for C<database.user> in the configuration files.

  266: =head2 EXAMPLE CONFIGURATION FLOW
  267: 
  268: =over 4
  269: 
  270: =item 1. Data Argument
  271: 
  272: The data passed into the constructor via the C<data> argument is the starting point.
  273: Essentially,
  274: this contains the default values.
  275: 
  276: =item 2. Loading Files
  277: 
  278: The module then looks for configuration files in the specified directories.
  279: It loads the following files in order of preference:
  280: C<base.yaml>, C<local.yaml>, C<base.json>, C<local.json>, C<base.xml>,
  281: C<local.xml>, C<base.ini>, and C<local.ini>.
  282: 
  283: If C<config_file> or C<config_files> is set, those files are loaded last.
  284: 
  285: If no C<config_dirs> is given, try hard to find the files in various places.
  286: 
  287: The value of C<config_dirs> can be overridden at runtime by the environment variable CONFIG_DIR
  288: (note that is just one directory, hence it's CONFIG_DIR not CONFIG_DIRS).
  289: 
  290: =item 3. Merging and Resolving
  291: 
  292: The module merges the contents of these files, with more specific configurations
  293: (e.g., C<local.*>) overriding general ones (e.g., C<base.*>).
  294: 
  295: =item 4. Environment Overrides
  296: 
  297: After loading and merging the configuration files,
  298: the environment variables are
  299: checked and used to override any conflicting settings.
  300: 
  301: =item 5. Command Line
  302: 
  303: Next, the command line arguments are checked and used to override any conflicting settings.
  304: 
  305: =item 6. Accessing Values
  306: 
  307: Values in the configuration can be accessed using a dotted notation
  308: (e.g., C<'database.user'>), regardless of the file format used.
  309: 
  310: =back

  411: =item * C<lazy>
  412: 
  413: When set to a true value, all source discovery and file I/O are deferred until the first
  414: call to C<get()>, C<exists()>, C<all()>, C<explain_sources()>, C<prefer_*()>,
  415: C<merge_defaults()>, or any AUTOLOAD accessor.  This can reduce startup time in
  416: applications that construct a C<Config::Abstraction> object before they know whether
  417: they will access it.
  418: 
  419: B<Differences from the default (eager) behaviour, and the debugging problems they cause:>
  420: 
  421: =over 4
  422: 
  423: =item 1. C<new()> always succeeds, even when no configuration exists.
  424: 
  425: In eager mode, C<new()> returns C<undef> immediately when no files are found and no
  426: C<data> was supplied, so a missing config is caught at the point of construction.
  427: In lazy mode, C<new()> always returns a blessed object.  If the configuration
  428: directories do not exist, the files are missing, or the prefix is wrong, you will
  429: not find out until the first accessor call - which may be deep inside your business
  430: logic, far from where the object was created.
  431: 
  432:   # Problem: the typo in config_dirs goes unnoticed until runtime
  433:   my $cfg = Config::Abstraction->new(
  434:       config_dirs => ['/etc/myapp/conifg'],   # typo - directory does not exist
  435:       lazy => 1,
  436:   );
  437:   # ... many lines later ...
  438:   my $host = $cfg->get('database.host');      # silently returns undef here
  439: 
  440: =item 2. Schema validation errors appear at the wrong place in the call stack.
  441: 
  442: When a C<schema> is supplied, eager mode validates the merged configuration inside
  443: C<new()> and throws immediately if the config does not match.  In lazy mode,
  444: validation is deferred to the first accessor call.  A schema violation therefore
  445: surfaces as an exception thrown by C<get()> or C<all()>, not by C<new()>, and the
  446: stack trace points to the accessor call rather than the construction site.  If the
  447: object is created in one module and accessed in another, the error message can be
  448: very misleading.
  449: 
  450: =item 3. Environment variables and C<@ARGV> are captured at access time, not construction time.
  451: 
  452: The module reads C<%ENV> and C<@ARGV> during C<_load_config()>.  In eager mode that
  453: happens in C<new()>, so the configuration reflects the environment at the moment the
  454: object is built.  In lazy mode, any change to C<%ENV> or C<@ARGV> between C<new()>
  455: and the first accessor call is silently picked up.  This makes test isolation harder:
  456: setting an environment variable I<after> constructing a lazy object will affect the
  457: values it returns, which is not the case with an eager object.
  458: 
  459: =item 4. File system state may change between construction and first use.
  460: 
  461: Because lazy mode defers all I/O, the files that are read are those that exist at the
  462: moment of first access, not at the moment C<new()> is called.  If a config file is
  463: written, deleted, or replaced between those two points (for example, by another
  464: process or test fixture), the object will silently use the new state.  An eager object
  465: is immune to this race.
  466: 
  467: =item 5. Errors from format parsers appear at accessor call sites.
  468: 
  469: Malformed YAML, JSON, XML, or INI files emit a C<carp> warning and are skipped during
  470: loading.  In eager mode those warnings appear near the program's startup.  In lazy mode
  471: they appear during the first accessor call, which can make it look as though a routine
  472: in your business logic is generating configuration warnings.
  473: 
  474: =back
  475: 
  476: B<When to use lazy loading:> It is most useful when a C<Config::Abstraction> object is
  477: created speculatively at module-load time and may never be accessed (for example, in a
  478: web framework where the config object is built for every request but some request paths
  479: never read it).  Avoid it when startup correctness is important, when you rely on
  480: C<new()> returning C<undef> to detect missing configuration, or when you use schema
  481: validation and need errors to point at the construction site.
  482:

 1506: =head2 Remote configuration directories (Newcastle Connection)
 1507: 
 1508: Any entry in C<config_dirs> whose path begins with C</../> is treated as a
 1509: remote specification rather than a local directory:
 1510: 
 1511:   /../hostname/path/to/dir
 1512: 
 1513: The hostname and directory are extracted, and the same standard files searched
 1514: locally (C<base.yaml>, C<local.yaml>, C<base.json>, etc.) are fetched from
 1515: the remote machine via L<File::Slurp::Remote> over SSH.
 1516: 
 1517: When the hostname resolves to the local machine -- C<localhost>, C<127.0.0.1>,
 1518: C<::1>, or the value returned by C<Sys::Hostname::hostname()> (checked as
 1519: both fully-qualified and short form, case-insensitively) -- the C</../host/>
 1520: wrapper is silently unwrapped and the enclosed path is processed through the
 1521: normal local file pipeline instead.  No SSH connection is made.  This means a
 1522: configuration written for a shared remote host degrades gracefully when run on
 1523: that host itself:
 1524: 
 1525:   # On any other machine: fetches /etc/myapp over SSH
 1526:   # On cfg-server itself: reads /etc/myapp from disk directly
 1527:   config_dirs => ['/../cfg-server/etc/myapp']
 1528: 
 1529: Remote directories participate in the normal merge pipeline and can be freely
 1530: mixed with local ones:
 1531: 
 1532:   my $cfg = Config::Abstraction->new(
 1533:       config_dirs => [
 1534:           '/etc/myapp',                        # local
 1535:           '/../deploy@cfg-server/etc/myapp',   # remote via SSH (local on cfg-server)
 1536:       ],
 1537:   );
 1538: 
 1539: SSH authentication is handled by the system SSH client.
 1540: No extra constructor options are required; use your SSH agent or
 1541: C<~/.ssh/config> for host-specific settings.
 1542: 
 1543: L<File::Slurp::Remote> must be installed for remote directories to work.
 1544: If it is absent the directory is silently skipped and a warning is emitted.
 1545: 
 1546: =head3 Why C</../> (the Newcastle Connection convention)
 1547: 
 1548: Several syntaxes were considered for marking a C<config_dirs> entry as remote.
 1549: Each alternative was rejected for a concrete reason:
 1550: 
 1551: =over 4
 1552: 
 1553: =item C<hostname/path> -- ambiguous
 1554: 
 1555: Indistinguishable from a relative local directory named C<hostname>.
 1556: The module cannot tell at parse time whether C<myserver/etc> is a two-level
 1557: local path or a remote specification.
 1558: 
 1559: =item C<hostname:/path> -- collides with Windows drive letters
 1560: 
 1561: The C<X:\> drive-letter convention on Windows uses exactly the same
 1562: C<letter:> prefix.  A single-letter hostname would be misidentified as a
 1563: drive, and path-normalisation code on Windows would mangle it.
 1564: 
 1565: =item C<file://hostname/path> -- wrong semantics
 1566: 
 1567: RFC 8089 defines C<file://> as a reference to a B<local> file.
 1568: C<file:///etc/passwd> (three slashes, empty host) is the canonical local form;
 1569: C<file://hostname/path> is reserved for the host component but is explicitly
 1570: discouraged for general use and is not understood by most tooling as meaning
 1571: SSH.
 1572: 
 1573: =item C<ssh://hostname/path> -- requires URI parsing
 1574: 
 1575: Introduces a dependency on URI parsing (or a bespoke prefix check) and
 1576: implies a specific transport.  C<File::Slurp::Remote> already abstracts
 1577: the transport; encoding C<ssh://> in the path would be misleading if a future
 1578: version of that module supports other transports such as C<rsync://>.
 1579: 
 1580: =item C</../hostname/path> -- the Newcastle Connection
 1581: 
 1582: The Newcastle Connection (Brownbridge, Dion, Elsworth, 1982) is a distributed
 1583: Unix convention in which the token C</../> at the start of a pathname means
 1584: "leave the local namespace and enter the named remote host".
 1585: It works because C</../> B<cannot exist> as a real filesystem path:
 1586: C<..> from the root directory resolves back to the root on every POSIX system,
 1587: so C</../> always denotes the root itself, never a child of the root.
 1588: No pathname-normalisation step, C<chdir>, or filesystem traversal will ever
 1589: produce a path that legitimately begins with C</../>, which means the prefix
 1590: is a permanent, collision-free sentinel that requires only a regex to detect.
 1591: 
 1592: =back
 1593: 
 1594: The Newcastle Connection prefix is therefore the only choice that is:
 1595: 
 1596: =over 4
 1597: 
 1598: =item * unambiguous on all platforms (POSIX and Windows)
 1599: 
 1600: =item * impossible to produce accidentally from a real local path
 1601: 
 1602: =item * detectable with a single C<m{^\Q/../\E}> regex, no URI parser needed
 1603: 
 1604: =item * transport-neutral (the hostname is passed to whatever remote driver is installed)
 1605: 
 1606: =back

 1865: =head1 COMMON PITFALLS
 1866: 
 1867: =head2 1. new() returns undef when no configuration is found
 1868: 
 1869: C<new()> returns C<undef>, not a blessed object, when no configuration data is
 1870: found and no C<data> argument was supplied.  Every caller must check the return value.
 1871: 
 1872:   my $cfg = Config::Abstraction->new(config_dirs => ['/etc/myapp']);
 1873:   die "No configuration found" unless defined $cfg;
 1874:   my $host = $cfg->get('database.host');   # safe
 1875: 
 1876: Forgetting the check leads to a cryptic "Can't call method on undef" error later,
 1877: with a stack trace that points to C<get()> rather than to the missing config file.
 1878: 
 1879: =head2 2. merge_defaults() requires a named argument, not a bare hashref
 1880: 
 1881:   # WRONG -- Params::Get fast-path returns the whole config unchanged
 1882:   my $merged = $cfg->merge_defaults(\%my_defaults);
 1883: 
 1884:   # RIGHT
 1885:   my $merged = $cfg->merge_defaults(defaults => \%my_defaults);
 1886: 
 1887: With the first form, C<Params::Get> treats the single hashref as the entire
 1888: parameter bag and returns the full config without merging anything.
 1889: 
 1890: =head2 3. Shallow merge in merge_defaults() silently drops nested keys from defaults
 1891: 
 1892: Without C<merge =E<gt> 1>, C<merge_defaults()> uses a plain Perl hash merge
 1893: (C<{ %defaults, %config }>) at the top level.  If the config contains a nested hash
 1894: for a key, it entirely replaces the corresponding nested hash in your defaults â€” any
 1895: keys that exist only in the defaults' nested hash are silently discarded.
 1896: 
 1897:   my $cfg = Config::Abstraction->new(
 1898:       data        => { db => { host => 'localhost', port => 5432 } },
 1899:       config_dirs => [],
 1900:   );
 1901: 
 1902:   my $merged = $cfg->merge_defaults(defaults => { db => { user => 'guest' } });
 1903:   # $merged->{db}{user} is UNDEF -- the whole 'db' hash was replaced by the config's version
 1904: 
 1905:   # To combine nested keys from both sides, pass merge => 1:
 1906:   my $merged = $cfg->merge_defaults(defaults => { db => { user => 'guest' } }, merge => 1);
 1907:   # $merged->{db}{user} is 'guest', $merged->{db}{host} is 'localhost'
 1908: 
 1909: =head2 4. undef from a higher-priority source permanently wins
 1910: 
 1911: C<Hash::Merge> LEFT_PRECEDENT means that an explicit C<undef> (YAML C<~>) in a
 1912: higher-priority source overrides a real value in a lower-priority source, including
 1913: when the lower-priority value is defined.
 1914: 
 1915:   # base.yaml:  timeout: 30
 1916:   # local.yaml: timeout: ~
 1917: 
 1918:   my $t = $cfg->get('timeout');   # undef -- local.yaml's null wins over base.yaml
 1919: 
 1920: This is intentional: it lets a local config deliberately unset a value.  If you
 1921: want to detect whether a key was explicitly nulled versus simply absent, use
 1922: C<explain_sources()> and inspect the C<sources> list.
 1923: 
 1924: =head2 5. Double underscore vs. single underscore in environment variable names
 1925: 
 1926: Single underscores are part of the key name; double underscores create a nesting level.
 1927: 
 1928:   APP_LOG_LEVEL=debug       => key 'log_level'   (single underscore, flat key)
 1929:   APP_DATABASE__HOST=db     => key 'database.host' (double underscore, nested)
 1930:   APP_API__RATE_LIMIT=100   => key 'api.rate_limit' (double underscore + single)
 1931: 
 1932: A common mistake is using single underscores expecting nested keys:
 1933: 
 1934:   APP_DATABASE_HOST=db   # produces key 'database_host', NOT 'database.host'
 1935: 
 1936: =head2 6. Using AUTOLOAD requires sep_char set to '_'
 1937: 
 1938: AUTOLOAD translates method names to config keys using C<sep_char>.  The default
 1939: C<sep_char> is C<'.'>, but method names cannot contain dots.  Set C<sep_char =E<gt> '_'>
 1940: to use AUTOLOAD, and be aware that this makes single underscores into hierarchy separators.
 1941: 
 1942:   my $cfg = Config::Abstraction->new(
 1943:       data    => { database => { host => 'localhost' } },
 1944:       sep_char => '_',
 1945:       config_dirs => [],
 1946:   );
 1947:   my $host = $cfg->database_host();   # works
 1948:   my $bad  = $cfg->no_such_key();    # dies: No such config key 'no_such_key'
 1949: 
 1950: =head2 7. Absolute config_file paths require an empty or omitted config_dirs
 1951: 
 1952: On Unix, C<File::Spec-E<gt>catfile('/etc', '/absolute/path.yaml')> concatenates the
 1953: two strings instead of letting the absolute path take over, producing a wrong path.
 1954: When C<config_file> is an absolute path, either omit C<config_dirs> entirely
 1955: (the constructor sets it to C<['']> automatically) or pass C<config_dirs =E<gt> ['']>
 1956: explicitly.
 1957: 
 1958:   # WRONG on Unix -- produces '/etc/etc/myapp/app.yaml'
 1959:   Config::Abstraction->new(
 1960:       config_file => '/etc/myapp/app.yaml',
 1961:       config_dirs => ['/etc'],
 1962:   );
 1963: 
 1964:   # RIGHT
 1965:   Config::Abstraction->new( config_file => '/etc/myapp/app.yaml' );
 1966: 
 1967: =head2 8. Tests must isolate from the developer's real config files
 1968: 
 1969: A call to C<new()> without C<config_dirs> will scan C</etc>, C<~/.conf>,
 1970: C<~/.config>, and other default locations and load any C<base.yaml> or
 1971: C<local.yaml> it finds there.  In a test suite this injects real host
 1972: configuration into your test object, causing non-deterministic failures.
 1973: 
 1974: Always pass C<config_dirs =E<gt> []> in tests that use only in-memory C<data>:
 1975: 
 1976:   my $cfg = Config::Abstraction->new(
 1977:       data        => { key => 'value' },
 1978:       config_dirs => [],              # do not scan the filesystem
 1979:   );
 1980: 
 1981: =head2 9. lazy => 1 defers errors until the first accessor call
 1982: 
 1983: With C<lazy =E<gt> 1>, C<new()> always returns a blessed object â€” it cannot return
 1984: C<undef> for a missing config, and any schema validation errors surface at the first
 1985: C<get()> or C<all()> call rather than at construction time.  See the C<lazy>
 1986: option documentation in L</new> for the full list of debugging implications.
