   47: 
   48: =head2 Pattern 1: Environment overrides file overrides in-code defaults
   49: 
   50: The most common pattern for twelve-factor-style apps.
   51: The C<data> argument supplies defaults, a YAML file supplies site configuration,
   52: and environment variables allow per-deployment overrides without touching any file.
   53: 
   54:   # config/base.yaml
   55:   #   database:
   56:   #     host: db.example.com
   57:   #     port: 5432
   58:   #     user: app
   59: 
   60:   use Config::Abstraction;
   61: 
   62:   my $config = Config::Abstraction->new(
   63:       data        => { database => { host => 'localhost', port => 5432 } },
   64:       config_dirs => ['config'],
   65:       env_prefix  => 'APP_',
   66:   );
   67: 
   68:   # In production, set APP_DATABASE__HOST=db.prod.example.com in the environment.
   69:   # That silently overrides the file value, which in turn overrides the default.
   70:   my $host = $config->get('database.host');
   71:   my $port = $config->get('database.port');
   72: 
   73: =head2 Pattern 2: Command-line arguments override everything
   74: 
   75: Useful for CLI tools where operator flags must win over every other source.
   76: 
   77:   # Run as: myscript.pl --APP_LOGLEVEL=debug --APP_DATABASE__HOST=localhost
   78: 
   79:   use Config::Abstraction;
   80: 
   81:   my $config = Config::Abstraction->new(
   82:       config_dirs => ['config'],
   83:       env_prefix  => 'APP_',
   84:   );
   85: 
   86:   # @ARGV is consumed and stripped during new(); the resulting config already
   87:   # has cli-layer values at the highest precedence.
   88:   my $loglevel = $config->get('loglevel');       # 'debug'  (from --APP_LOGLEVEL)
   89:   my $db_host  = $config->get('database.host');  # 'localhost' (from --APP_DATABASE__HOST)
   90: 
   91: =head2 Pattern 3: Multi-file layering (base + local override)
   92: 
   93: Separates shared defaults from machine-specific tweaks.
   94: Every developer has a C<base.yaml>; only the production server has C<local.yaml>.
   95: 
   96:   # config/base.yaml   -- checked into version control
   97:   #   database:
   98:   #     host: localhost
   99:   #     user: dev
  100:   #
  101:   # config/local.yaml  -- NOT checked in; production only
  102:   #   database:
  103:   #     host: db.prod.example.com
  104:   #     user: produser
  105:   #     password: s3cr3t
  106: 
  107:   use Config::Abstraction;
  108: 
  109:   my $config = Config::Abstraction->new(

  112:   );

  114:   # On a dev machine (no local.yaml): host='localhost', user='dev'
  115:   # On the prod server:               host='db.prod.example.com', user='produser'
  116:   my $db = $config->get('database.host');
  117:   my $user = $config->get('database.user');

  119: =head1 DESCRIPTION
  120: 
  121: C<Config::Abstraction> is a flexible configuration management layer that sits above C<Config::*> modules.
  122: It provides a simple way to layer multiple configuration sources with predictable merge order.
  123: It lets you define sources such as:
  124: 
  125: =over 4
  126: 
  127: =item * Perl hashes (in-memory defaults or dynamic values)
  128: 
  129: =item * Environment variables (with optional prefixes)
  130: 
  131: =item * Configuration files (YAML, JSON, INI, or plain key=value)
  132: 
  133: =item * Command-line arguments
  134: 
  135: =back
  136: 
  137: Sources are applied in the order they are provided. Later sources override
  138: earlier ones unless a key is explicitly set to C<undef> in the later source.
  139: 
  140: In addition to using drivers to load configuration data from multiple file
  141: formats (YAML, JSON, XML, and INI),
  142: it also allows levels of configuration, each of which overrides the lower levels.
  143: So, it also integrates environment variable
  144: overrides and command line arguments for runtime configuration adjustments.
  145: This module is designed to help developers manage layered configurations that can be loaded from files and overridden at run-time for debugging,
  146: offering a modern, robust and dynamic approach
  147: to configuration management.
  148: 
  149: =head2 Merge Precedence
  150: 
  151: Sources are applied in the order shown below.  Each row wins over every row
  152: above it.  When the same key appears in multiple sources, the highest-priority
  153: source always determines the final value - including when that value is C<undef>.
  154: 
  155:   Priority   Source                         Set with
  156:   --------   ------                         --------
  157:      1 (lo)  data constructor argument      data => { key => 'default' }
  158:      2        base.*  config files          config/base.yaml, base.json, ...
  159:      3        base.{env}.* config files     config/base.prod.yaml, ...
  160:      4        local.* config files          config/local.yaml, local.json, ...
  161:      5        local.{env}.* config files    config/local.prod.yaml, ...
  162:      6        default / script-name files   config/default.yaml, myapp.yaml, ...
  163:      7        config_file / config_files    config_file => '/etc/myapp.yaml'
  164:      8        Environment variables         APP_DATABASE__HOST=db.prod.example.com
  165:      9 (hi)  CLI arguments (@ARGV)          --APP_DATABASE__HOST=db.prod.example.com
  166: 
  167: The active environment is set by the C<environment> constructor option, or
  168: auto-detected from C<{env_prefix}ENV> (e.g. C<APP_ENV>), C<PLACK_ENV>, or
  169: C<NODE_ENV>.  When no environment is configured, rows 3 and 5 are skipped.
  170: 
  171: Within the file tier (rows 2-7), later files override earlier files using
  172: C<Hash::Merge> LEFT_PRECEDENT: every key in the later file wins over the same
  173: key in an earlier file, even when the later value is C<undef> (YAML C<~>).
  174: Nested hashes are merged recursively, so a C<local.yaml> that only sets
  175: C<database.host> will not erase C<database.port> from C<base.yaml>.
  176: 
  177:   Example - what wins for the key C<database.host> when APP_ENV=prod:
  178: 
  179:   data              =>  'localhost'              (overridden by base.yaml)
  180:   base.yaml         =>  'db.example.com'         (overridden by base.prod.yaml)
  181:   base.prod.yaml    =>  'db.prod.example.com'    (overridden by local.yaml)
  182:   local.yaml        =>  'db.local.example.com'   (overridden by local.prod.yaml)
  183:   local.prod.yaml   =>  'db.prod-local.example.com'  (overridden by $APP_DATABASE__HOST)
  184:   $APP_DATABASE__HOST  =>  'db.override.example.com'    <-- this wins
  185: 
  186: =head2 KEY FEATURES
  187: 
  188: =over 4
  189: 
  190: =item * Multi-Format Support
  191: 
  192: Supports configuration files in YAML, JSON, XML, and INI formats.
  193: Automatically merges configuration data from these different formats,
  194: allowing hierarchical configuration management.
  195: 
  196: =item * Environment Variable Overrides
  197: 
  198: Allows environment variables to override values in the configuration files.
  199: By setting environment variables with a specific prefix (default: C<APP_>),
  200: values in the configuration files can be dynamically adjusted without modifying
  201: the file contents.
  202: 
  203: =item * Flattened Configuration Option
  204: 
  205: Optionally supports flattening the configuration structure. This converts deeply
  206: nested configuration keys into a flat key-value format (e.g., C<database.user>
  207: instead of C<database-E<gt>{user}>). This makes accessing values easier for
  208: applications that prefer flat structures or need compatibility with flat
  209: key-value stores.
  210: 
  211: =item * Layered Configuration
  212: 
  213: Supports merging multiple layers of configuration files. For example, you can
  214: have a C<base.yaml> configuration file that provides default values, and a
  215: C<local.yaml> (or C<local.json>, C<local.xml>, etc.) file that overrides
  216: specific values. This allows for environment-specific configurations while
  217: keeping defaults intact.
  218: 
  219: =item * Merge Strategy
  220: 
  221: The module merges the configuration data intelligently, allowing values in more
  222: specific files (like C<local.yaml>, C<local.json>, C<local.xml>, C<local.ini>)
  223: to override values in base files. This enables a flexible and layered configuration
  224: system where you can set defaults and override them for specific environments.
  225: 
  226: =item * Error Handling
  227: 
  228: Includes error handling for loading configuration files.
  229: If any file fails to
  230: load (e.g., due to syntax issues), the module will throw descriptive error
  231: messages to help with debugging.
  232: 
  233: =item * Centralized Configuration Management
  234: 
  235: Supports remote configuration management files,
  236: so that configuration on remote machines can be centrally managed.
  237: 
  238: =back

  240: =head2 SUPPORTED FILE FORMATS
  241: 
  242: =over 4
  243: 
  244: =item * YAML (C<*.yaml>, C<*.yml>)
  245: 
  246: Loaded with C<YAML::XS>.
  247: 
  248: =item * JSON (C<*.json>)
  249: 
  250: Loaded with C<JSON::MaybeXS>.
  251: 
  252: =item * XML (C<*.xml>)
  253: 
  254: Loaded with C<XML::Simple> (preferred) or C<XML::PP> (fallback).
  255: 
  256: =item * INI (C<*.ini>)
  257: 
  258: Loaded with C<Config::IniFiles>.
  259: 
  260: =item * TOML (C<*.toml>)
  261: 
  262: Loaded with C<TOML::Tiny>, which implements TOML 1.0.  TOML is a good choice
  263: for human-editable configuration because its syntax is unambiguous: all values
  264: are typed, strings must be quoted, and nesting uses C<[section]> headers or
  265: dotted keys rather than indentation.
  266: 
  267:   # Example: config/base.toml
  268:   [database]
  269:   host   = "db.example.com"
  270:   port   = 5432
  271:   user   = "app"
  272: 
  273:   [cache]
  274:   ttl    = 300
  275:   debug  = false
  276: 
  277: C<base.toml> and C<local.toml> are discovered automatically in C<config_dirs>;
  278: C<local.toml> has higher precedence than C<base.toml>, following the same
  279: layering rules as all other formats.  TOML is also tried as a fallback parser
  280: in the all-parsers chain used for extensionless C<config_file> entries.
  281: 
  282: If C<TOML::Tiny> is not installed, TOML files are silently skipped with a
  283: C<carp> warning.
  284: 
  285: =item * Apache-style (C<*.conf>)
  286: 
  287: Loaded with L<Config::General>, which is optional.  C<base.conf>,
  288: C<local.conf> and their environment-specific forms are discovered like the
  289: other formats, and Config::General is the last parser tried for an
  290: extensionless C<config_file>.  If it is not installed, C<.conf> files are
  291: skipped.
  292: 
  293:   name      = myapp
  294:   log       debug
  295:   log       trace            # repeated keys become an array
  296:   <database>
  297:       host  = db.example.com
  298:       port  = 5432
  299:   </database>
  300:   <host www.example.com>     # a named block nests one level further
  301:       root  /var/www
  302:   </host>
  303: 
  304: Config::General's own C<E<lt>E<lt>include ...E<gt>E<gt>> directive is B<not>
  305: honoured, and a file that uses it is skipped with a warning, because it reads
  306: any file the process can read.  Use the C<include> key described under
  307: L</INCLUDING FILES> instead.  Config::General's variable interpolation is
  308: switched off in favour of L</VARIABLE INTERPOLATION>.
  309: 
  310: =back
  311: 
  312: =head2 INCLUDING FILES
  313: 
  314: With C<allow_includes =E<gt> 1>, a configuration file may name other files
  315: in a top-level C<include> key (a path, a glob, or an arrayref of them):
  316: 
  317:   # base.yaml
  318:   include:
  319:     - defaults/common.yaml
  320:     - conf.d/*.json
  321:   name: myapp
  322: 
  323: Any format may include any other.  The included files are merged I<under> the
  324: file that includes them, so the including file wins over its includes and,
  325: of several includes, the later one wins over the earlier.  Globs are expanded
  326: in sorted order.  A relative path is taken relative to the including file, not
  327: to the current directory.  Included files appear in C<config_path> and, with
  328: their own entries, in C<explain_sources()>.
  329: 
  330: Because an include is a way to make the module read a file, it is confined:
  331: an included file must be within the directory of the file that began the
  332: chain (any depth below it), or within a directory listed in C<include_dirs>.
  333: Symbolic links are resolved before the check.  A file outside those
  334: directories, a circular include, or a chain deeper than C<include_max_depth>
  335: croaks.  An include that does not exist is skipped with a warning.
  336: 
  337: Includes are not followed in files fetched from remote directories
  338: (Newcastle Connection).
  339: 
  340: =head2 VARIABLE INTERPOLATION
  341: 
  342: With C<interpolate =E<gt> 1>, string values may refer to other values:
  343: 
  344:   database:
  345:     host: db.example.com
  346:     port: 5432
  347:   dsn:  "dbi:Pg:host=${database.host};port=${database.port}"
  348:   home: "${env:HOME}/app"
  349:   lang: "${env:LANG:-C}"
  350:   cost: "$$5"                    # a literal $5
  351: 
  352: =over 4
  353: 
  354: =item * C<${a.b}> -- the value of the configuration key C<a.b> (always C<.>-separated, whatever C<sep_char> is)
  355: 
  356: =item * C<${env:NAME}> -- the environment variable C<NAME>
  357: 
  358: =item * C<${...:-default}> -- C<default> when the key or variable is missing
  359: 
  360: =item * C<$$> -- a literal C<$>
  361: 
  362: =back
  363: 
  364: Expansion happens after every source (files, includes, environment, command
  365: line) has been merged, so a reference sees the final value of its key, and
  366: references may chain.  A bare C<$name> is not special.  Values that are
  367: C<ENC[...]> tokens are left alone, so a secret can be referred to only after
  368: decryption by not referring to it.  An undefined key or variable, a circular
  369: reference, or a reference to a hash or array croaks, unless
  370: C<interpolate_strict> is false.  The caller's C<data> hashref is never
  371: modified.
  372: 
  373: Turn this on only for configuration you trust: a value taken from an
  374: environment variable or command-line argument that contains
  375: C<${env:NAME}> will be expanded too.
  376: 
  377: =head2 ENVIRONMENT VARIABLE HANDLING
  378: 
  379: Configuration values can be overridden via environment variables. Environment variables use double underscores (__) to denote nested configuration keys and single underscores remain as part of the key name under the prefix namespace.
  380: 
  381: For example:
  382: 
  383:   APP_DATABASE__USER becomes database.user (nested structure)
  384: 
  385:     $ export APP_DATABASE__USER="env_user"
  386: 
  387: will override any value set for `database.user` in the configuration files.
  388: 
  389:   APP_LOGLEVEL becomes APP.loglevel (flat under prefix namespace)
  390: 
  391:   APP_API__RATE_LIMIT becomes api.rate_limit (mixed usage)
  392: 
  393: This allows you to override both top-level and nested configuration values using environment variables.
  394: 
  395: Configuration values can be overridden via the command line (C<@ARGV>).
  396: For instance, if you have a key in the configuration such as C<database.user>,
  397: you can override it by adding C<"--APP_DATABASE__USER=other_user_name"> to the command line arguments.
  398: This will override any value set for C<database.user> in the configuration files.

  400: =head2 EXAMPLE CONFIGURATION FLOW
  401: 
  402: =over 4
  403: 
  404: =item 1. Data Argument
  405: 
  406: The data passed into the constructor via the C<data> argument is the starting point.
  407: Essentially,
  408: this contains the default values.
  409: 
  410: =item 2. Loading Files
  411: 
  412: The module then looks for configuration files in the specified directories.
  413: It loads the following files in order of preference:
  414: C<base.yaml>, C<local.yaml>, C<base.json>, C<local.json>, C<base.xml>,
  415: C<local.xml>, C<base.ini>, and C<local.ini>.
  416: 
  417: If C<config_file> or C<config_files> is set, those files are loaded last.
  418: 
  419: If no C<config_dirs> is given,
  420: C<Config::Abstraction> tries hard to find the files in various places.
  421: 
  422: The value of C<config_dirs> can be overridden at runtime by the environment variable CONFIG_DIR
  423: (note that is just one directory, hence it's CONFIG_DIR not CONFIG_DIRS).
  424: 
  425: =item 3. Merging and Resolving
  426: 
  427: The module merges the contents of these files, with more specific configurations
  428: (e.g., C<local.*>) overriding general ones (e.g., C<base.*>).
  429: 
  430: =item 4. Environment Overrides
  431: 
  432: After loading and merging the configuration files,
  433: the environment variables are
  434: checked and used to override any conflicting settings.
  435: 
  436: =item 5. Command Line
  437: 
  438: Next, the command line arguments are checked and used to override any conflicting settings.
  439: 
  440: =item 6. Accessing Values
  441: 
  442: Values in the configuration can be accessed using a dotted notation
  443: (e.g., C<'database.user'>), regardless of the file format used.
  444: 
  445: =back

  447: =head1 METHODS
  448: 
  449: =head2 new
  450: 
  451: Constructor for creating a new configuration object.
  452: 
  453: Options:
  454: 
  455: =over 4
  456: 
  457: =item * C<config_dirs>
  458: 
  459: An arrayref of directories to look for configuration files
  460: (default: C<$CONFIG_DIR>, C<$HOME/.conf>, C<$HOME/config>, C<$HOME/conf>, C<$DOCUMENT_ROOT/conf>, C<$DOCUMENT_ROOT/../conf>, C<conf>).
  461: 
  462: For centralised configuration management,
  463: entries beginning with C</../> are treated as remote specifications using the
  464: Newcastle Connection convention -- see L</Remote configuration directories (Newcastle Connection)>.
  465: 
  466: =item * C<config_file>
  467: 
  468: Points to a configuration file of any format.
  469: 
  470: =item * C<config_files>
  471: 
  472: An arrayref of files to look for in the configuration directories.
  473: Put the more important files later,
  474: since later files override earlier ones.
  475: 
  476: Considers the files C<default> and C<$script_name> before looking at C<config_file> and C<config_files>.
  477: 
  478: The running script itself is never read as configuration, even when one of the
  479: configuration directories is the directory it is in, and neither is any file
  480: that starts with C<#!>, since such a file is a program rather than
  481: configuration, and the Perl parser would run it.
  482: 
  483: =item * C<data>
  484: 
  485: A hash ref of default data to prime the configuration with.
  486: These are applied before loading
  487: other sources and can be overridden by later sources or by explicitly passing
  488: options directly to C<new>.
  489: 
  490:   $config = Config::Abstraction->new(
  491:       data => {
  492:           log_level => 'info',
  493:           retries => 3,
  494:       }
  495:   );
  496: 
  497: =item * C<defaults>
  498: 
  499: A hash reference that provides default values for the object's own attributes (such as C<config_dirs>, C<logger>, C<flatten>, etc.).
  500: If this option is supplied,
  501: the object is initialized using the keys in this hash as the base;
  502: any other options passed directly to C<new()> (aside from C<env_prefix>) are ignored.
  503: This allows you to pre-define a standard configuration profile for the object itself.
  504: Note that C<defaults> is distinct from the C<data> option - C<data> supplies the initial configuration values that will be merged with files, environment, and command line,
  505: while C<defaults> sets the object's internal parameters.
  506: The C<env_prefix> value,
  507: if provided as a top-level argument,
  508: still takes precedence over any C<env_prefix> that might exist inside the C<defaults> hash.
  509: 
  510: =item * C<encryption_key>
  511: 
  512: A 256-bit (32-byte) AES key used to transparently decrypt C<ENC[...]> values found in any
  513: configuration source after the full merge.  The key may be supplied as:
  514: 
  515: =over 4
  516: 
  517: =item 32 raw bytes
  518: 
  519: =item 64 lowercase or uppercase hex characters
  520: 
  521: =item 44 Base64 or Base64url characters (standard or URL-safe alphabet, with or without trailing C<=>)
  522: 
  523: =back
  524: 
  525: If no key is configured (and neither C<encryption_key_file> nor the corresponding
  526: environment variables are set), C<ENC[...]> tokens are left as literal strings.
  527: Decryption requires L<CryptX> (C<Crypt::AuthEnc::GCM>); if that module is absent a
  528: C<croak> is raised when an encrypted value is encountered.
  529: 
  530: See L</ENCRYPTED VALUES> for the full workflow.
  531: 
  532: =item * C<encryption_key_file>
  533: 
  534: Path to a file whose first line contains the encryption key in any of the formats accepted
  535: by C<encryption_key>.  Takes precedence over the C<ENCRYPTION_KEY_FILE> and
  536: C<{env_prefix}ENCRYPTION_KEY_FILE> environment variables, but is overridden by a key
  537: supplied directly via C<encryption_key>.
  538: 
  539: =item * C<env_prefix>
  540: 
  541: A prefix for environment variable keys and comment line options, e.g. C<MYAPP_DATABASE__USER>,
  542: (default: C<'APP_'>).
  543: 
  544: =item * C<environment>
  545:

 2857: =head2 Remote configuration directories (Newcastle Connection)
 2858: 
 2859: Any entry in C<config_dirs> whose path begins with C</../> is treated as a
 2860: remote specification rather than a local directory:
 2861: 
 2862:   /../hostname/path/to/dir
 2863: 
 2864: The hostname and directory are extracted, and the same standard files searched
 2865: locally (C<base.yaml>, C<local.yaml>, C<base.json>, etc.) are fetched from
 2866: the remote machine via L<File::Slurp::Remote> over SSH.
 2867: 
 2868: When the hostname resolves to the local machine -- C<localhost>, C<127.0.0.1>,
 2869: C<::1>, or the value returned by C<Sys::Hostname::hostname()> (checked as
 2870: both fully-qualified and short form, case-insensitively) -- the C</../host/>
 2871: wrapper is silently unwrapped and the enclosed path is processed through the
 2872: normal local file pipeline instead.  No SSH connection is made.  This means a
 2873: configuration written for a shared remote host degrades gracefully when run on
 2874: that host itself:
 2875: 
 2876:   # On any other machine: fetches /etc/myapp over SSH
 2877:   # On cfg-server itself: reads /etc/myapp from disk directly
 2878:   config_dirs => ['/../cfg-server/etc/myapp']
 2879: 
 2880: Remote directories participate in the normal merge pipeline and can be freely
 2881: mixed with local ones:
 2882: 
 2883:   my $cfg = Config::Abstraction->new(
 2884:       config_dirs => [
 2885:           '/etc/myapp',                        # local
 2886:           '/../deploy@cfg-server/etc/myapp',   # remote via SSH (local on cfg-server)
 2887:       ],
 2888:   );
 2889: 
 2890: SSH authentication is handled by the system SSH client.
 2891: No extra constructor options are required; use your SSH agent or
 2892: C<~/.ssh/config> for host-specific settings.
 2893: 
 2894: L<File::Slurp::Remote> must be installed for remote directories to work.
 2895: If it is absent the directory is silently skipped and a warning is emitted.
 2896: 
 2897: =head3 Why C</../> (the Newcastle Connection convention)
 2898: 
 2899: Several syntaxes were considered for marking a C<config_dirs> entry as remote.
 2900: Each alternative was rejected for a concrete reason:
 2901: 
 2902: =over 4
 2903: 
 2904: =item C<hostname/path> -- ambiguous
 2905: 
 2906: Indistinguishable from a relative local directory named C<hostname>.
 2907: The module cannot tell at parse time whether C<myserver/etc> is a two-level
 2908: local path or a remote specification.
 2909: 
 2910: =item C<hostname:/path> -- collides with Windows drive letters
 2911: 
 2912: The C<X:\> drive-letter convention on Windows uses exactly the same
 2913: C<letter:> prefix.  A single-letter hostname would be misidentified as a
 2914: drive, and path-normalisation code on Windows would mangle it.
 2915: 
 2916: =item C<file://hostname/path> -- wrong semantics
 2917: 
 2918: RFC 8089 defines C<file://> as a reference to a B<local> file.
 2919: C<file:///etc/passwd> (three slashes, empty host) is the canonical local form;
 2920: C<file://hostname/path> is reserved for the host component but is explicitly
 2921: discouraged for general use and is not understood by most tooling as meaning
 2922: SSH.
 2923: 
 2924: =item C<ssh://hostname/path> -- requires URI parsing
 2925: 
 2926: Introduces a dependency on URI parsing (or a bespoke prefix check) and
 2927: implies a specific transport.  C<File::Slurp::Remote> already abstracts
 2928: the transport; encoding C<ssh://> in the path would be misleading if a future
 2929: version of that module supports other transports such as C<rsync://>.
 2930: 
 2931: =item C</../hostname/path> -- the Newcastle Connection
 2932: 
 2933: The Newcastle Connection (Brownbridge, Dion, Elsworth, 1982) is a distributed
 2934: Unix convention in which the token C</../> at the start of a pathname means
 2935: "leave the local namespace and enter the named remote host".
 2936: It works because C</../> B<cannot exist> as a real filesystem path:
 2937: C<..> from the root directory resolves back to the root on every POSIX system,
 2938: so C</../> always denotes the root itself, never a child of the root.
 2939: No pathname-normalisation step, C<chdir>, or filesystem traversal will ever
 2940: produce a path that legitimately begins with C</../>, which means the prefix
 2941: is a permanent, collision-free sentinel that requires only a regex to detect.
 2942: 
 2943: =back
 2944: 
 2945: The Newcastle Connection prefix is therefore the only choice that is:
 2946: 
 2947: =over 4
 2948: 
 2949: =item * unambiguous on all platforms (POSIX and Windows)
 2950: 
 2951: =item * impossible to produce accidentally from a real local path
 2952: 
 2953: =item * detectable with a single C<m{^\Q/../\E}> regex, no URI parser needed
 2954: 
 2955: =item * transport-neutral (the hostname is passed to whatever remote driver is installed)
 2956: 
 2957: =back

 3249: Store the result in an environment variable or a key file (outside version control):
 3250: 
 3251:   export ENCRYPTION_KEY=<the 44-char base64url output>
 3252: 
 3253: B<Step 2 -- encrypt a secret value:>
 3254: 
 3255:   perl -MConfig::Abstraction -e '
 3256:     my $cfg = Config::Abstraction->new(data => {});
 3257:     print $cfg->encrypt_value("my_secret_password"), "\n";
 3258:   '
 3259: 
 3260: This prints something like:
 3261: 
 3262:   ENC[AES256GCM,QkJCQkJCQkJCQkJCO6Gfb0o5...]
 3263: 
 3264: B<Step 3 -- paste the token into your config file:>
 3265: 
 3266:   # config/base.yaml
 3267:   database:
 3268:     host: db.example.com
 3269:     user: myapp
 3270:     password: 'ENC[AES256GCM,QkJCQkJCQkJCQkJCO6Gfb0o5...]'
 3271: 
 3272: B<Step 4 -- load and use normally:>
 3273: 
 3274:   my $cfg = Config::Abstraction->new(config_dirs => ['config']);
 3275:   # $cfg->get('database.password') returns 'my_secret_password' -- already decrypted
 3276: 
 3277: =head2 Key configuration
 3278: 
 3279: The encryption key is resolved in this order (first match wins):
 3280: 
 3281: =over 4
 3282: 
 3283: =item 1. C<encryption_key> constructor option (raw bytes, hex, or base64)
 3284: 
 3285: =item 2. C<{env_prefix}ENCRYPTION_KEY> environment variable (default: C<APP_ENCRYPTION_KEY>)
 3286: 
 3287: =item 3. C<ENCRYPTION_KEY> environment variable
 3288: 
 3289: =item 4. File at C<encryption_key_file> constructor option
 3290: 
 3291: =item 5. File at C<{env_prefix}ENCRYPTION_KEY_FILE> environment variable
 3292: 
 3293: =item 6. File at C<ENCRYPTION_KEY_FILE> environment variable
 3294: 
 3295: =back
 3296: 
 3297: The key file should contain the key on its first line in any supported format.
 3298: B<Never commit the key to version control.>
 3299: 
 3300: =head2 Token format
 3301: 
 3302:   ENC[AES256GCM,<base64url(nonce || ciphertext || tag)>]
 3303: 
 3304: =over 4
 3305: 
 3306: =item * C<AES256GCM> -- AES-256 in GCM mode (authenticated encryption)
 3307: 
 3308: =item * Nonce -- 12 random bytes (fresh per encryption, never reused)
 3309: 
 3310: =item * GCM authentication tag -- 16 bytes; any modification causes decryption to croak
 3311: 
 3312: =item * Base64url encoding -- URL-safe alphabet, no padding ambiguity
 3313: 
 3314: =back
 3315: 
 3316: =head2 Behaviour when no key is configured
 3317: 
 3318: If no key is found, C<ENC[...]> tokens are left as literal strings.  This means
 3319: the feature is purely opt-in: existing deployments without a key configured are
 3320: unaffected.

 3328: =head1 COMMON PITFALLS
 3329: 
 3330: =head2 1. new() returns undef when no configuration is found
 3331: 
 3332: C<new()> returns C<undef>, not a blessed object, when no configuration data is
 3333: found and no C<data> argument was supplied.  Every caller must check the return value.
 3334: 
 3335:   my $cfg = Config::Abstraction->new(config_dirs => ['/etc/myapp']);
 3336:   die "No configuration found" unless defined $cfg;
 3337:   my $host = $cfg->get('database.host');   # safe
 3338: 
 3339: Forgetting the check leads to a cryptic "Can't call method on undef" error later,
 3340: with a stack trace that points to C<get()> rather than to the missing config file.
 3341: 
 3342: =head2 2. merge_defaults() requires a named argument, not a bare hashref
 3343: 
 3344:   # WRONG -- Params::Get fast-path returns the whole config unchanged
 3345:   my $merged = $cfg->merge_defaults(\%my_defaults);
 3346: 
 3347:   # RIGHT
 3348:   my $merged = $cfg->merge_defaults(defaults => \%my_defaults);
 3349: 
 3350: With the first form, C<Params::Get> treats the single hashref as the entire
 3351: parameter bag and returns the full config without merging anything.
 3352: 
 3353: =head2 3. Shallow merge in merge_defaults() silently drops nested keys from defaults
 3354: 
 3355: Without C<merge =E<gt> 1>, C<merge_defaults()> uses a plain Perl hash merge
 3356: (C<{ %defaults, %config }>) at the top level.  If the config contains a nested hash
 3357: for a key, it entirely replaces the corresponding nested hash in your defaults - any
 3358: keys that exist only in the defaults' nested hash are silently discarded.
 3359: 
 3360:   my $cfg = Config::Abstraction->new(
 3361:       data        => { db => { host => 'localhost', port => 5432 } },
 3362:       config_dirs => [],
 3363:   );
 3364: 
 3365:   my $merged = $cfg->merge_defaults(defaults => { db => { user => 'guest' } });
 3366:   # $merged->{db}{user} is UNDEF -- the whole 'db' hash was replaced by the config's version
 3367: 
 3368:   # To combine nested keys from both sides, pass merge => 1:
 3369:   my $merged = $cfg->merge_defaults(defaults => { db => { user => 'guest' } }, merge => 1);
 3370:   # $merged->{db}{user} is 'guest', $merged->{db}{host} is 'localhost'
 3371: 
 3372: =head2 4. undef from a higher-priority source permanently wins
 3373: 
 3374: C<Hash::Merge> LEFT_PRECEDENT means that an explicit C<undef> (YAML C<~>) in a
 3375: higher-priority source overrides a real value in a lower-priority source, including
 3376: when the lower-priority value is defined.
 3377: 
 3378:   # base.yaml:  timeout: 30
 3379:   # local.yaml: timeout: ~
 3380: 
 3381:   my $t = $cfg->get('timeout');   # undef -- local.yaml's null wins over base.yaml
 3382: 
 3383: This is intentional: it lets a local config deliberately unset a value.  If you
 3384: want to detect whether a key was explicitly nulled versus simply absent, use
 3385: C<explain_sources()> and inspect the C<sources> list.
 3386: 
 3387: =head2 5. Double underscore vs. single underscore in environment variable names
 3388: 
 3389: Single underscores are part of the key name; double underscores create a nesting level.
 3390: 
 3391:   APP_LOG_LEVEL=debug       => key 'log_level'   (single underscore, flat key)
 3392:   APP_DATABASE__HOST=db     => key 'database.host' (double underscore, nested)
 3393:   APP_API__RATE_LIMIT=100   => key 'api.rate_limit' (double underscore + single)
 3394: 
 3395: A common mistake is using single underscores expecting nested keys:
 3396: 
 3397:   APP_DATABASE_HOST=db   # produces key 'database_host', NOT 'database.host'
 3398: 
 3399: =head2 6. Using AUTOLOAD requires sep_char set to '_'
 3400: 
 3401: AUTOLOAD translates method names to config keys using C<sep_char>.  The default
 3402: C<sep_char> is C<'.'>, but method names cannot contain dots.  Set C<sep_char =E<gt> '_'>
 3403: to use AUTOLOAD, and be aware that this makes single underscores into hierarchy separators.
 3404: 
 3405:   my $cfg = Config::Abstraction->new(
 3406:       data    => { database => { host => 'localhost' } },
 3407:       sep_char => '_',
 3408:       config_dirs => [],
 3409:   );
 3410:   my $host = $cfg->database_host();   # works
 3411:   my $bad  = $cfg->no_such_key();    # dies: No such config key 'no_such_key'
 3412: 
 3413: =head2 7. Absolute config_file paths require an empty or omitted config_dirs
 3414: 
 3415: On Unix, C<File::Spec-E<gt>catfile('/etc', '/absolute/path.yaml')> concatenates the
 3416: two strings instead of letting the absolute path take over, producing a wrong path.
 3417: When C<config_file> is an absolute path, either omit C<config_dirs> entirely
 3418: (the constructor sets it to C<['']> automatically) or pass C<config_dirs =E<gt> ['']>
 3419: explicitly.
 3420: 
 3421:   # WRONG on Unix -- produces '/etc/etc/myapp/app.yaml'
 3422:   Config::Abstraction->new(
 3423:       config_file => '/etc/myapp/app.yaml',
 3424:       config_dirs => ['/etc'],
 3425:   );
 3426: 
 3427:   # RIGHT
 3428:   Config::Abstraction->new( config_file => '/etc/myapp/app.yaml' );
 3429: 
 3430: =head2 8. Tests must isolate from the developer's real config files
 3431: 
 3432: A call to C<new()> without C<config_dirs> will scan C</etc>, C<~/.conf>,
 3433: C<~/.config>, and other default locations and load any C<base.yaml> or
 3434: C<local.yaml> it finds there.  In a test suite this injects real host
 3435: configuration into your test object, causing non-deterministic failures.
 3436: 
 3437: Always pass C<config_dirs =E<gt> []> in tests that use only in-memory C<data>:
 3438: 
 3439:   my $cfg = Config::Abstraction->new(
 3440:       data        => { key => 'value' },
 3441:       config_dirs => [],              # do not scan the filesystem
 3442:   );
 3443: 
 3444: =head2 9. lazy => 1 defers errors until the first accessor call
 3445: 
 3446: With C<lazy =E<gt> 1>, C<new()> always returns a blessed object - it cannot return
 3447: C<undef> for a missing config, and any schema validation errors surface at the first
 3448: C<get()> or C<all()> call rather than at construction time.  See the C<lazy>
 3449: option documentation in L</new> for the full list of debugging implications.

 3539: =head1 LIMITATIONS
 3540: 
 3541: =over 4
 3542: 
 3543: =item * B<No separator escaping>
 3544: 
 3545: The separator character (C<sep_char>, default C<.>) cannot be embedded in a key name.
 3546: A key that literally contains a dot cannot be accessed via C<get()> when C<sep_char> is
 3547: the default.  Workaround: set C<sep_char> to a character not present in any key.
 3548: 
 3549: =item * B<Data::Reuse fixation disabled>
 3550: 
 3551: The C<Data::Reuse::fixate()> call inside C<get()> is currently a no-op because the
 3552: behaviour of C<Crypt::Storable::dclone> differs between Linux and macOS in a way
 3553: that cannot be resolved portably (RT#100461).  Hash values returned by C<get()> are
 3554: mutable references, not read-only copies.
 3555: 
 3556: =item * B<Windows environment variable case sensitivity>
 3557: 
 3558: On Windows, environment variable names are case-insensitive at the OS level but
 3559: case-sensitive in C<%ENV> as seen by Perl.  Overriding config keys via environment
 3560: variables may silently fail if the case does not match exactly.
 3561: 
 3562: =item * B<AUTOLOAD requires sep_char set to '_'>
 3563: 
 3564: AUTOLOAD method dispatch converts underscores to key separators.  If C<sep_char> is
 3565: the default C<'.'>, AUTOLOAD cannot reach nested keys because Perl method names cannot
 3566: contain dots.
 3567: 
 3568: =item * B<Remote directory TOML support requires File::Slurp::Remote>
 3569: 
 3570: TOML files in Newcastle Connection remote directories are only fetched when the
 3571: C<File::Slurp::Remote> module is installed.  Without it, remote directories are
 3572: skipped entirely regardless of file format.
 3573: 
 3574: =back
