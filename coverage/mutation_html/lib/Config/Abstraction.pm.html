   52:   );

   55:   # That silently overrides the file value, which in turn overrides the default.

   60:

  105: =head1 DESCRIPTION
  106: 
  107: C<Config::Abstraction> is a flexible configuration management layer that sits above C<Config::*> modules.
  108: It provides a simple way to layer multiple configuration sources with predictable merge order.
  109: It lets you define sources such as:
  110: 
  111: =over 4
  112: 
  113: =item * Perl hashes (in-memory defaults or dynamic values)
  114: 
  115: =item * Environment variables (with optional prefixes)
  116: 
  117: =item * Configuration files (YAML, JSON, INI, or plain key=value)
  118: 
  119: =item * Command-line arguments
  120: 
  121: =back
  122: 
  123: Sources are applied in the order they are provided. Later sources override
  124: earlier ones unless a key is explicitly set to C<undef> in the later source.
  125: 
  126: In addition to using drivers to load configuration data from multiple file
  127: formats (YAML, JSON, XML, and INI),
  128: it also allows levels of configuration, each of which overrides the lower levels.
  129: So, it also integrates environment variable
  130: overrides and command line arguments for runtime configuration adjustments.
  131: This module is designed to help developers manage layered configurations that can be loaded from files and overridden at run-time for debugging,
  132: offering a modern, robust and dynamic approach
  133: to configuration management.
  134: 
  135: =head2 Merge Precedence
  136: 
  137: Sources are applied in the order shown below.  Each row wins over every row
  138: above it.  When the same key appears in multiple sources, the highest-priority
  139: source always determines the final value - including when that value is C<undef>.
  140: 
  141:   Priority   Source                         Set with
  142:   --------   ------                         --------
  143:      1 (lo)  data constructor argument      data => { key => 'default' }
  144:      2        base.*  config files          config/base.yaml, base.json, ...
  145:      3        local.* config files          config/local.yaml, local.json, ...
  146:      4        default / script-name files   config/default.yaml, myapp.yaml, ...
  147:      5        config_file / config_files    config_file => '/etc/myapp.yaml'
  148:      6        Environment variables         APP_DATABASE__HOST=db.prod.example.com
  149:      7 (hi)  CLI arguments (@ARGV)          --APP_DATABASE__HOST=db.prod.example.com
  150: 
  151: Within the file tier (rows 2-5), later files override earlier files using
  152: C<Hash::Merge> LEFT_PRECEDENT: every key in the later file wins over the same
  153: key in an earlier file, even when the later value is C<undef> (YAML C<~>).
  154: Nested hashes are merged recursively, so a C<local.yaml> that only sets
  155: C<database.host> will not erase C<database.port> from C<base.yaml>.
  156: 
  157:   Example - what wins for the key C<database.host>:
  158: 
  159:   data         =>  'localhost'       (overridden by base.yaml)
  160:   base.yaml    =>  'db.example.com'  (overridden by local.yaml)
  161:   local.yaml   =>  'db.prod.example.com'   (overridden by $APP_DATABASE__HOST)
  162:   $APP_DATABASE__HOST => 'db.staging.example.com'   <-- this wins
  163: 
  164: =head2 KEY FEATURES
  165: 
  166: =over 4
  167: 
  168: =item * Multi-Format Support
  169: 
  170: Supports configuration files in YAML, JSON, XML, and INI formats.
  171: Automatically merges configuration data from these different formats,
  172: allowing hierarchical configuration management.
  173: 
  174: =item * Environment Variable Overrides
  175: 
  176: Allows environment variables to override values in the configuration files.
  177: By setting environment variables with a specific prefix (default: C<APP_>),
  178: values in the configuration files can be dynamically adjusted without modifying
  179: the file contents.
  180: 
  181: =item * Flattened Configuration Option
  182: 
  183: Optionally supports flattening the configuration structure. This converts deeply
  184: nested configuration keys into a flat key-value format (e.g., C<database.user>
  185: instead of C<database-E<gt>{user}>). This makes accessing values easier for
  186: applications that prefer flat structures or need compatibility with flat
  187: key-value stores.
  188: 
  189: =item * Layered Configuration
  190: 
  191: Supports merging multiple layers of configuration files. For example, you can
  192: have a C<base.yaml> configuration file that provides default values, and a
  193: C<local.yaml> (or C<local.json>, C<local.xml>, etc.) file that overrides
  194: specific values. This allows for environment-specific configurations while
  195: keeping defaults intact.
  196: 
  197: =item * Merge Strategy
  198: 
  199: The module merges the configuration data intelligently, allowing values in more
  200: specific files (like C<local.yaml>, C<local.json>, C<local.xml>, C<local.ini>)
  201: to override values in base files. This enables a flexible and layered configuration
  202: system where you can set defaults and override them for specific environments.
  203: 
  204: =item * Error Handling
  205: 
  206: Includes error handling for loading configuration files.
  207: If any file fails to
  208: load (e.g., due to syntax issues), the module will throw descriptive error
  209: messages to help with debugging.
  210: 
  211: =item * Centralized Configuration Management
  212: 
  213: Supports remote configuration management files,
  214: so that configuration on remote machines can be centrally managed.
  215: 
  216: =back

  242: are typed, strings must be quoted, and nesting uses C<[section]> headers or
  243: dotted keys rather than indentation.
  244: 
  245:   # Example: config/base.toml
  246:   [database]
  247:   host   = "db.example.com"
  248:   port   = 5432
  249:   user   = "app"

  251:   [cache]
  252:   ttl    = 300
  253:   debug  = false

  255: C<base.toml> and C<local.toml> are discovered automatically in C<config_dirs>;
  256: C<local.toml> has higher precedence than C<base.toml>, following the same

  265: =head2 ENVIRONMENT VARIABLE HANDLING
  266: 
  267: Configuration values can be overridden via environment variables. Environment variables use double underscores (__) to denote nested configuration keys and single underscores remain as part of the key name under the prefix namespace.
  268: 
  269: For example:
  270: 
  271:   APP_DATABASE__USER becomes database.user (nested structure)
  272: 
  273:     $ export APP_DATABASE__USER="env_user"
  274: 
  275: will override any value set for `database.user` in the configuration files.
  276: 
  277:   APP_LOGLEVEL becomes APP.loglevel (flat under prefix namespace)
  278: 
  279:   APP_API__RATE_LIMIT becomes api.rate_limit (mixed usage)
  280: 
  281: This allows you to override both top-level and nested configuration values using environment variables.
  282: 
  283: Configuration values can be overridden via the command line (C<@ARGV>).
  284: For instance, if you have a key in the configuration such as C<database.user>,
  285: you can override it by adding C<"--APP_DATABASE__USER=other_user_name"> to the command line arguments.
  286: This will override any value set for C<database.user> in the configuration files.

  288: =head2 EXAMPLE CONFIGURATION FLOW
  289: 
  290: =over 4
  291: 
  292: =item 1. Data Argument
  293: 
  294: The data passed into the constructor via the C<data> argument is the starting point.
  295: Essentially,
  296: this contains the default values.
  297: 
  298: =item 2. Loading Files
  299: 
  300: The module then looks for configuration files in the specified directories.
  301: It loads the following files in order of preference:
  302: C<base.yaml>, C<local.yaml>, C<base.json>, C<local.json>, C<base.xml>,
  303: C<local.xml>, C<base.ini>, and C<local.ini>.
  304: 
  305: If C<config_file> or C<config_files> is set, those files are loaded last.
  306: 
  307: If no C<config_dirs> is given, try hard to find the files in various places.
  308: 
  309: The value of C<config_dirs> can be overridden at runtime by the environment variable CONFIG_DIR
  310: (note that is just one directory, hence it's CONFIG_DIR not CONFIG_DIRS).
  311: 
  312: =item 3. Merging and Resolving
  313: 
  314: The module merges the contents of these files, with more specific configurations
  315: (e.g., C<local.*>) overriding general ones (e.g., C<base.*>).
  316: 
  317: =item 4. Environment Overrides
  318: 
  319: After loading and merging the configuration files,
  320: the environment variables are
  321: checked and used to override any conflicting settings.
  322: 
  323: =item 5. Command Line
  324: 
  325: Next, the command line arguments are checked and used to override any conflicting settings.
  326: 
  327: =item 6. Accessing Values
  328: 
  329: Values in the configuration can be accessed using a dotted notation
  330: (e.g., C<'database.user'>), regardless of the file format used.
  331: 
  332: =back

  440: 
  441: B<Differences from the default (eager) behaviour, and the debugging problems they cause:>
  442: 
  443: =over 4
  444: 
  445: =item 1. C<new()> always succeeds, even when no configuration exists.
  446: 
  447: In eager mode, C<new()> returns C<undef> immediately when no files are found and no
  448: C<data> was supplied, so a missing config is caught at the point of construction.
  449: In lazy mode, C<new()> always returns a blessed object.  If the configuration
  450: directories do not exist, the files are missing, or the prefix is wrong, you will
  451: not find out until the first accessor call - which may be deep inside your business
  452: logic, far from where the object was created.
  453: 
  454:   # Problem: the typo in config_dirs goes unnoticed until runtime
  455:   my $cfg = Config::Abstraction->new(
  456:       config_dirs => ['/etc/myapp/conifg'],   # typo - directory does not exist
  457:       lazy => 1,
  458:   );
  459:   # ... many lines later ...
  460:   my $host = $cfg->get('database.host');      # silently returns undef here
  461: 
  462: =item 2. Schema validation errors appear at the wrong place in the call stack.
  463: 
  464: When a C<schema> is supplied, eager mode validates the merged configuration inside
  465: C<new()> and throws immediately if the config does not match.  In lazy mode,
  466: validation is deferred to the first accessor call.  A schema violation therefore
  467: surfaces as an exception thrown by C<get()> or C<all()>, not by C<new()>, and the
  468: stack trace points to the accessor call rather than the construction site.  If the
  469: object is created in one module and accessed in another, the error message can be
  470: very misleading.
  471: 
  472: =item 3. Environment variables and C<@ARGV> are captured at access time, not construction time.
  473: 
  474: The module reads C<%ENV> and C<@ARGV> during C<_load_config()>.  In eager mode that
  475: happens in C<new()>, so the configuration reflects the environment at the moment the
  476: object is built.  In lazy mode, any change to C<%ENV> or C<@ARGV> between C<new()>
  477: and the first accessor call is silently picked up.  This makes test isolation harder:
  478: setting an environment variable I<after> constructing a lazy object will affect the
  479: values it returns, which is not the case with an eager object.
  480: 
  481: =item 4. File system state may change between construction and first use.
  482: 
  483: Because lazy mode defers all I/O, the files that are read are those that exist at the
  484: moment of first access, not at the moment C<new()> is called.  If a config file is
  485: written, deleted, or replaced between those two points (for example, by another
  486: process or test fixture), the object will silently use the new state.  An eager object
  487: is immune to this race.
  488: 
  489: =item 5. Errors from format parsers appear at accessor call sites.
  490: 
  491: Malformed YAML, JSON, XML, or INI files emit a C<carp> warning and are skipped during
  492: loading.  In eager mode those warnings appear near the program's startup.  In lazy mode
  493: they appear during the first accessor call, which can make it look as though a routine
  494: in your business logic is generating configuration warnings.
  495: 
  496: =back
  497: 
  498: B<When to use lazy loading:> It is most useful when a C<Config::Abstraction> object is
  499: created speculatively at module-load time and may never be accessed (for example, in a
  500: web framework where the config object is built for every request but some request paths
  501: never read it).  Avoid it when startup correctness is important, when you rely on
  502: C<new()> returning C<undef> to detect missing configuration, or when you use schema
  503: validation and need errors to point at the construction site.
  504: 
  505: =back

 1556: =head2 Remote configuration directories (Newcastle Connection)
 1557: 
 1558: Any entry in C<config_dirs> whose path begins with C</../> is treated as a
 1559: remote specification rather than a local directory:
 1560: 
 1561:   /../hostname/path/to/dir
 1562: 
 1563: The hostname and directory are extracted, and the same standard files searched
 1564: locally (C<base.yaml>, C<local.yaml>, C<base.json>, etc.) are fetched from
 1565: the remote machine via L<File::Slurp::Remote> over SSH.
 1566: 
 1567: When the hostname resolves to the local machine -- C<localhost>, C<127.0.0.1>,
 1568: C<::1>, or the value returned by C<Sys::Hostname::hostname()> (checked as
 1569: both fully-qualified and short form, case-insensitively) -- the C</../host/>
 1570: wrapper is silently unwrapped and the enclosed path is processed through the
 1571: normal local file pipeline instead.  No SSH connection is made.  This means a
 1572: configuration written for a shared remote host degrades gracefully when run on
 1573: that host itself:
 1574: 
 1575:   # On any other machine: fetches /etc/myapp over SSH
 1576:   # On cfg-server itself: reads /etc/myapp from disk directly
 1577:   config_dirs => ['/../cfg-server/etc/myapp']
 1578: 
 1579: Remote directories participate in the normal merge pipeline and can be freely
 1580: mixed with local ones:
 1581: 
 1582:   my $cfg = Config::Abstraction->new(
 1583:       config_dirs => [
 1584:           '/etc/myapp',                        # local
 1585:           '/../deploy@cfg-server/etc/myapp',   # remote via SSH (local on cfg-server)
 1586:       ],
 1587:   );
 1588: 
 1589: SSH authentication is handled by the system SSH client.
 1590: No extra constructor options are required; use your SSH agent or
 1591: C<~/.ssh/config> for host-specific settings.
 1592: 
 1593: L<File::Slurp::Remote> must be installed for remote directories to work.
 1594: If it is absent the directory is silently skipped and a warning is emitted.
 1595: 
 1596: =head3 Why C</../> (the Newcastle Connection convention)
 1597: 
 1598: Several syntaxes were considered for marking a C<config_dirs> entry as remote.
 1599: Each alternative was rejected for a concrete reason:
 1600: 
 1601: =over 4
 1602: 
 1603: =item C<hostname/path> -- ambiguous
 1604: 
 1605: Indistinguishable from a relative local directory named C<hostname>.
 1606: The module cannot tell at parse time whether C<myserver/etc> is a two-level
 1607: local path or a remote specification.
 1608: 
 1609: =item C<hostname:/path> -- collides with Windows drive letters
 1610: 
 1611: The C<X:\> drive-letter convention on Windows uses exactly the same
 1612: C<letter:> prefix.  A single-letter hostname would be misidentified as a
 1613: drive, and path-normalisation code on Windows would mangle it.
 1614: 
 1615: =item C<file://hostname/path> -- wrong semantics
 1616: 
 1617: RFC 8089 defines C<file://> as a reference to a B<local> file.
 1618: C<file:///etc/passwd> (three slashes, empty host) is the canonical local form;
 1619: C<file://hostname/path> is reserved for the host component but is explicitly
 1620: discouraged for general use and is not understood by most tooling as meaning
 1621: SSH.
 1622: 
 1623: =item C<ssh://hostname/path> -- requires URI parsing
 1624: 
 1625: Introduces a dependency on URI parsing (or a bespoke prefix check) and
 1626: implies a specific transport.  C<File::Slurp::Remote> already abstracts
 1627: the transport; encoding C<ssh://> in the path would be misleading if a future
 1628: version of that module supports other transports such as C<rsync://>.
 1629: 
 1630: =item C</../hostname/path> -- the Newcastle Connection
 1631: 
 1632: The Newcastle Connection (Brownbridge, Dion, Elsworth, 1982) is a distributed
 1633: Unix convention in which the token C</../> at the start of a pathname means
 1634: "leave the local namespace and enter the named remote host".
 1635: It works because C</../> B<cannot exist> as a real filesystem path:
 1636: C<..> from the root directory resolves back to the root on every POSIX system,
 1637: so C</../> always denotes the root itself, never a child of the root.
 1638: No pathname-normalisation step, C<chdir>, or filesystem traversal will ever
 1639: produce a path that legitimately begins with C</../>, which means the prefix
 1640: is a permanent, collision-free sentinel that requires only a regex to detect.
 1641: 
 1642: =back
 1643: 
 1644: The Newcastle Connection prefix is therefore the only choice that is:
 1645: 
 1646: =over 4
 1647: 
 1648: =item * unambiguous on all platforms (POSIX and Windows)
 1649: 
 1650: =item * impossible to produce accidentally from a real local path
 1651: 
 1652: =item * detectable with a single C<m{^\Q/../\E}> regex, no URI parser needed
 1653: 
 1654: =item * transport-neutral (the hostname is passed to whatever remote driver is installed)
 1655: 
 1656: =back

 1915: =head1 COMMON PITFALLS
 1916: 
 1917: =head2 1. new() returns undef when no configuration is found
 1918: 
 1919: C<new()> returns C<undef>, not a blessed object, when no configuration data is
 1920: found and no C<data> argument was supplied.  Every caller must check the return value.
 1921: 
 1922:   my $cfg = Config::Abstraction->new(config_dirs => ['/etc/myapp']);
 1923:   die "No configuration found" unless defined $cfg;
 1924:   my $host = $cfg->get('database.host');   # safe
 1925: 
 1926: Forgetting the check leads to a cryptic "Can't call method on undef" error later,
 1927: with a stack trace that points to C<get()> rather than to the missing config file.
 1928: 
 1929: =head2 2. merge_defaults() requires a named argument, not a bare hashref
 1930: 
 1931:   # WRONG -- Params::Get fast-path returns the whole config unchanged
 1932:   my $merged = $cfg->merge_defaults(\%my_defaults);
 1933: 
 1934:   # RIGHT
 1935:   my $merged = $cfg->merge_defaults(defaults => \%my_defaults);
 1936: 
 1937: With the first form, C<Params::Get> treats the single hashref as the entire
 1938: parameter bag and returns the full config without merging anything.
 1939: 
 1940: =head2 3. Shallow merge in merge_defaults() silently drops nested keys from defaults
 1941: 
 1942: Without C<merge =E<gt> 1>, C<merge_defaults()> uses a plain Perl hash merge
 1943: (C<{ %defaults, %config }>) at the top level.  If the config contains a nested hash
 1944: for a key, it entirely replaces the corresponding nested hash in your defaults - any
 1945: keys that exist only in the defaults' nested hash are silently discarded.
 1946: 
 1947:   my $cfg = Config::Abstraction->new(
 1948:       data        => { db => { host => 'localhost', port => 5432 } },
 1949:       config_dirs => [],
 1950:   );
 1951: 
 1952:   my $merged = $cfg->merge_defaults(defaults => { db => { user => 'guest' } });
 1953:   # $merged->{db}{user} is UNDEF -- the whole 'db' hash was replaced by the config's version
 1954: 
 1955:   # To combine nested keys from both sides, pass merge => 1:
 1956:   my $merged = $cfg->merge_defaults(defaults => { db => { user => 'guest' } }, merge => 1);
 1957:   # $merged->{db}{user} is 'guest', $merged->{db}{host} is 'localhost'
 1958: 
 1959: =head2 4. undef from a higher-priority source permanently wins
 1960: 
 1961: C<Hash::Merge> LEFT_PRECEDENT means that an explicit C<undef> (YAML C<~>) in a
 1962: higher-priority source overrides a real value in a lower-priority source, including
 1963: when the lower-priority value is defined.
 1964: 
 1965:   # base.yaml:  timeout: 30
 1966:   # local.yaml: timeout: ~
 1967: 
 1968:   my $t = $cfg->get('timeout');   # undef -- local.yaml's null wins over base.yaml
 1969: 
 1970: This is intentional: it lets a local config deliberately unset a value.  If you
 1971: want to detect whether a key was explicitly nulled versus simply absent, use
 1972: C<explain_sources()> and inspect the C<sources> list.
 1973: 
 1974: =head2 5. Double underscore vs. single underscore in environment variable names
 1975: 
 1976: Single underscores are part of the key name; double underscores create a nesting level.
 1977: 
 1978:   APP_LOG_LEVEL=debug       => key 'log_level'   (single underscore, flat key)
 1979:   APP_DATABASE__HOST=db     => key 'database.host' (double underscore, nested)
 1980:   APP_API__RATE_LIMIT=100   => key 'api.rate_limit' (double underscore + single)
 1981: 
 1982: A common mistake is using single underscores expecting nested keys:
 1983: 
 1984:   APP_DATABASE_HOST=db   # produces key 'database_host', NOT 'database.host'
 1985: 
 1986: =head2 6. Using AUTOLOAD requires sep_char set to '_'
 1987: 
 1988: AUTOLOAD translates method names to config keys using C<sep_char>.  The default
 1989: C<sep_char> is C<'.'>, but method names cannot contain dots.  Set C<sep_char =E<gt> '_'>
 1990: to use AUTOLOAD, and be aware that this makes single underscores into hierarchy separators.
 1991: 
 1992:   my $cfg = Config::Abstraction->new(
 1993:       data    => { database => { host => 'localhost' } },
 1994:       sep_char => '_',
 1995:       config_dirs => [],
 1996:   );
 1997:   my $host = $cfg->database_host();   # works
 1998:   my $bad  = $cfg->no_such_key();    # dies: No such config key 'no_such_key'
 1999: 
 2000: =head2 7. Absolute config_file paths require an empty or omitted config_dirs
 2001: 
 2002: On Unix, C<File::Spec-E<gt>catfile('/etc', '/absolute/path.yaml')> concatenates the
 2003: two strings instead of letting the absolute path take over, producing a wrong path.
 2004: When C<config_file> is an absolute path, either omit C<config_dirs> entirely
 2005: (the constructor sets it to C<['']> automatically) or pass C<config_dirs =E<gt> ['']>
 2006: explicitly.
 2007: 
 2008:   # WRONG on Unix -- produces '/etc/etc/myapp/app.yaml'
 2009:   Config::Abstraction->new(
 2010:       config_file => '/etc/myapp/app.yaml',
 2011:       config_dirs => ['/etc'],
 2012:   );
 2013: 
 2014:   # RIGHT
 2015:   Config::Abstraction->new( config_file => '/etc/myapp/app.yaml' );
 2016: 
 2017: =head2 8. Tests must isolate from the developer's real config files
 2018: 
 2019: A call to C<new()> without C<config_dirs> will scan C</etc>, C<~/.conf>,
 2020: C<~/.config>, and other default locations and load any C<base.yaml> or
 2021: C<local.yaml> it finds there.  In a test suite this injects real host
 2022: configuration into your test object, causing non-deterministic failures.
 2023: 
 2024: Always pass C<config_dirs =E<gt> []> in tests that use only in-memory C<data>:
 2025: 
 2026:   my $cfg = Config::Abstraction->new(
 2027:       data        => { key => 'value' },
 2028:       config_dirs => [],              # do not scan the filesystem
 2029:   );
 2030: 
 2031: =head2 9. lazy => 1 defers errors until the first accessor call
 2032: 
 2033: With C<lazy =E<gt> 1>, C<new()> always returns a blessed object - it cannot return
 2034: C<undef> for a missing config, and any schema validation errors surface at the first
 2035: C<get()> or C<all()> call rather than at construction time.  See the C<lazy>
 2036: option documentation in L</new> for the full list of debugging implications.
