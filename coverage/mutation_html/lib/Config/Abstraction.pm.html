   33: =head1 SYNOPSIS
   34: 
   35: C<Config::Abstraction> lets you load configuration from multiple sources,
   36: such as files, environment variables, and in-code defaults,
   37: and merge them with predictable precedence.
   38: It provides a consistent API for accessing the configuration settings, regardless of where they came from,
   39: this helps keep your application's or class's configuration flexible, centralized, separate from your code base and easy to override.
   40: 
   41:   use Config::Abstraction;
   42: 
   43:   my $config = Config::Abstraction->new(
   44:     config_dirs => ['config'],
   45:     env_prefix => 'APP_',
   46:     flatten => 0,
   47:   );
   48: 
   49:   my $db_user = $config->get('database.user');
   50: 
   51: =head1 DESCRIPTION
   52: 
   53: C<Config::Abstraction> is a flexible configuration management layer that sits above C<Config::*> modules.
   54: It provides a simple way to layer multiple configuration sources with predictable merge order.
   55: It lets you define sources such as:
   56: 
   57: =over 4
   58: 
   59: =item * Perl hashes (in-memory defaults or dynamic values)
   60: 
   61: =item * Environment variables (with optional prefixes)
   62: 
   63: =item * Configuration files (YAML, JSON, INI, or plain key=value)
   64: 
   65: =item * Command-line arguments
   66: 
   67: =back
   68: 
   69: Sources are applied in the order they are provided. Later sources override
   70: earlier ones unless a key is explicitly set to C<undef> in the later source.
   71: 
   72: In addition to using drivers to load configuration data from multiple file
   73: formats (YAML, JSON, XML, and INI),
   74: it also allows levels of configuration, each of which overrides the lower levels.
   75: So, it also integrates environment variable
   76: overrides and command line arguments for runtime configuration adjustments.
   77: This module is designed to help developers manage layered configurations that can be loaded from files and overridden at run-time for debugging,
   78: offering a modern, robust and dynamic approach
   79: to configuration management.
   80: 
   81: =head2 Merge Precedence Diagram
   82: 
   83:   +----------------+
   84:   |   CLI args     |  (Highest priority)
   85:   +----------------+
   86:   | Environment    |
   87:   +----------------+
   88:   | Config file(s) |
   89:   +----------------+
   90:   | Defaults       |  (Lowest priority)
   91:   +----------------+

   93: =head2 KEY FEATURES
   94: 
   95: =over 4
   96: 
   97: =item * Multi-Format Support
   98: 
   99: Supports configuration files in YAML, JSON, XML, and INI formats.
  100: Automatically merges configuration data from these different formats,
  101: allowing hierarchical configuration management.
  102: 
  103: =item * Environment Variable Overrides
  104: 
  105: Allows environment variables to override values in the configuration files.
  106: By setting environment variables with a specific prefix (default: C<APP_>),
  107: values in the configuration files can be dynamically adjusted without modifying
  108: the file contents.
  109: 
  110: =item * Flattened Configuration Option
  111: 
  112: Optionally supports flattening the configuration structure. This converts deeply
  113: nested configuration keys into a flat key-value format (e.g., C<database.user>
  114: instead of C<database-E<gt>{user}>). This makes accessing values easier for
  115: applications that prefer flat structures or need compatibility with flat
  116: key-value stores.
  117: 
  118: =item * Layered Configuration
  119: 
  120: Supports merging multiple layers of configuration files. For example, you can
  121: have a C<base.yaml> configuration file that provides default values, and a
  122: C<local.yaml> (or C<local.json>, C<local.xml>, etc.) file that overrides
  123: specific values. This allows for environment-specific configurations while
  124: keeping defaults intact.
  125: 
  126: =item * Merge Strategy
  127: 
  128: The module merges the configuration data intelligently, allowing values in more
  129: specific files (like C<local.yaml>, C<local.json>, C<local.xml>, C<local.ini>)
  130: to override values in base files. This enables a flexible and layered configuration
  131: system where you can set defaults and override them for specific environments.
  132: 
  133: =item * Error Handling
  134: 
  135: Includes error handling for loading configuration files.
  136: If any file fails to
  137: load (e.g., due to syntax issues), the module will throw descriptive error
  138: messages to help with debugging.
  139: 
  140: =item * Centralized Configuration Management
  141: 
  142: Supports remote configuration management files,
  143: so that configuration on remote machines can be centrally managed.
  144: 
  145: =back
  146:

  169: =head2 ENVIRONMENT VARIABLE HANDLING
  170: 
  171: Configuration values can be overridden via environment variables. Environment variables use double underscores (__) to denote nested configuration keys and single underscores remain as part of the key name under the prefix namespace.
  172: 
  173: For example:
  174: 
  175:   APP_DATABASE__USER becomes database.user (nested structure)
  176: 
  177:     $ export APP_DATABASE__USER="env_user"
  178: 
  179: will override any value set for `database.user` in the configuration files.
  180: 
  181:   APP_LOGLEVEL becomes APP.loglevel (flat under prefix namespace)
  182: 
  183:   APP_API__RATE_LIMIT becomes api.rate_limit (mixed usage)
  184: 
  185: This allows you to override both top-level and nested configuration values using environment variables.
  186: 
  187: Configuration values can be overridden via the command line (C<@ARGV>).
  188: For instance, if you have a key in the configuration such as C<database.user>,
  189: you can override it by adding C<"--APP_DATABASE__USER=other_user_name"> to the command line arguments.
  190: This will override any value set for C<database.user> in the configuration files.

  192: =head2 EXAMPLE CONFIGURATION FLOW
  193: 
  194: =over 4
  195: 
  196: =item 1. Data Argument
  197: 
  198: The data passed into the constructor via the C<data> argument is the starting point.
  199: Essentially,
  200: this contains the default values.
  201: 
  202: =item 2. Loading Files
  203: 
  204: The module then looks for configuration files in the specified directories.
  205: It loads the following files in order of preference:
  206: C<base.yaml>, C<local.yaml>, C<base.json>, C<local.json>, C<base.xml>,
  207: C<local.xml>, C<base.ini>, and C<local.ini>.
  208: 
  209: If C<config_file> or C<config_files> is set, those files are loaded last.
  210: 
  211: If no C<config_dirs> is given, try hard to find the files in various places.
  212: 
  213: The value of C<config_dirs> can be overridden at runtime by the environment variable CONFIG_DIR
  214: (note that is just one directory, hence it's CONFIG_DIR not CONFIG_DIRS).
  215: 
  216: =item 3. Merging and Resolving
  217: 
  218: The module merges the contents of these files, with more specific configurations
  219: (e.g., C<local.*>) overriding general ones (e.g., C<base.*>).
  220: 
  221: =item 4. Environment Overrides
  222: 
  223: After loading and merging the configuration files,
  224: the environment variables are
  225: checked and used to override any conflicting settings.
  226: 
  227: =item 5. Command Line
  228: 
  229: Next, the command line arguments are checked and used to override any conflicting settings.
  230: 
  231: =item 6. Accessing Values
  232: 
  233: Values in the configuration can be accessed using a dotted notation
  234: (e.g., C<'database.user'>), regardless of the file format used.
  235: 
  236: =back

  342: applications that construct a C<Config::Abstraction> object before they know whether
  343: they will access it.
  344: 
  345: B<Differences from the default (eager) behaviour, and the debugging problems they cause:>
  346: 
  347: =over 4
  348: 
  349: =item 1. C<new()> always succeeds, even when no configuration exists.
  350: 
  351: In eager mode, C<new()> returns C<undef> immediately when no files are found and no
  352: C<data> was supplied, so a missing config is caught at the point of construction.
  353: In lazy mode, C<new()> always returns a blessed object.  If the configuration
  354: directories do not exist, the files are missing, or the prefix is wrong, you will
  355: not find out until the first accessor call - which may be deep inside your business
  356: logic, far from where the object was created.
  357: 
  358:   # Problem: the typo in config_dirs goes unnoticed until runtime
  359:   my $cfg = Config::Abstraction->new(
  360:       config_dirs => ['/etc/myapp/conifg'],   # typo - directory does not exist
  361:       lazy => 1,
  362:   );
  363:   # ... many lines later ...
  364:   my $host = $cfg->get('database.host');      # silently returns undef here
  365: 
  366: =item 2. Schema validation errors appear at the wrong place in the call stack.
  367: 
  368: When a C<schema> is supplied, eager mode validates the merged configuration inside
  369: C<new()> and throws immediately if the config does not match.  In lazy mode,
  370: validation is deferred to the first accessor call.  A schema violation therefore
  371: surfaces as an exception thrown by C<get()> or C<all()>, not by C<new()>, and the
  372: stack trace points to the accessor call rather than the construction site.  If the
  373: object is created in one module and accessed in another, the error message can be
  374: very misleading.
  375: 
  376: =item 3. Environment variables and C<@ARGV> are captured at access time, not construction time.
  377: 
  378: The module reads C<%ENV> and C<@ARGV> during C<_load_config()>.  In eager mode that
  379: happens in C<new()>, so the configuration reflects the environment at the moment the
  380: object is built.  In lazy mode, any change to C<%ENV> or C<@ARGV> between C<new()>
  381: and the first accessor call is silently picked up.  This makes test isolation harder:
  382: setting an environment variable I<after> constructing a lazy object will affect the
  383: values it returns, which is not the case with an eager object.
  384: 
  385: =item 4. File system state may change between construction and first use.
  386: 
  387: Because lazy mode defers all I/O, the files that are read are those that exist at the
  388: moment of first access, not at the moment C<new()> is called.  If a config file is
  389: written, deleted, or replaced between those two points (for example, by another
  390: process or test fixture), the object will silently use the new state.  An eager object
  391: is immune to this race.
  392: 
  393: =item 5. Errors from format parsers appear at accessor call sites.
  394: 
  395: Malformed YAML, JSON, XML, or INI files emit a C<carp> warning and are skipped during
  396: loading.  In eager mode those warnings appear near the program's startup.  In lazy mode
  397: they appear during the first accessor call, which can make it look as though a routine
  398: in your business logic is generating configuration warnings.
  399: 
  400: =back
  401: 
  402: B<When to use lazy loading:> It is most useful when a C<Config::Abstraction> object is
  403: created speculatively at module-load time and may never be accessed (for example, in a
  404: web framework where the config object is built for every request but some request paths
  405: never read it).  Avoid it when startup correctness is important, when you rely on
  406: C<new()> returning C<undef> to detect missing configuration, or when you use schema
  407: validation and need errors to point at the construction site.
  408: 
  409: =back

 1432: =head2 Remote configuration directories (Newcastle Connection)
 1433: 
 1434: Any entry in C<config_dirs> whose path begins with C</../> is treated as a
 1435: remote specification rather than a local directory:
 1436: 
 1437:   /../hostname/path/to/dir
 1438: 
 1439: The hostname and directory are extracted, and the same standard files searched
 1440: locally (C<base.yaml>, C<local.yaml>, C<base.json>, etc.) are fetched from
 1441: the remote machine via L<File::Slurp::Remote> over SSH.
 1442: 
 1443: When the hostname resolves to the local machine -- C<localhost>, C<127.0.0.1>,
 1444: C<::1>, or the value returned by C<Sys::Hostname::hostname()> (checked as
 1445: both fully-qualified and short form, case-insensitively) -- the C</../host/>
 1446: wrapper is silently unwrapped and the enclosed path is processed through the
 1447: normal local file pipeline instead.  No SSH connection is made.  This means a
 1448: configuration written for a shared remote host degrades gracefully when run on
 1449: that host itself:
 1450: 
 1451:   # On any other machine: fetches /etc/myapp over SSH
 1452:   # On cfg-server itself: reads /etc/myapp from disk directly
 1453:   config_dirs => ['/../cfg-server/etc/myapp']
 1454: 
 1455: Remote directories participate in the normal merge pipeline and can be freely
 1456: mixed with local ones:
 1457: 
 1458:   my $cfg = Config::Abstraction->new(
 1459:       config_dirs => [
 1460:           '/etc/myapp',                        # local
 1461:           '/../deploy@cfg-server/etc/myapp',   # remote via SSH (local on cfg-server)
 1462:       ],
 1463:   );
 1464: 
 1465: SSH authentication is handled by the system SSH client.
 1466: No extra constructor options are required; use your SSH agent or
 1467: C<~/.ssh/config> for host-specific settings.
 1468: 
 1469: L<File::Slurp::Remote> must be installed for remote directories to work.
 1470: If it is absent the directory is silently skipped and a warning is emitted.
 1471: 
 1472: =head3 Why C</../> (the Newcastle Connection convention)
 1473: 
 1474: Several syntaxes were considered for marking a C<config_dirs> entry as remote.
 1475: Each alternative was rejected for a concrete reason:
 1476: 
 1477: =over 4
 1478: 
 1479: =item C<hostname/path> -- ambiguous
 1480: 
 1481: Indistinguishable from a relative local directory named C<hostname>.
 1482: The module cannot tell at parse time whether C<myserver/etc> is a two-level
 1483: local path or a remote specification.
 1484: 
 1485: =item C<hostname:/path> -- collides with Windows drive letters
 1486: 
 1487: The C<X:\> drive-letter convention on Windows uses exactly the same
 1488: C<letter:> prefix.  A single-letter hostname would be misidentified as a
 1489: drive, and path-normalisation code on Windows would mangle it.
 1490: 
 1491: =item C<file://hostname/path> -- wrong semantics
 1492: 
 1493: RFC 8089 defines C<file://> as a reference to a B<local> file.
 1494: C<file:///etc/passwd> (three slashes, empty host) is the canonical local form;
 1495: C<file://hostname/path> is reserved for the host component but is explicitly
 1496: discouraged for general use and is not understood by most tooling as meaning
 1497: SSH.
 1498: 
 1499: =item C<ssh://hostname/path> -- requires URI parsing
 1500: 
 1501: Introduces a dependency on URI parsing (or a bespoke prefix check) and
 1502: implies a specific transport.  C<File::Slurp::Remote> already abstracts
 1503: the transport; encoding C<ssh://> in the path would be misleading if a future
 1504: version of that module supports other transports such as C<rsync://>.
 1505: 
 1506: =item C</../hostname/path> -- the Newcastle Connection
 1507: 
 1508: The Newcastle Connection (Brownbridge, Dion, Elsworth, 1982) is a distributed
 1509: Unix convention in which the token C</../> at the start of a pathname means
 1510: "leave the local namespace and enter the named remote host".
 1511: It works because C</../> B<cannot exist> as a real filesystem path:
 1512: C<..> from the root directory resolves back to the root on every POSIX system,
 1513: so C</../> always denotes the root itself, never a child of the root.
 1514: No pathname-normalisation step, C<chdir>, or filesystem traversal will ever
 1515: produce a path that legitimately begins with C</../>, which means the prefix
 1516: is a permanent, collision-free sentinel that requires only a regex to detect.
 1517: 
 1518: =back
 1519: 
 1520: The Newcastle Connection prefix is therefore the only choice that is:
 1521: 
 1522: =over 4
 1523: 
 1524: =item * unambiguous on all platforms (POSIX and Windows)
 1525: 
 1526: =item * impossible to produce accidentally from a real local path
 1527: 
 1528: =item * detectable with a single C<m{^\Q/../\E}> regex, no URI parser needed
 1529: 
 1530: =item * transport-neutral (the hostname is passed to whatever remote driver is installed)
 1531: 
 1532: =back
