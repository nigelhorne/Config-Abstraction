   34: =head1 SYNOPSIS
   35: 
   36: C<Config::Abstraction> lets you load configuration from multiple sources,
   37: such as files, environment variables, and in-code defaults,
   38: and merge them with predictable precedence.
   39: It provides a consistent API for accessing the configuration settings, regardless of where they came from,
   40: this helps keep your application's or class's configuration flexible, centralized, and easy to override.
   41: 
   42:   use Config::Abstraction;
   43: 
   44:   my $config = Config::Abstraction->new(
   45:     config_dirs => ['config'],
   46:     env_prefix => 'APP_',
   47:     flatten => 0,
   48:   );
   49: 
   50:   my $db_user = $config->get('database.user');
   51: 
   52: =head1 DESCRIPTION
   53: 
   54: C<Config::Abstraction> is a flexible configuration management layer that sits above C<Config::*> modules.
   55: It provides a simple way to layer multiple configuration sources with predictable merge order.
   56: It lets you define sources such as:
   57: 
   58: =over 4
   59: 
   60: =item * Perl hashes (in-memory defaults or dynamic values)
   61: 
   62: =item * Environment variables (with optional prefixes)
   63: 
   64: =item * Configuration files (YAML, JSON, INI, or plain key=value)
   65: 
   66: =item * Command-line arguments
   67: 
   68: =back
   69: 
   70: Sources are applied in the order they are provided. Later sources override
   71: earlier ones unless a key is explicitly set to C<undef> in the later source.
   72: 
   73: In addition to using drivers to load configuration data from multiple file
   74: formats (YAML, JSON, XML, and INI),
   75: it also allows levels of configuration, each of which overrides the lower levels.
   76: So, it also integrates environment variable
   77: overrides and command line arguments for runtime configuration adjustments.
   78: This module is designed to help developers manage layered configurations that can be loaded from files and overridden at run-time for debugging,
   79: offering a modern, robust and dynamic approach
   80: to configuration management.
   81: 
   82: =head2 Merge Precedence Diagram
   83: 
   84:   +----------------+
   85:   |   CLI args     |  (Highest priority)
   86:   +----------------+
   87:   | Environment    |
   88:   +----------------+
   89:   | Config file(s) |
   90:   +----------------+
   91:   | Defaults       |  (Lowest priority)
   92:   +----------------+

   94: =head2 KEY FEATURES
   95: 
   96: =over 4
   97: 
   98: =item * Multi-Format Support
   99: 
  100: Supports configuration files in YAML, JSON, XML, and INI formats.
  101: Automatically merges configuration data from these different formats,
  102: allowing hierarchical configuration management.
  103: 
  104: =item * Environment Variable Overrides
  105: 
  106: Allows environment variables to override values in the configuration files.
  107: By setting environment variables with a specific prefix (default: C<APP_>),
  108: values in the configuration files can be dynamically adjusted without modifying
  109: the file contents.
  110: 
  111: =item * Flattened Configuration Option
  112: 
  113: Optionally supports flattening the configuration structure. This converts deeply
  114: nested configuration keys into a flat key-value format (e.g., C<database.user>
  115: instead of C<database-E<gt>{user}>). This makes accessing values easier for
  116: applications that prefer flat structures or need compatibility with flat
  117: key-value stores.
  118: 
  119: =item * Layered Configuration
  120: 
  121: Supports merging multiple layers of configuration files. For example, you can
  122: have a C<base.yaml> configuration file that provides default values, and a
  123: C<local.yaml> (or C<local.json>, C<local.xml>, etc.) file that overrides
  124: specific values. This allows for environment-specific configurations while
  125: keeping defaults intact.
  126: 
  127: =item * Merge Strategy
  128: 
  129: The module merges the configuration data intelligently, allowing values in more
  130: specific files (like C<local.yaml>, C<local.json>, C<local.xml>, C<local.ini>)
  131: to override values in base files. This enables a flexible and layered configuration
  132: system where you can set defaults and override them for specific environments.
  133: 
  134: =item * Error Handling
  135: 
  136: Includes error handling for loading configuration files.
  137: If any file fails to
  138: load (e.g., due to syntax issues), the module will throw descriptive error
  139: messages to help with debugging.
  140: 
  141: =back
  142:

  144: 
  145: =over 4
  146: 
  147: =item * YAML (C<*.yaml>, C<*.yml>)
  148: 
  149: The module supports loading YAML files using the C<YAML::XS> module.
  150: 
  151: =item * JSON (C<*.json>)

  154: 
  155: =item * XML (C<*.xml>)
  156:

  162:

  165: =head2 ENVIRONMENT VARIABLE HANDLING
  166: 
  167: Configuration values can be overridden via environment variables. Environment variables use double underscores (__) to denote nested configuration keys and single underscores remain as part of the key name under the prefix namespace.
  168: 
  169: For example:
  170: 
  171:   APP_DATABASE__USER becomes database.user (nested structure)
  172: 
  173:     $ export APP_DATABASE__USER="env_user"
  174: 
  175: will override any value set for `database.user` in the configuration files.
  176: 
  177:   APP_LOGLEVEL becomes APP.loglevel (flat under prefix namespace)
  178: 
  179:   APP_API__RATE_LIMIT becomes api.rate_limit (mixed usage)
  180: 
  181: This allows you to override both top-level and nested configuration values using environment variables.
  182: 
  183: Configuration values can be overridden via the command line (C<@ARGV>).
  184: For instance, if you have a key in the configuration such as C<database.user>,
  185: you can override it by adding C<"--APP_DATABASE__USER=other_user_name"> to the command line arguments.
  186: This will override any value set for C<database.user> in the configuration files.
  187: 
  188: =head2 EXAMPLE CONFIGURATION FLOW
  189: 
  190: =over 4
  191: 
  192: =item 1. Data Argument
  193: 
  194: The data passed into the constructor via the C<data> argument is the starting point.
  195: Essentially,
  196: this contains the default values.
  197: 
  198: =item 2. Loading Files
  199: 
  200: The module then looks for configuration files in the specified directories.
  201: It loads the following files in order of preference:
  202: C<base.yaml>, C<local.yaml>, C<base.json>, C<local.json>, C<base.xml>,
  203: C<local.xml>, C<base.ini>, and C<local.ini>.
  204: 
  205: If C<config_file> or C<config_files> is set, those files are loaded last.
  206: 
  207: If no C<config_dirs> is given, try hard to find the files in various places.
  208: 
  209: =item 3. Merging and Resolving
  210: 
  211: The module merges the contents of these files, with more specific configurations
  212: (e.g., C<local.*>) overriding general ones (e.g., C<base.*>).
  213: 
  214: =item 4. Environment Overrides
  215: 
  216: After loading and merging the configuration files,
  217: the environment variables are
  218: checked and used to override any conflicting settings.
  219: 
  220: =item 5. Command Line
  221: 
  222: Next, the command line arguments are checked and used to override any conflicting settings.
  223: 
  224: =item 6. Accessing Values
  225: 
  226: Values in the configuration can be accessed using a dotted notation
  227: (e.g., C<'database.user'>), regardless of the file format used.
  228: 
  229: =back
