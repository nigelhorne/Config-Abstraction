   33: =head1 SYNOPSIS
   34: 
   35: C<Config::Abstraction> lets you load configuration from multiple sources,
   36: such as files, environment variables, and in-code defaults,
   37: and merge them with predictable precedence.
   38: It provides a consistent API for accessing the configuration settings, regardless of where they came from,
   39: this helps keep your application's or class's configuration flexible, centralized, separate from your code base and easy to override.
   40: 
   41:   use Config::Abstraction;
   42: 
   43:   my $config = Config::Abstraction->new(
   44:     config_dirs => ['config'],
   45:     env_prefix => 'APP_',

   49:   my $db_user = $config->get('database.user');

   51: =head1 DESCRIPTION
   52: 
   53: C<Config::Abstraction> is a flexible configuration management layer that sits above C<Config::*> modules.
   54: It provides a simple way to layer multiple configuration sources with predictable merge order.
   55: It lets you define sources such as:
   56: 
   57: =over 4
   58: 
   59: =item * Perl hashes (in-memory defaults or dynamic values)
   60: 
   61: =item * Environment variables (with optional prefixes)
   62: 
   63: =item * Configuration files (YAML, JSON, INI, or plain key=value)
   64: 
   65: =item * Command-line arguments
   66: 
   67: =back
   68: 
   69: Sources are applied in the order they are provided. Later sources override
   70: earlier ones unless a key is explicitly set to C<undef> in the later source.
   71: 
   72: In addition to using drivers to load configuration data from multiple file
   73: formats (YAML, JSON, XML, and INI),
   74: it also allows levels of configuration, each of which overrides the lower levels.
   75: So, it also integrates environment variable
   76: overrides and command line arguments for runtime configuration adjustments.
   77: This module is designed to help developers manage layered configurations that can be loaded from files and overridden at run-time for debugging,
   78: offering a modern, robust and dynamic approach
   79: to configuration management.
   80:

   83:   +----------------+
   84:   |   CLI args     |  (Highest priority)
   85:   +----------------+
   86:   | Environment    |
   87:   +----------------+
   88:   | Config file(s) |
   89:   +----------------+
   90:   | Defaults       |  (Lowest priority)

  169: =head2 ENVIRONMENT VARIABLE HANDLING
  170: 
  171: Configuration values can be overridden via environment variables. Environment variables use double underscores (__) to denote nested configuration keys and single underscores remain as part of the key name under the prefix namespace.
  172: 
  173: For example:
  174: 
  175:   APP_DATABASE__USER becomes database.user (nested structure)
  176: 
  177:     $ export APP_DATABASE__USER="env_user"
  178: 
  179: will override any value set for `database.user` in the configuration files.
  180: 
  181:   APP_LOGLEVEL becomes APP.loglevel (flat under prefix namespace)
  182: 
  183:   APP_API__RATE_LIMIT becomes api.rate_limit (mixed usage)
  184: 
  185: This allows you to override both top-level and nested configuration values using environment variables.
  186: 
  187: Configuration values can be overridden via the command line (C<@ARGV>).
  188: For instance, if you have a key in the configuration such as C<database.user>,
  189: you can override it by adding C<"--APP_DATABASE__USER=other_user_name"> to the command line arguments.
  190: This will override any value set for C<database.user> in the configuration files.

 1385: =head2 Remote configuration directories (Newcastle Connection)
 1386: 
 1387: Any entry in C<config_dirs> whose path begins with C</../> is treated as a
 1388: remote specification rather than a local directory:
 1389: 
 1390:   /../hostname/path/to/dir
 1391: 
 1392: The hostname and directory are extracted, and the same standard files searched
 1393: locally (C<base.yaml>, C<local.yaml>, C<base.json>, etc.) are fetched from
 1394: the remote machine via L<File::Slurp::Remote> over SSH.
 1395: 
 1396: When the hostname resolves to the local machine -- C<localhost>, C<127.0.0.1>,
 1397: C<::1>, or the value returned by C<Sys::Hostname::hostname()> (checked as
 1398: both fully-qualified and short form, case-insensitively) -- the C</../host/>
 1399: wrapper is silently unwrapped and the enclosed path is processed through the
 1400: normal local file pipeline instead.  No SSH connection is made.  This means a
 1401: configuration written for a shared remote host degrades gracefully when run on
 1402: that host itself:
 1403: 
 1404:   # On any other machine: fetches /etc/myapp over SSH
 1405:   # On cfg-server itself: reads /etc/myapp from disk directly
 1406:   config_dirs => ['/../cfg-server/etc/myapp']
 1407: 
 1408: Remote directories participate in the normal merge pipeline and can be freely
 1409: mixed with local ones:
 1410: 
 1411:   my $cfg = Config::Abstraction->new(
 1412:       config_dirs => [
 1413:           '/etc/myapp',                        # local
 1414:           '/../deploy@cfg-server/etc/myapp',   # remote via SSH (local on cfg-server)
 1415:       ],
 1416:   );
 1417: 
 1418: SSH authentication is handled by the system SSH client.
 1419: No extra constructor options are required; use your SSH agent or
 1420: C<~/.ssh/config> for host-specific settings.
 1421: 
 1422: L<File::Slurp::Remote> must be installed for remote directories to work.
 1423: If it is absent the directory is silently skipped and a warning is emitted.
 1424: 
 1425: =head3 Why C</../> (the Newcastle Connection convention)
 1426: 
 1427: Several syntaxes were considered for marking a C<config_dirs> entry as remote.
 1428: Each alternative was rejected for a concrete reason:
 1429: 
 1430: =over 4
 1431: 
 1432: =item C<hostname/path> -- ambiguous
 1433: 
 1434: Indistinguishable from a relative local directory named C<hostname>.
 1435: The module cannot tell at parse time whether C<myserver/etc> is a two-level
 1436: local path or a remote specification.
 1437: 
 1438: =item C<hostname:/path> -- collides with Windows drive letters
 1439: 
 1440: The C<X:\> drive-letter convention on Windows uses exactly the same
 1441: C<letter:> prefix.  A single-letter hostname would be misidentified as a
 1442: drive, and path-normalisation code on Windows would mangle it.
 1443: 
 1444: =item C<file://hostname/path> -- wrong semantics
 1445: 
 1446: RFC 8089 defines C<file://> as a reference to a B<local> file.
 1447: C<file:///etc/passwd> (three slashes, empty host) is the canonical local form;
 1448: C<file://hostname/path> is reserved for the host component but is explicitly
 1449: discouraged for general use and is not understood by most tooling as meaning
 1450: SSH.
 1451: 
 1452: =item C<ssh://hostname/path> -- requires URI parsing
 1453: 
 1454: Introduces a dependency on URI parsing (or a bespoke prefix check) and
 1455: implies a specific transport.  C<File::Slurp::Remote> already abstracts
 1456: the transport; encoding C<ssh://> in the path would be misleading if a future
 1457: version of that module supports other transports such as C<rsync://>.
 1458: 
 1459: =item C</../hostname/path> -- the Newcastle Connection
 1460: 
 1461: The Newcastle Connection (Brownbridge, Dion, Elsworth, 1982) is a distributed
 1462: Unix convention in which the token C</../> at the start of a pathname means
 1463: "leave the local namespace and enter the named remote host".
 1464: It works because C</../> B<cannot exist> as a real filesystem path:
 1465: C<..> from the root directory resolves back to the root on every POSIX system,
 1466: so C</../> always denotes the root itself, never a child of the root.
 1467: No pathname-normalisation step, C<chdir>, or filesystem traversal will ever
 1468: produce a path that legitimately begins with C</../>, which means the prefix
 1469: is a permanent, collision-free sentinel that requires only a regex to detect.
 1470: 
 1471: =back
 1472: 
 1473: The Newcastle Connection prefix is therefore the only choice that is:
 1474: 
 1475: =over 4
 1476: 
 1477: =item * unambiguous on all platforms (POSIX and Windows)
 1478: 
 1479: =item * impossible to produce accidentally from a real local path
 1480: 
 1481: =item * detectable with a single C<m{^\Q/../\E}> regex, no URI parser needed
 1482: 
 1483: =item * transport-neutral (the hostname is passed to whatever remote driver is installed)
 1484: 
 1485: =back
