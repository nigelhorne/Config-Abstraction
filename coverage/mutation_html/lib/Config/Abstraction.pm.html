   33: =head1 SYNOPSIS
   34: 
   35: C<Config::Abstraction> lets you load configuration from multiple sources,
   36: such as files, environment variables, and in-code defaults,
   37: and merge them with predictable precedence.
   38: It provides a consistent API for accessing the configuration settings, regardless of where they came from,
   39: this helps keep your application's or class's configuration flexible, centralized, separate from your code base and easy to override.
   40: 
   41:   use Config::Abstraction;
   42: 
   43:   my $config = Config::Abstraction->new(
   44:     config_dirs => ['config'],
   45:     env_prefix => 'APP_',
   46:     flatten => 0,
   47:   );
   48: 
   49:   my $db_user = $config->get('database.user');

   51: =head1 DESCRIPTION
   52: 
   53: C<Config::Abstraction> is a flexible configuration management layer that sits above C<Config::*> modules.
   54: It provides a simple way to layer multiple configuration sources with predictable merge order.
   55: It lets you define sources such as:
   56: 
   57: =over 4
   58: 
   59: =item * Perl hashes (in-memory defaults or dynamic values)
   60: 
   61: =item * Environment variables (with optional prefixes)
   62: 
   63: =item * Configuration files (YAML, JSON, INI, or plain key=value)
   64: 
   65: =item * Command-line arguments
   66: 
   67: =back
   68: 
   69: Sources are applied in the order they are provided. Later sources override
   70: earlier ones unless a key is explicitly set to C<undef> in the later source.
   71: 
   72: In addition to using drivers to load configuration data from multiple file
   73: formats (YAML, JSON, XML, and INI),
   74: it also allows levels of configuration, each of which overrides the lower levels.
   75: So, it also integrates environment variable
   76: overrides and command line arguments for runtime configuration adjustments.
   77: This module is designed to help developers manage layered configurations that can be loaded from files and overridden at run-time for debugging,
   78: offering a modern, robust and dynamic approach
   79: to configuration management.
   80: 
   81: =head2 Merge Precedence Diagram
   82: 
   83:   +----------------+
   84:   |   CLI args     |  (Highest priority)
   85:   +----------------+
   86:   | Environment    |
   87:   +----------------+
   88:   | Config file(s) |
   89:   +----------------+
   90:   | Defaults       |  (Lowest priority)
   91:   +----------------+

   93: =head2 KEY FEATURES
   94: 
   95: =over 4
   96: 
   97: =item * Multi-Format Support
   98: 
   99: Supports configuration files in YAML, JSON, XML, and INI formats.
  100: Automatically merges configuration data from these different formats,
  101: allowing hierarchical configuration management.
  102: 
  103: =item * Environment Variable Overrides
  104: 
  105: Allows environment variables to override values in the configuration files.
  106: By setting environment variables with a specific prefix (default: C<APP_>),
  107: values in the configuration files can be dynamically adjusted without modifying
  108: the file contents.
  109: 
  110: =item * Flattened Configuration Option
  111: 
  112: Optionally supports flattening the configuration structure. This converts deeply
  113: nested configuration keys into a flat key-value format (e.g., C<database.user>
  114: instead of C<database-E<gt>{user}>). This makes accessing values easier for
  115: applications that prefer flat structures or need compatibility with flat
  116: key-value stores.
  117: 
  118: =item * Layered Configuration
  119: 
  120: Supports merging multiple layers of configuration files. For example, you can
  121: have a C<base.yaml> configuration file that provides default values, and a
  122: C<local.yaml> (or C<local.json>, C<local.xml>, etc.) file that overrides
  123: specific values. This allows for environment-specific configurations while
  124: keeping defaults intact.
  125: 
  126: =item * Merge Strategy
  127: 
  128: The module merges the configuration data intelligently, allowing values in more
  129: specific files (like C<local.yaml>, C<local.json>, C<local.xml>, C<local.ini>)
  130: to override values in base files. This enables a flexible and layered configuration
  131: system where you can set defaults and override them for specific environments.
  132: 
  133: =item * Error Handling
  134: 
  135: Includes error handling for loading configuration files.
  136: If any file fails to
  137: load (e.g., due to syntax issues), the module will throw descriptive error
  138: messages to help with debugging.
  139: 
  140: =item * Centralized Configuration Management
  141: 
  142: Supports remote configuration management files,
  143: so that configuration on remote machines can be centrally managed.
  144: 
  145: =back

  169: =head2 ENVIRONMENT VARIABLE HANDLING
  170: 
  171: Configuration values can be overridden via environment variables. Environment variables use double underscores (__) to denote nested configuration keys and single underscores remain as part of the key name under the prefix namespace.
  172: 
  173: For example:
  174: 
  175:   APP_DATABASE__USER becomes database.user (nested structure)
  176: 
  177:     $ export APP_DATABASE__USER="env_user"
  178: 
  179: will override any value set for `database.user` in the configuration files.
  180: 
  181:   APP_LOGLEVEL becomes APP.loglevel (flat under prefix namespace)
  182: 
  183:   APP_API__RATE_LIMIT becomes api.rate_limit (mixed usage)
  184: 
  185: This allows you to override both top-level and nested configuration values using environment variables.
  186: 
  187: Configuration values can be overridden via the command line (C<@ARGV>).
  188: For instance, if you have a key in the configuration such as C<database.user>,
  189: you can override it by adding C<"--APP_DATABASE__USER=other_user_name"> to the command line arguments.
  190: This will override any value set for C<database.user> in the configuration files.

  192: =head2 EXAMPLE CONFIGURATION FLOW
  193: 
  194: =over 4
  195: 
  196: =item 1. Data Argument
  197: 
  198: The data passed into the constructor via the C<data> argument is the starting point.
  199: Essentially,
  200: this contains the default values.
  201: 
  202: =item 2. Loading Files
  203: 
  204: The module then looks for configuration files in the specified directories.
  205: It loads the following files in order of preference:
  206: C<base.yaml>, C<local.yaml>, C<base.json>, C<local.json>, C<base.xml>,
  207: C<local.xml>, C<base.ini>, and C<local.ini>.
  208: 
  209: If C<config_file> or C<config_files> is set, those files are loaded last.
  210: 
  211: If no C<config_dirs> is given, try hard to find the files in various places.
  212: 
  213: The value of C<config_dirs> can be overridden at runtime by the environment variable CONFIG_DIR
  214: (note that is just one directory, hence it's CONFIG_DIR not CONFIG_DIRS).
  215: 
  216: =item 3. Merging and Resolving
  217: 
  218: The module merges the contents of these files, with more specific configurations
  219: (e.g., C<local.*>) overriding general ones (e.g., C<base.*>).
  220: 
  221: =item 4. Environment Overrides
  222: 
  223: After loading and merging the configuration files,
  224: the environment variables are
  225: checked and used to override any conflicting settings.
  226: 
  227: =item 5. Command Line
  228: 
  229: Next, the command line arguments are checked and used to override any conflicting settings.
  230: 
  231: =item 6. Accessing Values
  232: 
  233: Values in the configuration can be accessed using a dotted notation
  234: (e.g., C<'database.user'>), regardless of the file format used.
  235: 
  236: =back

 1014: =head2 Remote configuration directories (Newcastle Connection)
 1015: 
 1016: Any entry in C<config_dirs> whose path begins with C</../> is treated as a
 1017: remote specification rather than a local directory:
 1018: 
 1019:   /../hostname/path/to/dir
 1020: 
 1021: The hostname and directory are extracted, and the same standard files searched
 1022: locally (C<base.yaml>, C<local.yaml>, C<base.json>, etc.) are fetched from
 1023: the remote machine via L<File::Slurp::Remote> over SSH.
 1024: 
 1025: When the hostname resolves to the local machine -- C<localhost>, C<127.0.0.1>,
 1026: C<::1>, or the value returned by C<Sys::Hostname::hostname()> (checked as
 1027: both fully-qualified and short form, case-insensitively) -- the C</../host/>
 1028: wrapper is silently unwrapped and the enclosed path is processed through the
 1029: normal local file pipeline instead.  No SSH connection is made.  This means a
 1030: configuration written for a shared remote host degrades gracefully when run on
 1031: that host itself:
 1032: 
 1033:   # On any other machine: fetches /etc/myapp over SSH
 1034:   # On cfg-server itself: reads /etc/myapp from disk directly
 1035:   config_dirs => ['/../cfg-server/etc/myapp']
 1036: 
 1037: Remote directories participate in the normal merge pipeline and can be freely
 1038: mixed with local ones:
 1039: 
 1040:   my $cfg = Config::Abstraction->new(
 1041:       config_dirs => [
 1042:           '/etc/myapp',                        # local
 1043:           '/../deploy@cfg-server/etc/myapp',   # remote via SSH (local on cfg-server)
 1044:       ],
 1045:   );
 1046: 
 1047: SSH authentication is handled by the system SSH client.
 1048: No extra constructor options are required; use your SSH agent or
 1049: C<~/.ssh/config> for host-specific settings.
 1050: 
 1051: L<File::Slurp::Remote> must be installed for remote directories to work.
 1052: If it is absent the directory is silently skipped and a warning is emitted.
 1053: 
 1054: =head3 Why C</../> (the Newcastle Connection convention)
 1055: 
 1056: Several syntaxes were considered for marking a C<config_dirs> entry as remote.
 1057: Each alternative was rejected for a concrete reason:
 1058: 
 1059: =over 4
 1060: 
 1061: =item C<hostname/path> -- ambiguous
 1062: 
 1063: Indistinguishable from a relative local directory named C<hostname>.
 1064: The module cannot tell at parse time whether C<myserver/etc> is a two-level
 1065: local path or a remote specification.
 1066: 
 1067: =item C<hostname:/path> -- collides with Windows drive letters
 1068: 
 1069: The C<X:\> drive-letter convention on Windows uses exactly the same
 1070: C<letter:> prefix.  A single-letter hostname would be misidentified as a
 1071: drive, and path-normalisation code on Windows would mangle it.
 1072: 
 1073: =item C<file://hostname/path> -- wrong semantics
 1074: 
 1075: RFC 8089 defines C<file://> as a reference to a B<local> file.
 1076: C<file:///etc/passwd> (three slashes, empty host) is the canonical local form;
 1077: C<file://hostname/path> is reserved for the host component but is explicitly
 1078: discouraged for general use and is not understood by most tooling as meaning
 1079: SSH.
 1080: 
 1081: =item C<ssh://hostname/path> -- requires URI parsing
 1082: 
 1083: Introduces a dependency on URI parsing (or a bespoke prefix check) and
 1084: implies a specific transport.  C<File::Slurp::Remote> already abstracts
 1085: the transport; encoding C<ssh://> in the path would be misleading if a future
 1086: version of that module supports other transports such as C<rsync://>.
 1087: 
 1088: =item C</../hostname/path> -- the Newcastle Connection
 1089: 
 1090: The Newcastle Connection (Brownbridge, Dion, Elsworth, 1982) is a distributed
 1091: Unix convention in which the token C</../> at the start of a pathname means
 1092: "leave the local namespace and enter the named remote host".
 1093: It works because C</../> B<cannot exist> as a real filesystem path:
 1094: C<..> from the root directory resolves back to the root on every POSIX system,
 1095: so C</../> always denotes the root itself, never a child of the root.
 1096: No pathname-normalisation step, C<chdir>, or filesystem traversal will ever
 1097: produce a path that legitimately begins with C</../>, which means the prefix
 1098: is a permanent, collision-free sentinel that requires only a regex to detect.
 1099: 
 1100: =back
 1101: 
 1102: The Newcastle Connection prefix is therefore the only choice that is:
 1103: 
 1104: =over 4
 1105: 
 1106: =item * unambiguous on all platforms (POSIX and Windows)
 1107: 
 1108: =item * impossible to produce accidentally from a real local path
 1109: 
 1110: =item * detectable with a single C<m{^\Q/../\E}> regex, no URI parser needed
 1111: 
 1112: =item * transport-neutral (the hostname is passed to whatever remote driver is installed)
 1113: 
 1114: =back
